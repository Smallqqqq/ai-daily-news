## open-code-review — 阿里开源的代码审查 CLI，同模型下 token 只用通义版 Agent 的 1/9

![[ocr-demo-1.png]]
![[ocr-demo-2.png]]

  用 Claude Code 这类通用 Agent 做代码审查，失败模式高度一致：改了一个文件 80% 的行数，它漏掉了根目录的权限改动；说"第三个方法有问题"，指到的却是第 5 行；上一轮审得很细，这一轮同一类问题又放过去了。阿里给这套问题的诊断很直接：纯语言驱动的架构对审查过程没有硬约束，覆盖不完整、定位漂移、质量不稳定，都是同一根因。open-code-review（命令行 `ocr`）就是公开的解法，源自阿里集团内部在用的代码审查助手，6 月底开源、不到一个月冲到 22.1K stars——9 月 7 日刚登顶 GitHub Trending，周增约 4,750 星。

  架构上它拆成两半，各司其职。确定性工程这一半不碰模型：先做精确的文件筛选（哪些文件要审、哪些过滤掉，比如只有测试改了就不该重读一遍业务代码），再把相关文件智能打包成一个审查单元送进单个子 Agent（`message_en.properties` 和 `message_zh.properties` 会被捆绑审查，避免出现"英文键改了中文键没人管"这类遗漏），打包后的大变更集能并行跑；规则匹配走模板引擎 + 文件特征，比纯语言驱动稳定；还有外挂的定位和反思组件，独立修正 AI 评论的位置与内容偏差。Agent 这一半只管动态决策：场景化提示词是为代码审查调优过的，工具集是从生产工具调用轨迹里蒸馏出来的——先统计频率分布、重复率、调用链影响，再把通用 Agent 工具换成为审查而生的工具子集。

  效果在 AACR-Bench 有据可查：50 个热门开源仓库、200 个真实 PR、10 种编程语言、80 多位资深工程师交叉标注、共 1,505 个标注缺陷，数据集挂在 Hugging Face。同样底层模型下，OCR 的准确率（Precision）和 F1 显著高于 Claude Code，token 消耗约为其 1/9，速度更快；召回率刻意压低，官方明说是"以精准度换取低噪声"——少报但报得准，这对合并前门禁是合理取舍。典型用法是 PR 级别的门禁：GitHub Actions、GitLab CI、Gerrit、GitFlic 都有集成，跑完输出 JSON，或者用 `ocr delegate` 委托模式把你自己的编码 Agent 当宿主——Claude Code、Codex、Cursor、OpenCode 的模型直接上场，OCR 连 API key 都不用配（QCA Forward 场景再单独配）。

```bash
# 前置条件：Git >= 2.41
npm install -g @alibaba-group/open-code-review

# 交互式配置供应商与模型（内置选项或自定义，自动测连通性）
ocr config provider
ocr config model

# 工作区模式：审查所有暂存、未暂存、未跟踪的变更
ocr review

# 分支范围（merge-base 定位）与单个提交
ocr review --from main --to feature-branch
ocr review --commit abc123

# 中断恢复 + 全量文件扫描（无需 git 历史）
ocr review --from main --to feature-branch --resume <session-id>
ocr scan --path internal/agent

# 输出 JSON，供宿主 agent / CI 消费
ocr review --format json --output result.json

# 委托模式：由 Claude Code / Codex / Cursor 用自己的模型执行审查
ocr delegate preview
ocr delegate rule src/main.go src/handler.go
```

  我选它的原因：PR-AF 的深度审查质量更高但是慢——35-50 分钟的流水线适合合并前最后一道门禁，不适合每个 PR 都跑；Pullfrog 是跑在 Actions 里的多面手 Agent（能做的不止审查），且 beta 期功能在变；CodeRabbit 和 Copilot Review 要订阅。OCR 是唯一把"不会漏文件、不会指错行、不会反复横跳"用工程手段锁死的开源方案——同样底层模型下 1/9 的 token 支出，也是它在 CI 里能跑得勤快的底气。

## dot-ai — 用大白话部署到任意 Kubernetes 集群，MCP 里说一句就能干活

![[dotai-demo.png]]

  日常部署 K8s 有一个尴尬的断层：环境里装配的是资深 SRE 的规则——这些命名空间归谁、哪些镜像版本准入、配置文件的模板从哪来，全部压在文档和人的脑子里。AI 编码 Agent 能写代码、能跑构建，真让它"把这个服务部署到预发集群"，它要么没权限、要么不知道往哪放、要么绕过了本来该过的审核。dot-ai（DevOps AI Toolkit）处理的正是这一层：一个双模式 Agent，面向任何 Kubernetes 集群，用自然语言完成部署与治理。

  工作原理三个关键词。一是**动态发现**：不预写集群清单，代理自己探测当前环境里有哪些集群，摸清它们的状态；二是**双模式入口**：MCP 服务器接入编码助手（Claude Code、Cursor、Windsurf、VS Code Copilot 都支持，Claude Code 里 `/mcp` 选中服务器走 OAuth 浏览器登录即可），CLI 供脚本、CI/CD 管道和想要省 token 的场景直连，同一套工具能力；三是**自然语言治理**：部署建议、修复与根因分析、组织模式与策略管理（governance 文件随仓库自动初始化）、组织文档语义搜索，都在自然语言层面完成。技术上用 MCP Protocol + Vercel AI SDK + Kubernetes + CNCF 生态搭起来，模型随你配，API key 自己带。

  典型场景两个。一是 Agent 拿到它的 MCP 后，一句"把这个版本部署到 staging，但别碰 customer 命名空间"——部署、审计、策略判定走完整流程。二是存量治理：让 AI 解释"为什么上周的发布失败了"、按组织文档里的约定自动生成部署规则，历史 repo 的 governance 文件初始化交给工具做。项目起底是 DevOps 教育者 Viktor Farcic（DevOps Toolkit 作者）维护的，beta 但 1,333 次提交、336 颗星、76 个 fork，用 OpenTelemetry 埋点（可关）——看着像个真工具，不是演示项目。验证接入的办法很直接：接完问一句 "Show dot-ai status"，返回里包含 Kubernetes 连接、向量库和完整工具清单，有没有配好一目了然。

```bash
# 方式一：完整 stack（推荐入门，含 Helm chart 部署）
#   https://devopstoolkit.ai/docs/stack

# 方式二：npm 包直接装 CLI
npm install -g @vfarcic/dot-ai

# 接入 Claude Code（项目中放 .mcp.json，Token 来自部署环境变量 DOT_AI_AUTH_TOKEN）
{
  "mcpServers": {
    "dot-ai": {
      "type": "http",
      "url": "http://dot-ai.127.0.0.1.nip.io",
      "headers": { "Authorization": "Bearer <your-auth-token>" }
    }
  }
}

# 接完问一句验证：
# "Show dot-ai status"
```

| 工具 | 安装方式 | 核心特点 | 价格 | 热度 |

  Kagent 热度更高，但定位是"把 Agent 建在 K8s 上"的基础设施框架，要写 CRD、运维控制面；dot-ai 的定位是"给开发团队用的部署助手"，小团队接一个 MCP 就能让 Agent 说人话部署，要我在两者之间选，这条立等可用的优势比 3.3K 星更值。stakpak 概念接近但还早。约束也写明：336 颗星、beta 状态，适合试点用，生产级大规模组织还得自己压测。
