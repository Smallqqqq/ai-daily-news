## grok-build — SpaceX/xAI 开源的终端全屏编码 Agent，22K+ stars

![[grok-build-demo.png]]

  Claude Code 之后，终端编码 Agent 这个品类突然拥挤了起来。Codex CLI、Gemini CLI、Qwen Code、Kilo CLI——每家 AI 厂商都推出了自己的命令行编码助手，形态也高度趋同：REPL 对话 + 文件读写 + 命令执行。grok-build 是 xAI 的答案，但它的思路不太一样：不是另一个 REPL，而是一个**全屏 TUI 应用**，带鼠标交互、面板拖拽和实时渲染。

  grok-build 在 7 月 14 日开源，24 小时内冲到 GitHub 趋势榜第一，目前 22,351 stars。用 Rust 写成，编译快，启动更快。安装只有一行 `curl`，首次启动弹浏览器完成 xAI 账号认证——不需要本地 GPU，不需要下载模型，但**必须付费订阅 SuperGrok（$30/月）或 SuperGrok Heavy（$300/月）才能使用**。开源的是客户端，不是大脑。

  从架构看，grok-build 的分层相当清晰：`xai-grok-pager` 管 TUI（滚动、提示框、弹窗、渲染），`xai-grok-shell` 管 Agent 运行时和 headless 模式，`xai-grok-tools` 管工具实现（终端、文件编辑、搜索），`xai-grok-workspace` 管文件系统、版本控制、checkpoint。这意味着它既能以交互式 TUI 运行，也能以 `grok exec` 方式在 CI 里 headless 跑，还能通过 ACP（Agent Client Protocol）嵌入编辑器。

  TUI 体验是它最明显的差异化。传统 CLI Agent 的对话像一长串聊天记录——提示词、工具调用、输出、下一轮提示词，来回滚屏找上下文。grok-build 的全屏界面把对话、文件 diff、终端输出拆成独立的可视区域，鼠标可以点击文件、拖拽面板、切换标签。习惯 tmux 分屏工作流的开发者会觉得很自然。

  对比同类终端 Agent：

| 工具 | 模型绑定 | 界面 | 价格 | 开源 | MCP |
|------|---------|------|------|------|-----|
| **grok-build**（今日推荐）| 仅 Grok/xAI | 全屏 TUI + 鼠标 | $30-300/月 | 客户端 Apache 2.0 | ✅ |
| Claude Code | 仅 Claude | REPL | $20/月或 API | ❌ | ✅ |
| Codex CLI | 仅 OpenAI | REPL + TUI | $20-200/月 | CLI 开源 | ✅ |
| Gemini CLI | 仅 Gemini | REPL | 免费额度 + API | 客户端开源 | ✅ |
| Aider | 任意模型（BYOK）| REPL | 免费 + API | Apache 2.0 | ❌ |
| OpenCode | 75+ 厂商 | TUI + 桌面 + IDE | 免费 + API | 开源 | ✅ |

  grok-build 适合已经在用 xAI/Grok 生态的团队。如果你是 Grok 订阅用户，它是目前最自然的选择——不需要额外付费，不需要折腾 API key，开箱即用。但如果你需要模型自由度（今天用 Claude、明天切 GPT），Aider 或 OpenCode 更合适。如果你需要的是最成熟的终端 Agent 生态（插件、技能、社区），Claude Code 仍然是基准线。

  grok-build 的一个实际限制：外部贡献不被接受（CONTRIBUTING.md 明确写了），且代码是从 SpaceXAI 内部 monorepo 定期同步出来的单个 squash commit，没有完整的开发历史。这是「开放源代码」而不是「开放治理」。

## GitHub MCP Server v1.7.0 — 抢在 MCP 无状态协议生效前完成迁移，31.7K stars 的官方基础设施

  如果你在维护或使用任何 MCP Server，7 月 28 日这个日期你应该标记在日历上。这一天，MCP 协议的最大一次修订将正式发布——移除 `initialize`/`initialized` 握手、删除 `Mcp-Session-Id`、弃用 Roots/Sampling/Logging 三个原语、引入 Extensions 机制。一句话：**MCP 从有状态变成无状态**。

  GitHub MCP Server 是 MCP 生态里装机量最大的服务器之一（31,688 stars，周安装量超 200 万），它抢在 7 月 23 日发布了 v1.7.0，已经完整支持新协议。这意味着 Git 操作、Issue 管理、PR 审查、CI/CD 监控——所有这些通过 AI Agent 对 GitHub 的操作——在 7 月 28 日之后不会断。

  v1.7.0 做了三件事来适配新协议。第一，**去掉深度包检测**：以前 MCP 网关需要解析每个请求的 JSON-RPC body 才能做日志记录和密钥扫描，新协议把必要信息放进了 HTTP 头，网关不再需要「偷看」请求体。第二，**升级 elicitation 实现**：OAuth 登录流程在新协议中拆成了多个独立 HTTP 请求，Go SDK 提供了一个包装层让新旧客户端都能正常工作。第三，**移除 Redis 会话**：`initialize` 时的数据库写入和每次请求的数据库读取都消失了——请求更快，运维更简单。

  除此之外，v1.7.0 还带来了 Server-to-Server 认证（GitHub App 通过 stdio 直连，适合企业/云环境）、Projects 工具分页改进、以及 Lockdown 模式的更多安全加固。v1.6.0（7 月 15 日）引入的 `fields` 参数也在 Insiders 模式中启用了——模型可以指定只需要哪些字段，缩小工具响应体积，节省上下文窗口。

  这些变更的实际影响：以前部署一个远程 MCP Server 需要 sticky session、共享 session 存储和网关层的深度包检测。现在你可以把它放在一个普通的 AWS ALB 或 Cloudflare 负载均衡后面，不需要任何自定义路由逻辑。

  对普通开发者的影响更直接：如果你用 Claude Code 或 Cursor 连接 GitHub MCP Server，**什么都不需要做**——所有 Tier 1 SDK 保持了向后兼容，客户端升级后会自然适配。但如果你自己维护了一个 MCP Server，7 月 28 日之前需要审计一遍：有没有隐式依赖跨调用 session 状态的工具？有没有还在用 SSE 传输的老配置？

```bash
# 远程模式（推荐，无需本地部署）
# 在 VS Code / Claude Code 中添加：
claude mcp add --transport http github https://api.githubcopilot.com/mcp/

# 本地 Docker 模式（OAuth 登录，无需创建 token）
docker run -i --rm -p 127.0.0.1:8085:8085 \
  -e GITHUB_OAUTH_CALLBACK_PORT=8085 \
  ghcr.io/github/github-mcp-server

# 本地编译模式
git clone https://github.com/github/github-mcp-server.git
cd github-mcp-server
go build ./cmd/github-mcp-server
export GITHUB_PERSONAL_ACCESS_TOKEN=ghp_...
./github-mcp-server stdio
```

### 同类对比

| 工具 | 定位 | 核心差异 | 热度 |
|------|------|---------|------|
| **GitHub MCP Server**（今日推荐）| GitHub 官方 MCP | 最完整的 GitHub API 覆盖，首批适配新协议 | ⭐ 31.7K |
| GitLab MCP Server | GitLab 社区 MCP | GitLab 平台专用，覆盖 MR/Issue/CI | ⭐ 1.2K |
| GitMCP | 通用 Git 仓库文档 | 零配置，URL 替换即可给任意仓库加文档查询 | ⭐ 8.3K |
| Bitbucket MCP | Atlassian 生态 | Bitbucket Cloud/Server 的 MCP 接入 | ⭐ 0.5K |

  GitHub MCP Server 在这个品类里没有真正的竞品——它覆盖的 GitHub API 面是所有同类工具中最广的（20 个 toolset、100+ 工具），而且由 GitHub 官方维护。其他 Git 平台的 MCP Server 各有侧重，但功能深度和更新速度都差一个量级。
