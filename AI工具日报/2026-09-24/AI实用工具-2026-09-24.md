## agent-skills — 把高级工程师的流程拆成 25 个技能，让编码 Agent 照着走

![[agent-skills-demo.jpg]]

　　编码 Agent 最稳定的毛病是走捷径：需求还没说清楚就开始写，测试跳过，安全审查略过。这跟模型能力关系不大，缺的是一套「什么时候该停下来」的判据。Addy Osmani（Google Chrome 团队）把这套判据做成了 25 个技能，每个技能是一份带步骤、检查点、退出标准的 `SKILL.md`。

　　每个技能结构统一：Overview、When to Use、Process、Rationalizations、Red Flags。前三段算常规，真正起作用的是第四段——它把 Agent 常用的借口逐条列出来当场反驳，比如「这个改动太小，不用写测试」会被显式标成 red flag。技能按工作类型自动激活，也能用斜杠命令手动调。

　　九个命令对应完整生命周期：`/spec`、`/plan`、`/build`、`/test`、`/constraints`、`/review`、`/webperf`、`/code-simplify`、`/ship`。`/build auto` 批准一次后自主执行，但仍然逐任务跑测试驱动开发、逐个提交，碰到失败或高风险步骤会停下来等人。

　　附带 4 个评审人格（code-reviewer、test-engineer、security-auditor、web-performance-auditor）和 7 份参考清单（definition-of-done、security-checklist、observability-checklist 等）。内容吸收了不少 Google 工程实践，Hyrum 定律、Beyonce 规则、Chesterton's Fence 都在里面。仓库还自带三层 eval 框架（结构、路由、行为），部分跑在 CI 上——同类技能包里很少有人做自测，这一点比较少见。

```bash
# 通用：skills CLI，支持 70+ 种 Agent
npx skills add addyosmani/agent-skills              # 装全部 25 个技能
npx skills add addyosmani/agent-skills --list       # 先看清单
npx skills add addyosmani/agent-skills --skill test-driven-development

# Claude Code
/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills

# Codex CLI 0.122+
codex plugin marketplace add addyosmani/agent-skills
codex plugin add agent-skills@agent-skills
```

　　单技能安装只复制 `skills/<name>/`，不含仓库级 `references/`，共享清单的路径会失效（issue #361），要完整的就整包装。

### 同类工具对比

| 工具 | 安装方式 | 核心特点 | 价格 | 热度 |
|------|---------|---------|------|------|
| **agent-skills**（今日推荐）| `npx skills add addyosmani/agent-skills` | 覆盖 SDLC 六个阶段，每个技能带反理据表和 red flags，仓库内自带 eval | 开源免费 | ⭐ 98,724 |
| Superpowers | `/plugin marketplace add obra/superpowers` | 方法论最完整，TDD 执行最严，适合长时间自主任务 | 开源免费 | ⭐ 290,720 |
| mattpocock/skills | Claude Code 插件 | 需求追问（grill）最强，偏个人日常工作流 | 开源免费 | ⭐ 268,529 |
| OpenSpec | `npm i -g @fission-ai/openspec` | 规范驱动开发，每次变更独立成文件夹 | 开源免费 | ⭐ 70,061 |

　　三套技能包共用同一套 Markdown + YAML frontmatter 机制，差别在形状。Superpowers 的 stars 接近它的三倍，但覆盖面偏向构建内循环；agent-skills 是从 spec 一路管到 CI/CD、可观测性和发布，适合把一个完整功能推完。mattpocock 的重心在需求追问。三者共同的短板是跨会话的长期记忆，目前谁都没解决。

　　Om Mishra 在同一仓库、同一模型、同一 prompt 下做过对照：agent-skills 约 8 分钟出代码、跑了 7 轮验证，Superpowers 约 12 分钟、5 轮验证，前者顺带发现了一个不在本次改动范围内的兼容性问题。样本只有一个任务，不能当基准看，方向可以参考。选型上不建议两个包同时当活跃路由，命令名会撞车，TDD 理念也不一致。

## gcx — 让编码 Agent 去查生产数据，而不是猜

![[gcx-demo.png]]

　　Agent 写性能相关的代码时只能凭训练数据猜：超时设多少、mock 返回几条、这个接口正常该多快。这些数字在生产环境里全都查得到，只是要跳好几个页面。Grafana 把这件事收进了一条命令行。

　　gcx 是 Grafana 官方发布的 agentic CLI，覆盖 Cloud、Enterprise 和自建 OSS（自建要求 Grafana 12 以上，官方推荐 13+）。查询面包括 metrics、logs、traces、profiles，往外还有告警规则、SLO、Synthetic Monitoring、IRM OnCall、k6 压测、Frontend Observability 和 Agent Observability。输出是 JSON/YAML，配结构化错误和分级退出码。它能自动识别 Claude Code、GitHub Copilot、Cursor 这类环境，切到 agent 模式。

　　配套的 Agent Skills 随 CLI 一起装，覆盖告警排查、仪表盘创建与 GitOps、数据源探索、结构化调试、SLO 管理、可观测性落地。装完之后 Agent 遇到线上问题会先 `logs query` 再开口。

![[gcx-demo-2.png]]

　　典型用法是拿 RED 指标和 p95 延迟反推测试里的 mock 参数，或者把生产看板的查询拉到本地 `grafana/otel-lgtm` 栈上复现。官方给的定位是「不要猜，查真实生产数据」，落到 PR 上就是可以把看板链接直接贴进描述里，评审时看的东西从「Agent 有没有看懂需求」变成「跑起来的系统符不符合预期」。

```bash
# 安装（三选一）
brew install gcx
curl -fsSL https://raw.githubusercontent.com/grafana/gcx/main/scripts/install.sh | sh
go install github.com/grafana/gcx/cmd/gcx@latest

gcx login

# 给 Agent 装技能
/plugin marketplace add grafana/gcx                 # Claude Code
/plugin install gcx@gcx-marketplace

gcx agent skills list                               # Codex / OpenCode / Pi 等 .agents 兼容框架
gcx agent skills install --all

gcx metrics query --help                            # 查询入口
gcx --version                                       # 核对版本
```

## treg — Agent 工具的 OpenRouter，按次调用，不用给每个供应商开账号

![[treg-hero.png]]

　　Agent 要干活就得有工具，麻烦在于真实工作需要的工具大多在订阅墙后面：Semrush 一个月 139 美元、Moz 99、Crunchbase 99、Apollo 每个席位 59，有的干脆没有公开 API。给每个供应商注册账号、管密钥、盯配额，成本比用工具本身还高。

　　treg 把自己放在代理层：它持有这些账户，按调用次数计费，最低一分钱一次，调用方不碰密钥。目录里现在有 60 多个供应商、3,000 多个端点。有条硬规则是它只转发、不做模型（the proxy relays, never models the upstream），认证在服务端注入，上游 API 改了调用方也不受影响。

　　凭据解析有固定顺序：团队自注册的工具，再是团队为该供应商存的密钥，然后是已验证的公开路径（免费），最后才落到 treg 自己的密钥、计入团队预付余额。没有公开定价的端点会被直接拒绝，不会白送；余额不够返回 HTTP 402。鉴权头是 `X-Treg-Token`，代理入口在 `/call/{...}`。

　　入口有三个：CLI、Claude Code 插件、给其他 Agent 用的 skill。检索方式是按任务而不是按供应商，官方那句 Ask for the task, not the tool 说得挺准。

```bash
# CLI
curl -fsSL https://treg.to/install.sh | sh
treg login
treg catalog search "backlinks for a domain"
treg call tikhub.tiktok.user.profile --query uniqueId=tiktok
treg balance

# Claude Code 插件
/plugin marketplace add superdesigndev/treg
/plugin install treg@treg

# 其他 Agent
npx skills add superdesigndev/treg -s treg

# 自托管服务端
pip install "tools-registry[server]"
```

### 同类工具对比

| 工具 | 安装方式 | 核心特点 | 价格 | 热度 |
|------|---------|---------|------|------|
| **treg**（今日推荐）| `curl -fsSL https://treg.to/install.sh \| sh` | 代理层持有账号，按调用付费，调用方无密钥，可自托管 | 按调用计费，$0.01 起 | ⭐ 2,744 |
| Smithery | 托管注册中心 | MCP 服务器的发现与部署，已被 Arcade.dev 收购 | 免费 + 托管费 | — |
| Orthogonal | MCP 接入 | 30+ API 合作方，按调用付费，MCP 原生、无密钥管理 | 按调用计费 | — |
| ToolRouter | 托管网关 | 254 个工具 + 1,345 个技能，按成功调用计费，失败不收 | $0.005/次 + 工具价 | — |

　　这一类比的都是「Agent 怎么拿到外部工具」。Smithery 那条路解决的是 MCP 服务器的托管，质量与定价归发布者管；treg 自己承担账号和计费，换来调用方零配置，自托管也可以。它的目录偏外部数据类 API，工程向的工具反而不多，这是现阶段的短板。许可证要留意：Apache 2.0 加了附加条款，自由使用和自托管没问题，但未经书面许可不能把代码再分发成竞品的托管服务。
