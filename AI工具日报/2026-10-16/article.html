OpenUI 1.0 — 生成式 UI 的开放标准，比 JSON 省 67% token

![OpenUI 生成的 business health 仪表盘](./openui-demo.png)

Agent 的回复一直只有一种形态：文本。顶多富一点，是 Markdown。生成式 UI 想解决的就是这个断层：让模型直接生成界面。图表、表单、数据表、仪表盘，边生成边渲染。OpenUI 是这个方向里走得最"标准化"的一个，昨天（10 月 15 日）发布 1.0，仓库 11,061 星，MIT 协议。

它的核心是 OpenUI Lang，一门为模型输出设计的紧凑流式语言。整个链路很短：定义或复用一个组件库，从组件库自动生成 system prompt，发给任意模型，模型流式吐回 OpenUI Lang 文本，客户端渲染器边收边渲染。模型能画的界面被组件库锁死：allowlist 即安全边界，模型想画一个不存在的组件，渲染层直接忽略。上面那张图就是官方组件库渲染出的 business health 仪表盘，整块界面全部由声明式文本流拼成。官方给的 token 账：OpenUI Lang 比等价的 JSON 生成省至多 67% 的 token，在 60 tok/s 的模型上，一屏界面 4.9 秒拼完，用 JSON 输出的方案要 14.2 秒。

1.0 的更新集中在表达能力：defineFunction 注册自定义函数（参数按组件 prop 规则校验，调用失败返回 null 而不是炸掉整页）、library.extend 从既有组件库派生新库（增删改组件、加函数和 action）、buildMessage/parseMessage 给回复套一层 openui: 消息格式以便存储重放。注意 runtime 覆盖：只有 React 的包升到了 1.0，Vue、Svelte、Angular 还停在 0.4。生态接口是它的另一半卖点：Vercel AI SDK 有官方 adapter（兼容 v6/v7，处理文本、tool call、多步执行），LangChain/LangGraph 走 AG-UI 通道，LangChain 官方文档已经把 OpenUI 和 CopilotKit、assistant-ui 并列为推荐前端集成。对编码 agent 还提供了 skill：一句 npx skills add thesysdev/skills --skill openui，Claude Code、Codex、Cursor 就能直接照着 scaffold 生成式 UI 应用。

# 一条命令起一个带流式生成式 UI 的聊天应用（Next.js + React）
npx @openuidev/cli@latest create --name genui-chat-app

# 给编码 agent 装 OpenUI skill：组件库设计、Lang 语法、prompt 生成、调试坏输出
npx skills add thesysdev/skills --skill openui

Ghidra MCP Server — 209 个工具，把反编译器交给 AI 逆向

![装好 GhidraMCP 扩展后的 Tools 菜单](./ghidra-mcp-demo.png)

逆向工程的工作面是很枯燥的：在反编译器里一个函数一个函数读，认出来就改名、打注释、定结构体，重复几百遍。把这个过程交给 LLM 的前提是 AI 能用你的反编译器。Ghidra 的 MCP 实现已经有好几个，bethington 这个是目前工具面最全的：209 个 MCP 工具，README 里直言是竞品的 3 倍，而且读操作之外，命名、改类型、写注释、建结构体、执行脚本、P-code 模拟、实时调试这些写操作也一应俱全。

架构是两件套：一个跑在 Ghidra 里的 Java 扩展（GhidraMCPPlugin，监听 127.0.0.1:8089），加一个 Python 桥（bridge-mcp-ghidra），MCP 客户端拉起桥进程，桥把每次工具调用代理给扩展。除常规的反编译/导航/交叉引用之外，真正拉开差距的是三样。一是 P-code 模拟和 PCode-graph 数据流分析，能驱动 Ghidra 的仿真引擎跑指令流。二是批量操作：一次调用处理整批函数，官方口径减少 93% 的 API 调用。三是跨二进制文档转移，用 SHA-256 函数哈希匹配，把 v1 上人工整理的注释和命名自动迁移到打补丁后的 v2，同一个函数只需要标注一次。配套还有一批实战打磨的 AI 工作流 prompt：文档化流程 V5、匈牙利命名法参考、孤儿代码发现指南。

上面那张截图是装完扩展后的样子：Ghidra 的 Tools 菜单里多出一个 GhidraMCP 子菜单。版本耦合是硬约束：7.x 扩展只加载在编译时的 Ghidra 12.1.4 + Java 21 上；带 tag 的 release（7.0.0、7.1.0）是稳定版，main 和 rc 是 beta，dev 分支工具名随便改，别在其上搭自动化。所有通信走回环地址，扩展不访问外部服务，恶意样本分析场景没有额外外联风险。Windows 用户记一个坑：MCP 客户端要用桥的绝对路径配置 command，GUI 启动的客户端看不到 shell 的 PATH，写裸命令名会 spawn ENOENT。

MCP Server AI Companion — IntelliJ 的 102 项能力，全部交给 AI 助手

![MCP Companion 调用监控面板](./mcp-companion-demo.png)

编码 agent 跑在 IDE 外面，盲区一大片：编译错误在 Build 窗口里、测试结果在 Test 窗口里、断点暂停时变量在 Debugger 里，Git 状态要看 VCS 面板，SQL 结果在 Database 窗口。它要修编译错误，只能猜你改了哪行；要看测试挂了什么，只能自己重跑。这个 JetBrains 插件把 IDE 的这些状态和能力整理成 102 个 MCP 工具全部暴露出去，任何兼容 MCP 的助手（Claude、Claude Code、Copilot、Codex、Cursor、Windsurf）接上就能看到你 IDE 里正在发生什么。

102 个工具的分布：编辑器与导航（get_open_editors 返回打开的文件、光标位置、选中内容；highlight_text 用 IDE 的高亮色标出多处代码；show_diff 调起 IntelliJ 原生 diff 查看器对比提案）;构建与测试（get_build_output 返回结构化的错误树而不是纯文本；get_test_results 带通过/失败状态和堆栈；send_to_terminal 支持 waitForIdle=true，等输出稳定再返回）;调试（条件断点增删改、debug_run_configuration 启动调试、get_debug_variables 在断点处直接读局部变量）;代码分析（run_inspections 对整个项目跑检查、get_quick_fixes + apply_quick_fix 拿修复建议并应用）;数据库（execute_database_query 返回 JSON 结果，UPDATE/DELETE/DROP 前要确认）;Gradle（任务列表、依赖树、refresh）;以及最大的一块 VCS——30 多个 git 操作：blame、文件历史、跨分支 diff、stash、branch 管理、rebase、cherry-pick、merge 冲突列表、甚至 IntelliJ 的本地历史（get_local_history，Git 之外那层自动快照）。GitHub PR 和 GitLab MR 也有一整组工具，从列表、详情、评论、diff 到创建、合并、请求 review，不用装 gh / glab CLI。

上面那张图是它的监控面板（MCP Companion Monitoring），也是同类插件里少见的设计：AI 每次工具调用都会列出时间戳、耗时、完整 JSON 参数和响应内容，连其他 MCP 插件的调用也以灰色显示进来。出了"这个改动是谁动的"的疑问时，翻这个面板比翻日志直观。工具粒度可配置——Settings → Tools → MCP Server Companion 里每一项都能单独开关；带副作用的操作（终端执行、数据库写、commit/push、删分支）都有确认门。典型对话像这样："检查编译错误并修复"、"跑测试，告诉我哪个挂了、为什么"、"在 18 行加个断点，启动调试，跑到 i==3 时告诉我 jj 的值"、"把改过的文件 stage 起来，根据 diff 写 commit message 然后 push"。

# 安装后重启 IDE，Settings → Tools → MCP Server Companion 里逐项配置工具开关
# 再按插件说明把 MCP 端点接入你的 AI 客户端（Claude / Copilot / Codex / Cursor / Windsurf 任意）
