ARTEMIS — 一句话驱动 Android 真机跑完整个测试流程

![artemis-demo-1](./artemis-demo-1.png)

Android 端到端测试的维护成本大半压在定位器上。Appium 那套 XPath 和 ID 选择器只要 UI 改一次就得跟着改一批；Maestro 的 YAML 流程好写，碰到 Compose、Flutter、Canvas 自绘界面还是得重新找锚点。ARTEMIS 换了个思路：不写选择器，给一句自然语言，让模型看着屏幕操作。

它跑在 Python 3.12+ 上，通过 ADB 连真机或模拟器。第一次执行任务时会在设备上装一个 Accessibility Helper，用来读屏幕布局树，也可以用 UIAutomator2 作为替代后端。元素定位走「动态优先」：无障碍树里有元素索引就用索引，读不到再退回坐标和视觉识别。

执行侧分两档。Flash 是「看一眼、做一步」的反应式循环，官方给的数字是每步 3 到 5 秒。它的历史记录靠截图折叠成视觉摘要，旧步骤压缩成可检索的段落，所以循环本身不设轮数上限。Pro 是 Planner / Operator / Checker 的多 Agent 图。Planner 维护一份带里程碑的 Markdown 任务计划，每个动作执行前过一遍 Safety Net（先查 XML，再退回像素）。动作失败会开一条 incident，留在 Operator 上下文里直到后续某个动作成功才消除；最后 Checker 对着原始目标做一次终审。长流程能跑到 100 步以上。

典型用法是把它当 MCP 服务器接进 Claude Code、Codex、Antigravity，然后在对话里直接派活：「把最新改动打成 APK、装到连接的设备上、用测试账号打开登录页、检查登录后有没有意外弹窗、把最终页面截图给我。」跑完返回截图、Logcat 和结构化结果。也可以不进 IDE，命令行直接跑 uv run artemis run "Open Settings, find Battery and tell me current level" --profile flash，或者开 Web 控制台 uv run artemis ui 看实时投屏、推理轨迹和执行回放。它同时是个 Python 库，能塞进 pytest 和 CI。

AndroidWorld 基准（20 多个 App、100 多个多步任务）上官方给出 99%+ 的任务完成率。这个数字是项目自己跑的，AndroidWorld 排行榜不做独立复核，看的时候留个余地。仓库 5,433 stars、482 forks，Apache-2.0。

git clone https://github.com/google/artemis.git
cd artemis
./start.sh          # macOS / Linux
.\start.bat         # Windows PowerShell，前面的 .\ 不能省

启动脚本会检测并装好 ADB、scrcpy、FFmpeg 和 uv，然后问你要不要顺手把全局 MCP 配置和测试规则装进已识别的 IDE。已经装好了想补装，用 uv run artemis mcp --install all 一次装到所有支持的客户端；只装 Claude Code 就把 all 换成 claude。

ARTEMIS 首次公开提交是 8 月 13 日，其中 229 个文件里有 228 个与创业公司 Minitap 的 Apache-2.0 项目 mobile-use 高度一致，作者名单被替换掉了。Minitap 在 9 月 11 日公开证据，Google 当天在 README 和文件头补上署名，现在 README 末尾写着「本项目包含 Minitap, Inc. 开发的源代码」。功能本身不受影响，知道这段背景再决定用不用更踏实。

x64dbg-MCP Server — 把 Windows 上最常用的免费调试器交给 Agent

![x64dbg-mcp-demo](./x64dbg-mcp-demo.png)

给 AI 装逆向能力这件事，过去一年基本都发生在静态反汇编器上：IDA Pro 的 MCP、Ghidra 的 MCP，Agent 面对的是磁盘上那个不动了的二进制。可真正排查崩溃、跟壳、盯注册表调用的时候，你要的是动态调试——挂上运行中的进程、下硬件断点、改内存、单步走。x64dbg 是 Windows 上做这件事的免费标配，这个插件把它的全部能力开成了 HTTP 接口。

实现方式是原生插件。它用 Zig 写成，编译出单个 .dp64 / .dp32 文件丢进 x64dbg 的插件目录，启动时由 x64dbg 自己加载。加载时从 x64bridge.dll 和 x64dbg.dll 里解析出 SDK 符号，然后在后台线程起一个 HTTP 服务器，MCP 客户端用 JSON-RPC 调工具，每个工具直接映射到 x64dbg 的 SDK 调用。没有外部进程，没有轮询，插件就活在调试器自己的地址空间里。也因为没有 .NET、没有 Python 运行时，跨平台交叉编译出 x32 和 x64 两个版本只要一条命令。

README 的表里数下来 80 多个工具，从 LoadBinary、SetHardwareBreakpoint、StepOver、ReadMemory、GetAllRegisters 这类基础操作，到 FindPattern 通配符扫描、GetReferences 找 CALL/JMP 交叉引用、DetectOEP 检测壳的原始入口点、DumpModule 脱壳落盘、GetPEB 读进程环境块、FollowPointer 多级解引用、TraceInto 记录 N 条指令的地址和反汇编。另外还有 22 个调试事件回调，断点命中、异常、DLL 加载卸载、线程切换都能触发。

用起来是这样：把 dist/ 里的内容复制到 x64dbg 根目录，启动调试器，MCP 服务器自动起来，x64 默认听 0.0.0.0:9094，x32 听 9095。在 .mcp.json 里配上地址和一个 Bearer token 就能连。token 首次运行时自动生成，之后每个请求都要带，没带直接 401——这是个能读写进程内存的接口，跑在明文 HTTP 上，别往不可信网络里暴露。

{
  "mcpServers": {
    "x64dbg": {
      "type": "http",
      "url": "http://localhost:9094/",
      "headers": { "Authorization": "Bearer YOUR_TOKEN_HERE" }
    }
  }
}

实际的对话长这样：你说「加载 calc.exe 并在入口点断下」，Agent 依次调 LoadBinary、SetBreakpoint、run、WaitForPause，回你断在 0x7FF7A1234000；你问当前寄存器，它调 GetAllRegisters 把 RAX、RCX、RDX 全列出来；你说读当前指令指针处的 64 字节，它回一段十六进制；你说再单步三条并把栈给我，它 StepOver 三次再调 GetCallStack。整个过程你不需要在调试器界面上点任何东西。

仓库 1,964 stars、198 forks，MIT。最新 v1.3 发布于 9 月 2 日，三个版本的 Release 累计下载 2,454 次。

pgbot — 只读连上 Postgres，用 SQL 算出结论再让 Agent 解释

![pgbot-demo-1](./pgbot-demo-1.png)

让 AI 查数据库这件事有个隐藏矛盾：模型会编。它看到一张慢查询表，可能给你一个听起来很合理但完全错误的索引建议。pgbot 的处理方式是把结论和解释拆开：所有发现由 Go 代码从 PostgreSQL 自己的统计视图里算出来，模型只负责把算好的结论翻译成人话，不参与下结论。

实现上它是个单文件静态二进制，用 pg_monitor 角色只读连进去，读 pg_stat_statements、pg_stat_user_indexes 这些统计视图，然后打印一份「结论优先」的健康报告：顶部四条仪表（缓存命中率、锁等待和肇事查询、回滚率、空闲索引占用字节），中间一行列出这次检查通过了的子系统，然后是一个健康评分，最后按 CRITICAL / WARNING / NOTE 三档列发现。报告长这样：

connected · db.example.com · postgres 17.4 · read-only · 6h20m window

  cache hit  [████████████████████]  99.4%     ok
  lock wait  [████████████░░░░░░░░]  61.0%     query 4f2a
  rollbacks  [██░░░░░░░░░░░░░░░░░░]  12.0%     watch
  idle idx   [██████░░░░░░░░░░░░░░]  18.0 GiB  review

Database health: 82/100

CRITICAL
● transaction-id age 1.8B — 84% toward wraparound

WARNING
● orders queries 3.2× slower (8 → 26 ms mean)
● 3 unused indexes consume 18 GB

只读不是靠一个开关，是靠角色本身没有写权限。会话层还压了三层兜底：default_transaction_read_only、statement_timeout=15s、lock_timeout=2s，加上语句包在 BEGIN READ ONLY 里。pgbot init 会把建只读角色的 SQL 生成出来给你，不执行任何东西。

它还有一个我挺喜欢的特性：每次运行都在本地写一份基线。从第三次跑开始，它会告诉你「什么变了、为什么值得管」：哪条查询变慢了、哪张表开始走顺序扫描、哪个索引不再被使用。pgbot why 甚至能沿着基线历史给出一条因果链，症状、机理、前因，带数字和起始时间。

接 Agent 的方式是 pgbot mcp，走 stdio，只暴露确定性工具：inspect、unused_indexes、top_queries、vacuum_health、suggest_indexes（用 hypopg 让规划器验证，不是拍脑袋）、explain_plan、why、compare_to_baseline 等十来个。每个工具返回固定 JSON 结构并带 exactness 标签，永远不把原始连接串或查询字面量交给模型。
