## Security Audit Skill — 查漏洞的 agent，不能是发现漏洞的那个

![[security-audit-demo.png]]

　　让 coding agent 审代码找漏洞，最大的障碍不是它找不到，是它太爱报。同一个 agent 自己找、自己验，等于让一个人批改自己的卷子，它对自己写下的判断有天然的确认倾向，最后交上来一堆看着吓人、实际站不住的候选。Cloudflare 把这件事拆成六个阶段，核心设计只有一条，README 里的原话是：检查某个发现的 agent，永远不是发现它的那个 agent。

　　六个阶段是这样走的。先做侦察，把架构、信任边界、输入面和已有覆盖画成 `architecture.md` 加一份 `coverage-ledger.json`。然后按 ledger 里的单元分配隔离的 hunter 去查，查完由 coverage critic 找缺口，这一步保证的是「哪些地方还没被看过」是可数的，而不是凭感觉。第三阶段把每个候选丢给全新的 verifier，verifier 的任务是证伪它。第四阶段把结论按 confirmed / needs_validation / rejected 三档写进 `findings.json`，并对照 `report-schema.json` 校验。之后还有一轮独立记录验证，最后才生成 `REPORT.md`。父 agent 在指定节点要跑两个零依赖的 Node 校验器，`validate-coverage-ledger.cjs` 和 `validate-findings.cjs`，覆盖表不全或者 findings 不合 schema 就直接拦下来。

　　三种判定的含义分得很清。confirmed 要求完整的来源追溯和有界的观测结果；needs_validation 是确有未决事实、但不给严重级别；rejected 记录的是被证伪的候选，也保留下来。对同一个仓库多跑几次是累加的，会用上一次的 ledger 和 findings 找缺口、复验改动过的源码，不把过期或者悬而未决的东西算作已覆盖。

　　用法是在待审计的代码库里起一个 agent，说 "security audit this codebase" 或者 "do a security review, output to ~/audits/my-project"。默认输出到 `~/security-audit-skill/<repo-name>/run-<N>`，除非你显式指定仓库内被版本控制忽略的目录，否则不会往你仓库里写文件。它覆盖的攻击面写在十几个 Markdown 里：内存安全与二进制、LLM 提示注入与工具滥用、HTTP 请求分帧与认证、客户端 DOM 注入、供应链与发布、云与部署、RPC 与消息队列、资源耗尽、多租户数据隔离、桌面与移动端本地 IPC。

```bash
npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit
# 装到用户级而非当前项目
npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit --global
```

　　仓库 13.8K stars、740 forks、MIT 许可。README 里有一句很实在的观察：在他们自己的测试中，单次运行大约只能找到重复运行累计发现的一半漏洞。它的用法是反复跑，且每一轮的覆盖面都可审计。它对宿主有硬要求：agent 得支持工具调用和并行子代理，需要 Node.js 跑校验器，还需要 OS 级沙箱（禁外网、净化环境变量、限制资源、只允许写指定 scratch 路径），否则流程会把线索挂在 needs_validation，而不会去真的执行目标代码。

## BrowserSkill — 让 agent 用你已登录的浏览器，用完把标签页还回来

![[browserskill-demo.png]]

　　让 agent 操作浏览器这件事不缺方案。Playwright MCP、chrome-devtools-mcp 那一类都是开一个干净的无头实例，跑完关掉。麻烦出现在需要登录态的地方：你得把 cookie 喂进去，或者专门为它建一个测试账号，然后看着它抓到的页面和你自己看到的不是同一个。腾讯这个项目反过来做，直接用你本机那个已经登录好的 Chrome，同时让它别打断你。

　　架构值得说清楚，因为它是这个项目大部分设计取舍的来源。agent 侧通过 shell 调 `bsk` 命令，CLI 通过本地 IPC 找到 daemon，daemon 在 127.0.0.1 上开 WebSocket 连浏览器扩展，扩展再驱动一个独立的 Agent Window。agent 从不直接和浏览器通信，所有动作都过 daemon 这一层。好处是你用任何能调 shell 的 agent 都行，README 里列了 Cursor、Claude Code、Codex、OpenClaw、CodeBuddy、WorkBuddy、Pi、Hermes，不存在 harness 锁定。

　　标签页那部分是它最像「给真人用的工具」的地方。agent 需要碰你已经打开的页面时，必须显式执行 `tab borrow`，借的时候默认要你点确认，任务结束归还，你其余的浏览器不受影响。`tab borrow --timeout 60s` 控制的是等你确认的时长，不决定是否需要确认。遇到验证码、登录、弹窗确认，agent 可以发起 request-help 请你接管，你处理完它接着跑，这个 human-in-the-loop 是内建的，不靠 agent 自己发挥。

　　安装最省事的方式是让 agent 自己装，把这一行丢给它：

```bash
Set up browser-skill on this machine by following https://raw.githubusercontent.com/Tencent/BrowserSkill/main/AGENT_INSTALL.md
```

　　手动装 CLI，macOS/Linux 用 `curl -fsSL https://raw.githubusercontent.com/Tencent/BrowserSkill/main/install.sh | sh`，Windows 用 `irm https://raw.githubusercontent.com/Tencent/BrowserSkill/main/install.ps1 | iex`，装到 `~/.local/bin`。扩展从 Chrome Web Store 或 Edge Add-ons 装。然后 `bsk install-skill` 会列出支持的 harness 让你空格选中、回车安装，非交互场景用 `bsk install-skill --harness cursor --json`。装完跑 `bsk doctor` 看扩展连上没有，再新开一个 agent 会话让它打开 example.com 总结一下。

　　数据上，仓库 5.3K stars、370 forks、521 commits、MIT 许可。平台覆盖 macOS（Apple Silicon 和 Intel）、Linux（x64/ARM64）、Windows x64，浏览器支持 Chrome 和 Edge，Firefox 在计划里。0.3.0 起 `--unattended` 和 `BSK_REQUEST_HELP=off` 这类开关被废止，改用扩展弹窗里的两个选项（借用前是否确认、是否允许求助），把权限决定权从命令行挪到你能看见的地方。扩展会借用你的真实身份去操作网站，这点在装之前要想清楚。

## fx — 6.4 MB 的编码 agent，能编译成 WASM 跑在浏览器里

![[fx-demo.png]]

　　编码 agent 的 harness 这两年在比谁功能多，安装体积跟着涨到几百 MB。Vercel Labs 往反方向做了一次：用 Zig 写了个单文件原生二进制，v0.0.7 时是 6.19 MiB，到 8 月下旬长到 7.8 MiB，仓库的 CI 给六个 Linux CLI 命令路径卡了 2 毫秒的墙钟预算。官方宣称的冷启动是 10 微秒，这个数字没有第三方在同样条件下复现出来过，但「启动不做任何事、直接等输入」这个方向是真的。

　　「小」是靠砍系统提示词和工具集换来的，官方明说这么做的目的是少占模型的上下文窗口。功能面倒不窄：约 26 个内置工具（有一份 benchmark 数到 11 个），带 MCP、subagent（一次性子代理和持久子代理两种，ctrl+x 管理器，持久身份）、skills、后台命令、词法语义搜索、web search/fetch、vision，以及 ACP。模型侧默认走 Vercel AI Gateway，也支持 `fx login codex` 用 ChatGPT 订阅、`fx login grok` 用 Grok 订阅，或者填自定义的 OpenAI 兼容端点（Ollama、OpenRouter）。

　　它的接入面比一般 CLI 宽，这是真正的差异所在，四个面：

```bash
curl -fsSL https://fx.sh/setup.sh | bash   # 装到 ~/.local/bin
fx login                                    # 走 Vercel 授权流，会话存在本地
fx                                          # 在项目目录里起交互式 shell
fx ask "read src/ and tell me how requests are routed" --json   # 一次性调用，返回结构化输出
fx acp                                      # 走 stdio 接 ACP 客户端
```

　　第四个面是把 agent 嵌进 JS 宿主。SDK 以 libfx 发到 npm，`createFxAgent()` 加载 fx-core.wasm 拿到核心，`createFxTerminal()` 再加上交互终端 fx-term.wasm，仓库里带 Node.js、浏览器、Next.js、Nuxt 四个示例，浏览器上跑需要 Chrome/Edge 137+ 且开启 JSPI。想在 SaaS 里塞一个 agent、或者同时开几十个实例的场景，6 MB 和 250 MB 是「能做」和「做不了」的区别。

　　第三方 headless-harness-bench 对六个 headless harness 做静态源码审计，81 分制加权总分下 fx 排第五：omp 66.1 > dsh 65.6 > opencode 61.6 > Pi 60.9 > fx 58.1 > Crush 52.1。它成本与许可一项拿了最高的 3.0，取消与进程卫生 2.5，但隔离与密钥卫生只有 1.6，扩展性 1.6。更要紧的是 v0.0.5 起沙箱被拿掉了：被批准的命令现在作为普通宿主子进程运行，老的 sandbox 配置项已退役。官方文档的态度是「权限回调不是沙箱」，嵌入方需要自己提供隔离。项目本身标着 experimental，README 原话是 use at your own risk。仓库 3.1K stars、352 forks、Apache-2.0。
