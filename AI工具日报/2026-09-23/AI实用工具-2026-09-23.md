## colibri — 744B 模型从磁盘流式喂进 25GB 内存

![[colibri-demo-1.png]]

  MoE 模型的稀疏性一直被浪费。GLM-5.2 有 744B 参数，但每个 token 只激活约 40B，其中真正随 token 变化的只有路由专家那部分，约 11 GB。剩下的稠密权重（attention、shared experts、embeddings，约 17B）是每个 token 都要用的，这才该常驻内存。colibri 把这条线切清楚了：该留的留下，不该留的扔磁盘。

  引擎是纯 C 写的，零运行时依赖——不用 BLAS，不用 Python，不用 GPU。[README](https://github.com/JustVugg/colibri) 里的说法是"把 VRAM、RAM、NVMe 当成一个统一的放置层级"。稠密部分 int4 常驻约 9.9 GB；19,456 个路由专家（75 个 MoE 层 × 256 + MTP head，每个约 19 MB）躺在磁盘上约 370 GB，按 token 流式读。核心机制是一套权重级的 JIT：per-layer LRU 缓存、学习出来的 pinned 热存储、以及一层前瞻预取——路由器提前一层跑，用 71.6% 的实测可预测性把搬运延迟盖在计算下面。I/O 侧做了批量专家并集（一个 batch 里每个专家只读一次）、`O_DIRECT`、双 SSD 加权条带。

  ![[colibri-demo-2.png]]

  作者对性能的态度比多数项目诚实。同一引擎、同一个 int4 容器，只改放置方式：

  | 硬件 | 解码速度 |
  |------|---------|
  | 6× RTX 5090 全驻留 | 5.8–6.8 tok/s |
  | 128 GB CPU 台式机（热缓存） | ~1.8 tok/s |
  | 单张 RTX 5070 Ti 笔记本 | ~1.07 tok/s |
  | 25 GB 开发机（冷启动） | 0.05–0.1 tok/s |

  最后一行是正确性证明，不是能用来看聊天输出的配置——冷启动每 token 要读约 11 GB，磁盘速度基本决定 tok/s。想真用起来，需要一块快 NVMe 加足够的 RAM 把稠密权重和一份热专家缓存留在内存里。

  其他实测数字：MLA KV 每个 token 576 个浮点数，常规做法是 32,768，小了 57 倍。双 SSD 9 GB/s + 3 GB/s 组合让读取快约 33%。Qwen3.6 在两张 8 GB 卡上开 CUDA 分级，从 1.44 tok/s 提到 10.05 tok/s（7.0×）。MTP 投机解码在有收益时每 forward 出 2.2–2.8 个 token。项目给了一条硬保证：放置只决定速度，永不静默改变模型精度或路由语义。

  ![[colibri-demo-4.png]]

  Brain 页面值得单独看一眼。它把 GLM-5.2 实测出来的专家图谱画成一张皮层图，13,260 个被刻画的专家落在十个区域里（Python、SQL、数学、诗歌、法律、中文……），位置编码的是实测路由亲和度。点进 Python 区域能看到 1,142 个专家组成的星图，按层号和索引标注；随机挑一个（第 17 层第 178 号）是通用型，熵 3.13，亲和度分布为 20.2% Python、14.6% JSON、14.2% 对话、13.3% SQL。

```bash
# 预编译包（无需编译器）
mkdir colibri && tar xzf colibri-v1.8.0-linux-x86_64.tar.gz -C colibri && cd colibri
python3 coli info

# 或从源码构建（需 gcc/clang + OpenMP）
git clone https://github.com/JustVugg/colibri && cd colibri/c
./setup.sh

# 按模型族编译，CUDA=1 启用显存专家层
make -C c glm          # GLM-5.2 744B
make -C c qwen36 CUDA=1
make -C c olmoe        # 7B，最小，适合先跑通

# 运行
COLI_MODEL=/nvme/glm52_i4 ./coli chat     # 终端界面
COLI_MODEL=/nvme/glm52_i4 ./coli doctor   # 只读就绪检查
./coli web --model /nvme/glm52_i4         # API + 网页面板
```

## FastMCP 4 — MCP 协议换了，框架跟着重写

![[fastmcp-demo-1.png]]

  MCP 的 `2026-07-28` 协议修订版去掉了会话握手。请求变成彼此独立的，不再需要 `Mcp-Session-Id` 粘在同一个后端进程上。这对写服务器的人是个不小的改动，FastMCP 4 就是围着这个变化重写的。

  4.0.0 代号 "Four Real"，2026-08-31 GA，最新补丁 4.0.5（09-17）。引擎围绕新协议和重写后的 Python SDK v2 重建，但大部分复杂度被框架自己吸收了——官方说法是"多数 FastMCP 3 服务器不用改代码就能升级"。协议按连接逐个协商，所以老客户端连新服务器不会断，客户端也会先探新协议、失败再退回旧握手。

  4.0 加的东西：

  - **交互式工具**（SEP-2322）：工具可以反过来要输入或要审批，不直接给最终答案。这是多轮往返的工具支持，社区叫它 "guard mode"。
  - **无会话状态**：`UserSession` 和 `SessionId` 在无会话协议上提供显式的服务端状态，按认证用户划分，可以配持久化存储。共享的请求态键能在负载均衡和 worker 重启之间存活。
  - **后台任务**：`@mcp.tool(task=True)`，走 `io.modelcontextprotocol/tasks` 扩展（SEP-2663），放在可选的 `fastmcp-tasks` 包里，和 FastMCP 3 共用 Docket 引擎，客户端自动轮询，可选 Redis/Valkey 做持久化。
  - **扩展机制**：`add_extension()`（SEP-2133）把能力协商的协议特性变成受支持的插件面，自带 lifespan 管理。
  - **依赖注入**：`Depends` 配 `CallArgument`，把依赖绑到调用参数上，同时不污染工具 schema。这块由 Prefect 的 staff engineer Chris Guidry 贡献。
  - **ClientGroup**：每个服务器一个 client，统一工具目录，`{server}_{tool}` 命名空间带碰撞检查，支持调用路由和 per-tool 来源标注。
  - **企业认证**：服务端身份断言（SEP-990 ID-JAG，beta）、`require_roles`、scope step-up 挑战（SEP-2350）、DCR `application_type`（SEP-837）、机器对机器客户端认证。beta 3 还加了 Prefect Horizon 认证。
  - 参数补全、服务级缓存提示（SEP-2549）、可路由传输头（`Mcp-Method`/`Mcp-Name`，SEP-2243）。

  破坏性变更有两个：服务端发起的 sampling 和 roots 从服务端 API 里移除了；3.x 时代的兼容垫片也删了。升级指南在 `gofastmcp.com/getting-started/upgrading/from-fastmcp-3`。

  体量上，FastMCP 1.0 在 2024 年被合并进官方 MCP Python SDK，独立项目现在日均百万次下载，官方称驱动了 70% 的 MCP 服务器。TypeScript 侧有 `@prefecthq/fastmcp-ts`。

![[fastmcp-demo-2.png]]

```bash

# 或
```

## Jev — 不生成文本的判断模型，输出带概率的类型化答案

  用 LLM 做分类、路由、打标，本质上是在用生成模型干判别的活。等它把推理链写完，再从回复里把标签抠出来，token 花了、延迟扛了，最后要的只是一个类别和一个置信度。

  Jev 是 TypeSafe AI 的第一个 "System One" 模型，2026-09-15 发布，创始人 Diogo Almeida 是前 OpenAI 研究员，InstructGPT/RLHF 的早期作者之一。它不生成文本，也没有推理过程可以看。你发应用状态加一组类型化问题，拿回来的是带校准概率的类型化答案，同一个请求里的多个问题并行评估。

  三个原语，覆盖大部分判断场景：

  | 原语 | 问什么 | 返回什么 |
  |------|--------|---------|
  | **Choice** | 从给定选项里挑一个 | 选中项 + 每个选项的概率 + 置信度 |
  | **Score** | 在有序量表上打分 | 概率加权位置 + 每级概率 + 置信度 |
  | **Noul** | 某个陈述是否成立 | "是"的概率（0–1） |

  实现上用非自回归的并行采样，训练方法是 RLCD（Reinforcement Learning for Calibrated Decisions），奖励概率与准确度的对齐，而非人类认可度。实际效果是答案不会超出你定义的 schema——它没法在你给的选项之外编一个出来。TypeSafe 建议的用法是拆原子问题，因为同一次请求里的问题并行跑，多问几个几乎不增加耗时：官方给的一个例子是 13 个问题一次调用比 13 次单独调用便宜 11.5 倍、快 9.6 倍。

  数据上，第三方测出来的比官方自报的更有参考价值：

  - **liteLLM 基准**：中位延迟 126.81 ms，Haiku 是 688.40 ms，快 5.43 倍；p95 快 3.88 倍。期望层级匹配率 95.00% vs 73.75%。按注册价算，单次分类成本低 96.118%。
  - **OpenRouter Banking77 意图分类**（3,080 条）：1,000 次请求 $0.11，Claude Opus 5 是 $2.42，约 1/22。准确率 81.0% vs 84.4%，两者在 89.3% 的样本上判断一致，都没有输出格式错误。
  - **定价**：输入 $0.042 / 百万 token，输出 token 免费。每条响应带 `usage.cost` 字段显示本次花费。十条万条 1,000 token 的请求 = 1 亿 token = $4.20。
  - **延迟**：端到端 70–500 ms，对比前沿 LLM 的 3–329 秒。官方宣传口径是快 193.6 倍、便宜 444.6 倍，这是自设基准的上限值，独立验证有限。

  采用速度是它真正的信号。Vercel 的 AI Gateway 在发布 24 小时内，付费用户里有 13% 试用了 Jev，是此前任何模型发布的两倍；36 小时内 14 万开发者加入 beta。LangChain 在 09-20 放出了 "Jev-as-a-Judge" 实验。

  Jev 不能解释自己的判断。需要书面理由时，官方建议让聊天模型来解释结果，或者把低置信度的样本转人工。TypeSafe 自己文档里标了"锯齿"：多跳问题、额外间接层、日期解析、数值精度这几类任务会掉准确率。第三方 Explainx.ai 的测试给出 67.8% 对 74.1% 的聚合准确率，和官方基准差距明显。中文有覆盖但准确率偏低。还有一个绕不开的点：它只覆盖判断那一步，应用架构得把"决策"和"生成"拆开——推荐的做法是 Jev 做路由和分类、代码里做计算、LLM 负责写。

```bash
# 走 OpenRouter，用现成的 OpenRouter key，不需要单独注册 TypeSafe
curl https://openrouter.ai/api/alpha/decisions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "typesafe/jev-1.13",
    "state": {"ticket": "用户说续费按钮点了没反应，已经等了三天"},
    "questions": [
      {"id": "urgent", "type": "noul", "text": "这个问题需要立即人工介入"},
      {"id": "topic", "type": "choice", "text": "工单属于哪一类",
       "options": ["支付", "账号", "功能故障", "其他"]}
    ]
  }'

# TypeSafe 直连 SDK
npm install pi-typesafe      # JS/TS，一个 client + key store
pip install typesafe         # Python
```

  模型 ID `typesafe/jev-1.13`，别名 `~typesafe/jev-latest` 跟随最新版本。上下文 32,000 token，覆盖状态加所有问题。09-21 全面开放，注册用户送 $5 额度，约合 1.2 亿 token。
