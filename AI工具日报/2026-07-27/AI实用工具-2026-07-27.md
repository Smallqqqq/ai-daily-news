# AI 实用工具 · 2026-07-27

![[summary.png]]

  今天两个工具分别解决了 AI 开发中两个不对称问题：Agent 只能靠 grep 理解代码，但 IDE 里躺着完整的语义索引；手写一个生产级 MCP Server 要几百行胶水代码，但 OpenAPI spec 里已经写好了所有端点的签名。MCP Steroid 把前者打通了，mcpify 把后者自动化了。

---

## MCP Steroid + devrig CLI — 把整个 IntelliJ 变成 AI Agent 的工具箱

  AI 编码 Agent（Claude Code、Codex、Cursor）的能力边界受限于它们能「看到」什么。文件读写 + grep 搜索是通用方案，但在大型 Java/Kotlin 项目里，grep 找不到接口的间接实现、分不清同名方法的重载、看不懂依赖注入的装配链。IDE 里躺着 PSI 语法树、类型解析、调用图、数据流分析——但 Agent 访问不到。

  MCP Steroid 是一个运行在 JetBrains IDE 内部的 MCP Server，通过 8 个 MCP 工具把 IntelliJ 平台的完整能力暴露给外部 AI Agent。它不是「又一个文件读写 MCP」——它让 Agent 能执行 Kotlin 代码直接调用 IntelliJ API、截取 IDE 截图并 OCR 识别界面元素、发送键盘鼠标事件操控 IDE、甚至驱动调试器和测试运行器。2026 年 7 月新增的 devrig CLI 更进一步：一个 stdio 桥接进程，自动发现本机所有正在运行的 IntelliJ 实例（跨项目），或者在没有 IDE 运行时自动下载、安装、启动一个给 Agent 用。

  核心理念值得关注：工具数量刻意保持很少（8 个），真正的能力藏在 `mcp-steroid://` 的 prompt 资源里——这些资源教 Agent 如何在 `steroid_execute_code` 里直接写 Kotlin 调用 IntelliJ API。开发者社区贡献的「recipes」越多，Agent 能做的事情就越多，不需要等插件发版。

  实际场景：Agent 可以通过 `find_references` 精确定位一个接口方法的所有实现类（包括依赖注入间接装配的），通过 `get_type_hierarchy` 理解继承链，通过 `steroid_take_screenshot` 看到 IDE 的实时状态（包括编译错误、调试断点、测试结果），然后通过 `steroid_execute_code` 执行重构——所有操作都在 IDE 的 PSI 索引之上，精度远高于文本搜索。

```bash
# 1. 在 JetBrains IDE 中安装插件
# Settings → Plugins → Marketplace → 搜索 "MCP Steroid" → Install

# 2. 安装 devrig CLI（推荐方式，stdio 桥接）
# 下载地址：https://github.com/jonnyzzz/mcp-steroid/releases

# 3. 注册到 Claude Code（一次注册，所有项目生效）
claude mcp add --scope user steroid -- devrig
```

  前提要求：JetBrains IDE 2024.2+，需要安装 MCP Steroid 插件（plugin ID: 30019）。devrig CLI 自动处理 IDE 发现和连接。

| 工具 | 原理 | IDE 能力 | 可视化 | 语言 | 热度 |
|------|------|---------|--------|------|------|

## mcpify — 一行命令把 OpenAPI Spec 变成带语义搜索、熔断器、Dockerfile 的生产级 MCP Server

  企业内部的 API 通常都有现成的 OpenAPI 文档。但把这些 API 暴露给 AI Agent 使用时，现状很尴尬：要么写几百行胶水代码从头搭一个 MCP Server（认证、重试、限流、日志、测试、Docker 化全套），要么把整个 OpenAPI JSON 塞进上下文窗口让模型自己翻（消耗大量 token，还容易幻觉出 API 里根本不存在的端点）。

  mcpify 是一个 Rust CLI，把这个过程压缩成了一行命令。指向一个 OpenAPI 2.0、3.0 或 3.1 规范（本地文件或 URL），它在几秒内生成一个完整的、可直接部署的 MCP Server 项目。支持五种语言且功能完全对等：TypeScript、Rust、Python、C#、Go。

  架构上做对了三件事。第一，**每个生成的 Server 只暴露 3 个通用工具**——`search(query)` 用语义向量搜索找到最相关的 API 操作，`get(operationId)` 返回指定操作的完整 Schema，`call(operationId, arguments)` 校验参数、注入认证凭据、执行请求、校验响应。数百个端点缩成 3 个工具，Agent 的上下文窗口压力骤降。第二，**内嵌 SQLite + sqlite-vec 语义数据库**，在生成时解析 OpenAPI spec 并建立端点的向量索引，运行时不需要任何外部服务。第三，**企业级脚手架开箱即用**：结构化日志（含密钥脱敏）、OpenTelemetry 追踪和指标、熔断器/重试/限流、健康检查、OS 密钥链凭据存储、完整测试套件、多阶段 Docker 构建和 CI/CD 配置都在模板里。

  生成的项目有两种运行模式：Terminal Client 模式（开发者在终端里直接搜索和调用 API）和 Harness Server 模式（作为 MCP Server 被 Claude Desktop、Cursor 等 Agent 宿主调用）。认证方案从 OpenAPI spec 的 `components.securitySchemes` 自动发现——Basic、API Key、OAuth1、OAuth2——每种生成一个策略实现，运行时选一个激活。

  对于多版本 API（如 Jira 同时有 v2 和 v3），`mcpify add-version` 可以为已有项目追加新版本的 spec，只重新生成少数版本感知文件，不动认证、传输层和测试代码。`remove-version` 安全清理指定版本。这个设计让 mcpify 不仅是「一次性生成工具」，而是 API 生命周期内的长期伙伴。

```bash
# 安装（Rust 环境）
cargo install mcpify

# 从 URL 生成 TypeScript MCP Server
mcpify https://petstore3.swagger.io/api/v3/openapi.json -l typescript -o petstore-mcp

# 从本地文件生成 Python MCP Server
mcpify ./api-spec.yaml -l python -o my-api-mcp

# 给已有项目追加新版本
cd my-api-mcp
mcpify add-version https://api.example.com/v2/openapi.json --set-default
```

  前提要求：需要 Rust 工具链安装 mcpify 本身。生成的项目需要对应的语言运行时（Node.js、Cargo、uv/Python、.NET 或 Go）。目标 API 需要可网络访问。

### 同类工具对比

| 工具 | 输出 | 工具数量 | 语义搜索 | 企业特性 | 语言支持 | 热度 |
|------|------|---------|---------|---------|---------|------|
| **mcpify**（今日推荐）| 完整项目 + DB | 3 个通用工具 | ✅ sqlite-vec | ✅ 全套 | TS/Rust/Py/C#/Go | crates.io 新发布 |
| mcpgen | Python 源文件 | 每个端点一个 | ❌ | ❌ | Python | ⭐ 16 |
| MCP Gateway/Adapter | 运行时代理 | 按配置 | ❌ | 部分 | N/A | N/A |
| OpenAPI-to-MCP 系列 | 运行时桥接 | 每个端点一个 | ❌ | ❌ | 各不同 | 碎片化 |

  mcpify 在这个品类里做了两个差异化选择：用语义搜索把大量端点压缩成 3 个工具（其他工具都是每个端点一个工具，API 大了之后 Agent 的工具列表会爆炸），以及生成「完整项目」而不是「运行时代理」（生成物不依赖 mcpify，可以独立部署、修改、版本控制）。代价是需要 Rust 工具链安装，对不熟悉 Rust 生态的开发者有点门槛——但生成出来的项目不要求 Rust。
