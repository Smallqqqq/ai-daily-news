## chrome-devtools-mcp — 让编码 Agent 自己读浏览器的性能轨迹和网络请求

　　前端排障最难受的一段路是「我描述给你听」。你看到页面卡，Agent 只能读代码猜；你贴一张 DevTools 截图，它拿不到网络时序，也拿不到 trace 里的长任务。Chrome 团队把这个环节补上了：把 DevTools 协议封装成 MCP 服务器，Agent 自己开浏览器、自己点、自己读性能数据。

　　原理不复杂。它走 CDP（Chrome DevTools Protocol）连真实 Chrome，把 DevTools 的能力拆成 26 个工具暴露给 MCP 客户端——性能 trace、Lighthouse 审计、内存快照、带完整请求头和响应体的网络记录、Console 监听、扩展管理，以及基于 Puppeteer 的自动等待式操作。浏览器只在真正调用到需要它的工具时才启动，不是一连上就拉起进程。

　　它同时提供一个不依赖 MCP 的 CLI，所以也能塞进 CI 做性能回归。几个参数值得记：`--slim` 砍到只留基础浏览器任务，`--headless` 无头，`--isolated` 隔离 profile，`--no-performance-crux` 阻止 trace URL 上报给 Google CrUX API，`--no-usage-statistics` 关掉默认开启的使用统计。

　　典型用法两种。一种是「这个页面为什么慢」——Agent 录一条 trace，从长任务里定位到具体函数，再回去读对应源码改。另一种是排查线上问题——给它一个 URL，让它把失败的请求、报错、Console 异常拉回来，而不是你一条条复制粘贴。

　　数据上最有说服力的是成本。Trackingplan 的实测结论：一次 10–15 步的交互审计，跑在 Chrome DevTools MCP 上比跑在 Playwright MCP 上便宜一个数量级。原因是它监听 CDP 事件流、只取需要的那一段，而 Playwright MCP 每交互一次就重新生成整棵 accessibility tree。cdp-browser-mcp 用 tiktoken 做过一组 8 种页面的快照 token 对比，GitHub Issues 页是 9,616 对 17,597，BBC 新闻页 13,232 对 20,798，Shoelace 组件库页 12,120 对 17,739——内容密集页上优势最大。反过来 Wikipedia 那种超长文档它是 67,946，比 Playwright MCP 的 58,138 更贵，这是它的设计取向：给精准数据，不给全文。

```json
{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": ["-y", "chrome-devtools-mcp@latest"]
    }
  }
}
```

　　最简模式，只做基础浏览器任务、无头：

```bash
npx -y chrome-devtools-mcp@latest --slim --headless
```

　　要求 Node.js LTS 加当前稳定版 Chrome，只支持 Google Chrome 和 Chrome for Testing，不支持 Chromium 各分支。

## humanizer — 25 条 AI 写作特征，一条条从稿子里挑出来

　　英文稿件这一侧的「去 AI 味」，blader/humanizer 是目前最公认的一个。它是个纯 Markdown 的 agent skill，任何支持 skill 的 agent 都能装：Claude Code、Codex、Cursor 都行。

　　它解决的问题很具体：AI 腔的文字读起来不像人写的。它给的前提假设挺准——模型会挑一个能覆盖最广读者的写法，而人只写给一个读者、一个主题。

　　25 条特征分五类：用铺垫代替直接陈述、按规则造节奏、虚张声势和借用权威、按规则排版、聊天记录和草稿残留。清单来源是维基百科的《Signs of AI writing》词条，由 WikiProject AI Cleanup 维护，不是自己拍脑袋编的。工作流程：先按严重程度从高到低列出命中的特征，再在「不假设原结构必须保留」的前提下重写，然后把重写稿对着特征清单和原文事实核一遍，出终稿。缺事实的地方它会问你，不编。

　　3.0 版把原来的 35 条合并成了 25 条。用法上有个细节实用：直接粘文本，它给你「首版重写 + 简短点评 + 终稿」三段；指向一个文件，它只动散文部分，代码、数据、frontmatter 和链接目标都保留。还可以先喂它两三段你自己写的东西，让它按你的语感和标点习惯来。

　　四种安装方式，选一种：

```bash
# 方式一：skills CLI，默认装当前项目，加 --global 装全局
npx skills add blader/humanizer --global
```

```
# 方式二：Claude Code 插件，需 2.1.142 或更新
/plugin marketplace add blader/humanizer
/plugin install humanizer@humanizer
```

　　方式三是 Claude Desktop 下 ZIP 当 skill 上传，方式四是手动把 `SKILL.md` 拷进 agent 的 skill 目录。

　　规则覆盖度上，Slopbeth 2026 年 6 月做过一份公开英文反 slop 写作工具的矩阵：Slopbeth 自己 99 分，blader/humanizer 84 分排第二，后面是 great-writer 78、human-copy 74、skill-deslop 72、humanink 70、stop-slop 68、anti-ai-slop-writing 65。注意这是规则覆盖度，不是「骗过检测器」的排名。

　　检测器那边有个反向数据值得看。HumanizerAI 拿这类 skill 去打 GPTZero：基线本来就有 66.7% 的绕过率、平均分 35.1；加上「禁词表」之后绕过率掉到 30.0%、分数涨到 62.3；两条激进指令都加更是掉到 23.3%、73.8。禁词和堆细节会反噬，因为 GPTZero 主要量的是句长变化和困惑度，句子节奏比词汇更能说明问题。所以把它当改文风的工具用，别当过检测的工具用。

## TeamAI CLI — 团队的 Skill、规则、MCP 放进一个 Git 仓，评审合并后自动同步到每个人的每款 Agent

　　团队用编码 Agent 到一定规模会撞上同一个问题：有人用 Claude Code，有人用 Codex，有人用 Cursor。谁写了一条好用的 skill、谁总结了一条该遵守的规则、谁踩到了一个 MCP 配置的坑——这些经验都在个人机器上，散在各自的 `~/.claude/`、`~/.codex/`、`~/.cursor/` 里，没法共享，也没法评审。

　　腾讯开源的 TeamAI CLI 把这件事做成 Git 原生的分发流程：团队建一个共享仓放 Skills、Rules、Docs、Hooks、MCP 配置、环境变量和 Agent 定义，`teamai push` 开分支发 MR，人工评审合并，成员这边由 SessionStart hook 在会话启动时自动 `teamai pull` 同步。一份配置，多端生效。

　　覆盖面是 9 款编码 Agent、13 项能力，分三组：Harness 7 项（skills / rules / docs / env / agents / hooks / mcp）、知识库 3 项（learnings / codebase / teamwiki）、分析 3 项（usage / sessions / dashboard）。支持的 Agent 有 Claude Code、Codex、Cursor、CodeBuddy、WorkBuddy、OpenCode、OpenClaw、Hermes、DeepSeek Harness，skills 分别写进 `~/.claude/skills/`、`~/.codex/skills/`、`~/.cursor/skills/`、`~/.codebuddy/skills/` 这些原生目录。

　　治理这块是它和普通同步工具拉开距离的地方。`teamai roles` 做岗位到命名空间的映射，按角色决定谁拿到哪些资源；`teamai tags` 按主题订阅；`teamai source add/list/browse/remove` 订阅其他团队的公开 skill 仓。MCP 只在 `mcp/mcp.yaml` 里声明一次（支持 stdio / http / sse，密钥用 `${VAR}` 占位），pull 时由它写入各工具的原生配置格式。

　　经验回流是它最有野心的部分。Stop hook 检测「摩擦信号」——你打断了 AI、拒绝了某次工具调用、让它在同一处反复重试——然后提示你把这次经验总结成 Learning 提交入库。召回走 `teamai recall <query>`，检索是 BM25 加依赖图谱重排，还带一层相关性预检。代码库知识图谱用 WASM 编译的 tree-sitter 做 AST 解析；作者的说法是原生 tree-sitter 构建在国内部分企业网络下至少 30% 的安装会失败，WASM 是绕开这个的妥协。另有 `teamai digest` 出周报、`teamai session save` 做脱敏会话存档、`teamai dashboard` 看面板，指标含 token 用量、会话量和人工介入率。

```bash
npm install -g teamai-cli
```

```bash
# 项目级，默认，资源落在项目目录
cd /path/to/my-project
teamai init https://github.com/yourorg/yourrepo

# 用户级
teamai init https://github.com/yourorg/yourrepo --scope user
```

　　需要 Node.js ≥ 18，MIT 协议，TypeScript 写的。没有现成团队仓可以从 teamai-hub 组织的 template 仓库用「Use this template」生成。常用命令二十来个：`init`、`status`、`pull`、`push`、`contribute`、`recall`、`import`、`mcp list|inject|remove`、`roles`、`tags`、`source`、`members`、`skill exclude`、`codebase --extract|--deep-enrich|--reconcile|--lint`、`ci extract-mr`、`digest`、`session save`、`dashboard`、`doctor`、`uninstall`。

　　两个边界必须知道。`env/` 目录明确写了不要放 secrets，它只分发非敏感环境变量和开关，不是密钥方案。`teamai init` 会往配置里注入 hooks，卸载要走 `teamai uninstall`，手动删目录会留残留。另外它还不支持按 provider 配 Models，`teamai packages` 也只认 npm package 和 Claude Code plugin 两种。

### 同类工具对比

| 工具 | 安装方式 | 核心特点 | 价格 | 热度 |
|------|---------|---------|------|------|

　　为什么选它而不是 rulesync：rulesync 解决的是「规则定了，但每个项目手里版本不一致」，同步方向是中央源到多个项目目录，管的是文件；TeamAI CLI 管的是团队——谁该拿到什么、改动必须过评审、经验怎么回流成公共资产。前者零学习成本，后者要求团队有 Git 写权限并接受 push → review → merge → pull 的流程。十人以下、只用一款 Agent 的团队，rulesync 就够了。
