# AI 实用工具 · 2026-08-19

![[summary.png]]

  今天三条线都指向同一件事：让 Agent 干活之前，先把它的手脚和护栏装好。GitHub 把 Agent 塞进了自家 CI 平台，add-mcp 管的是 MCP 服务器装进 16 个客户端的重复劳动，aurl 让 Agent 调任意 REST API 不用再配一个 MCP 服务器。

## GitHub Agentic Workflows — GitHub 官方把编码 Agent 请进 Actions，Markdown 即工作流

![[gh-aw-demo.png]]

  传统 GitHub Actions 的问题是它只会执行，不会判断。写一个 "分析 CI 失败日志并回复 issue" 的自动化，靠 shell 脚本和 grep 撑不起来，得人盯着。GitHub Agentic Workflows（gh-aw）从 6 月 11 日起进入公开预览，做法是把编码 Agent 放进 Actions 的执行环境里跑：工作流用 Markdown 加 YAML frontmatter 描述——目标是什么、允许做什么、输出什么——gh CLI 扩展把它编译成 `.lock.yml`，由 GitHub Actions 调度执行。底层引擎可选 Copilot CLI、Claude Code 或 OpenAI Codex，GitHub Next 的 Don Syme 和 Peli de Halleux 在 2 月的技术预览介绍里把它定位成"带护栏的仓库自动化"。

  安全模型是这套东西和"在 CI 里跑一个 agent 脚本"的本质区别。Agent 步骤默认只读；写操作必须声明为 safe outputs——评论、建 issue、开 PR 各自跑在独立 job 里，拿的是受限写 token，Agent 本身从头到尾不持有写权限。外面再套三层：Agent Workflow Firewall 做域名白名单，只有显式允许的外部地址能访问；threat detection job 在写操作落地前用 AI 扫一遍提议内容，拦 prompt 注入和凭据泄露；staged mode 可以先跑一遍只出预览不动真格。输出有上限约束（比如评论最多 3 条、PR 最多 1 个），跑飞了也跑不远。

  官方文档给的典型场景：issue 自动分类、CI 失败原因分析、依赖更新、过期文档修正、死代码清理，以及每日仓库报告——截图里就是一条由工作流生成的 "Daily Repo Report" issue，把发布数、提交数、PR 总量汇总成一条。更狠的用法在官方周更里能看到：gh-aw 自己的仓库用 PureLock 每周自动给核心编译函数补纯函数测试，三周跑三次、每次 15 到 22 分钟、约 6 万 token，全程只读直到最后开一个 PR。Carvana 和 Marks & Spencer 已经在用：后者把 issue 分诊、依赖维护、漏洞修复做成跨仓库复用的工作流目录，官方 changelog 里 CTO 的原话是"过去要几小时的工程工作现在几分钟自动完成"。

  公开预览 6 月至今保持每周 1-2 个版本（8 月 10 日周更时是 v0.86.1），社区讨论区活跃。它不免费给承诺，KDnuggets 的入门实测提醒了几点：预览期 API 会变、token 消耗要自己盯、复杂工作流的 prompt 调试成本不低。但对已经在 GitHub 上的团队，这是目前把 Agent 自动化接进既有 CI 治理体系最短的一条路。

```bash
# 安装 gh CLI 扩展（需要已安装 gh 并登录）
gh extension install github/gh-aw

# 之后按官方 quickstart 建第一个工作流：写 Markdown + YAML frontmatter，
# 扩展编译成 .lock.yml 交给 GitHub Actions 执行；现成模板在 githubnext/agentics
```

## add-mcp — 一条命令给 16 个编码客户端装上同一个 MCP 服务器

  MCP 服务器的安装是纯手工活：找到包名、确定启动参数、再往每个客户端各自的配置文件里塞 JSON。Claude Code 写在 `~/.claude.json`，Cursor 写在 `.cursor/mcp.json`，Codex 写在 `.codex/config.toml`，格式还不一样。装三个服务器、用两个客户端，就是六份手抄配置。add-mcp 把这个过程压成一条命令：传 URL 或包名，它自动检测你机器上装过哪些编码客户端，把配置写进各自正确的位置。

  支持面是目前同类里最宽的：16 个客户端，包括 Claude Code、Codex、Cursor、VS Code、Gemini CLI、GitHub Copilot CLI、Cline、Zed、Windsurf、Grok Build 等，每个都有项目级（提交进仓库给团队共享）和全局两种安装范围。传输层三种都吃：streamable HTTP 远程服务器、SSE、本地 stdio。远程服务器还能带 OAuth scopes 和自定义 header，token 走交互授权不落配置文件。除了装，还有配套命令：`find` 搜注册表、`list` 看现状、`remove` 卸载、`sync` 把服务器名跨客户端对齐——你给同一个服务器在 Cursor 里叫 `github`、在 Claude Code 里叫 `gh`，sync 能统一。

  对多客户端混用的人（Claude Code 写代码、Cursor 看 diff、Codex 跑批量任务），这东西省的是每周都会发生的 15 分钟。团队场景更值：`npx add-mcp <server> -y` 写进项目的 `.mcp.json`，新同事 clone 下来就是全套工具。

```bash
# 远程 HTTP 服务器，URL 直接装
npx add-mcp https://mcp.example.com/mcp

# 按包名装 stdio 服务器，同时写给 Claude Code 和 Cursor
npx add-mcp "npx -y @modelcontextprotocol/server-github" -a claude-code -a cursor

# 搜注册表、交互式挑选
npx add-mcp find vercel

# 全局安装、跳过确认、连同 auto-approve（支持的客户端）
npx add-mcp "executor mcp" --name executor -g -a codex -a claude-code -y --auto-approve
```

## aurl — 把任意 OpenAPI 变成 Agent 随手可调的 CLI，不装 MCP 服务器

  MCP 是让 Agent 调 API 的主流解法，但它有两个代价：写服务器或找现成的，以及把整个工具目录塞进每轮对话的上下文。aurl 走另一条路——Agent 本来就会用 CLI，给它一个能按需发现端点的 CLI 就够了。注册 API 时 aurl 解析 OpenAPI 3.0/3.1、Swagger 2.0 或 GraphQL 的 spec，自动识别认证方式，之后 Agent 用 `--help` 看端点清单、用 `describe` 查参数类型、直接发经过校验的请求，全程不读原始 API 文档。

  关键是按需拉取：spec 存在本地（`~/.config/aurl/`），解析是懒加载的，只在执行对应命令时才读。一个 1080 个端点的 GitHub spec，Agent 也只看到它问的那几条，而不是把整个工具目录灌进上下文。认证处理也省心：spec 里的 `securitySchemes` 在注册时自动识别——apiKey 探测 header 名、bearer 提示输 token、basic 提示用户名密码——凭据存在 `~/.config/aurl/auth/` 且权限 0600。作者还做了配套技能，`npx skills add ShawnPana/aurl` 一条命令教会 Claude Code、Cursor、Codex、Copilot 等 40+ 客户端怎么用它。

  一个具体的对照：接 GitHub API，MCP 方案是配 github-mcp-server、管 token、每轮背着几十个工具 schema；aurl 方案是 `aurl add github <spec-url>` 一条命令，之后 Agent 自己 `aurl github --help` 找端点、`aurl github GET /repos/org/repo` 发请求。对偶尔要调外部 API 的场景，后者轻一个数量级。

```bash
# 安装（Go 或 Homebrew 二选一）
go install github.com/shawnpana/aurl@latest
# brew install shawnpana/tap/aurl

# 注册一个 REST API
aurl add petstore https://petstore3.swagger.io/api/v3/openapi.json

# 注册 GraphQL API
aurl add --graphql linear https://api.linear.app/graphql

# 看可用端点
aurl petstore --help

# 发请求
aurl petstore GET /pet/1

# 给 Claude Code / Cursor 等 40+ 客户端装配套技能
npx skills add ShawnPana/aurl
```

### 同类工具对比

| 工具 | 形态 | 核心特点 | 热度 |
|------|------|---------|------|
| **aurl**（今日推荐）| Go CLI + 技能 | OpenAPI/GraphQL → 按需发现式 CLI，自动鉴权 | ⭐ 159 |
| openapi-cli4ai | Python CLI（uvx）| 同思路的 pull-based 发现 | ⭐ 13 |
| apifable | MCP server | OpenAPI 浏览 + TypeScript 类型生成 | ⭐ 9 |
| mcpify | CLI | OpenAPI → 生产级 MCP server（7 月 27 日已推荐）| 已推荐 |

  aurl 和 mcpify 正好相反：mcpify 把 spec 变成 MCP 服务器，aurl 把 spec 变成 CLI。选哪个看客户端——如果你的 Agent 环境已经深度绑定 MCP（Claude Desktop 这类只能吃 MCP 的宿主），走 mcpify；如果 Agent 有 shell 执行权（Claude Code、Cursor、Codex CLI），aurl 少一层协议转换，出问题直接 `curl` 对照排查。openapi-cli4ai 思路相同但热度差一个数量级，apifable 面向 TypeScript 前端项目的类型生成，定位更窄。
