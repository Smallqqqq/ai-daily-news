# AI 实用工具 · 2026-08-12

![[summary.png]]

  今天这个工具踩在了一个被大多数人忽略的缝隙上：MCP 协议让 AI 能调用任意工具，但谁来保证这些工具不会把代码库搞坏？Coding Tools MCP 给出的答案是——把文件读写、命令执行、Git 操作全部塞进一个带三道安全闸门的 MCP 服务器，任何 MCP 客户端接上就能安全编码。

---

## Coding Tools MCP — 给任意 MCP 客户端装上 20 个安全编码工具，模型无关、客户端无关

  AI 编码工具的现状是割裂的。Claude Code 有自己的文件操作工具，Cursor 有自己的，Codex 有自己的——每一套都是私有的，行为不一致，安全策略各自为战。如果你想在自己的 agent 里用 Anthropic SDK 从头搭一个编码循环，你得手写文件读写、命令执行、diff 应用这些基础能力，而且安全边界要从零设计。

  Coding Tools MCP 把这一层抽了出来。它不绑定任何模型或客户端，只是一个 MCP 服务器，暴露 20 个经过实战检验的编码工具。Claude Desktop、Claude Code、Cursor、Cline，或者你自己用 SDK 写的 agent——接上同一个服务器，拿到的是同一套工具、同一个安全模型。

  核心设计只有一条：**工作区根目录是绝对的边界**。服务器启动时指定 `--workspace /path/to/repo`，之后所有文件操作都被锁在这个目录内。绝对路径、`..` 穿越、符号链接逃逸全部拒绝。Linux 上还叠加了 Landlock 内核级文件系统隔离，就算工具本身有漏洞也出不了工作区。

  命令执行被拆成了三道安全模式，而不是简单的"允许/禁止"开关：

  | 模式 | 适用场景 | 实际限制 |
  |------|---------|---------|
  | `safe`（默认）| 日常 agent 工作 | 禁止网络特征命令、shell 展开、内联脚本、危险命令（`rm -rf /` 等）|
  | `trusted` | 本地开发 | 放开网络和 shell 展开，保留密钥过滤和危险命令检查 |
  | `dangerous` | 隔离容器/VM | 关闭命令权限门控，但工作区路径限制依然生效 |

  这个设计比大多数内置方案更精细。Claude Code 的命令审批是二元的——要么全拦要么全放。Coding Tools MCP 的中间档 `trusted` 允许 `curl` 和 `npm install`，但依然拦截 `rm -rf /` 和密钥泄露——这正是本地开发最需要的平衡点。

  工具的搜索结果和命令输出都经过裁剪和分页，官方数据是：在 dogfood 基准测试中，序列化后的工具结果字节数逐版本下降了 37%，而任务完成率不变。对于上下文窗口寸土寸金的编码 agent 来说，输出越紧凑，能记住的历史步骤就越多。

  除了基础的读写执行，这套工具还带了完整的 Git 检查套件——`git_status`、`git_diff`、`git_log`、`git_show`、`git_blame`——以及交互式会话管理。`exec_command` 可以启动一个 REPL 或调试器（真正的 PTY），然后跨对话轮次用 `write_stdin` 喂输入、`read_output` 翻页读取、`kill_session` 清理。长时运行进程是一等公民，带截止时间看门狗和有界缓冲区。

  远程访问场景也考虑到了。配好 Bearer token 或 OAuth 2.1 + PKCE 认证，通过 `cloudflared` 或 `ngrok` 打一条 HTTPS 隧道，就能从手机上的 claude.ai 遥控家里的工作站。容器化部署同样简单——一行 `docker run` 启动预配置好工具链和缓存的沙箱，指向可疑 PR 跑完就销毁。

  如果你更喜欢图形界面而非命令行配置，`pip install "coding-tools-mcp[desktop]"` 然后运行 `coding-tools-mcp-desktop` 会弹出一个桌面 GUI，管理工作区配置、隧道启停、凭证设置，支持中英文。

```bash
# Python 用户
uvx coding-tools-mcp --stdio --workspace /path/to/repo

# Node 用户
npx coding-tools-mcp --stdio --workspace /path/to/repo

# HTTP 模式（去掉 --stdio 即可，监听 127.0.0.1:8765/mcp）
uvx coding-tools-mcp --workspace /path/to/repo

# 容器化沙箱
docker build -t coding-tools-mcp-sandbox:local .
docker run --rm --init -it -p 8765:8765 -v "$PWD:/workspace" coding-tools-mcp-sandbox:local
```

### 同类工具对比

| 工具 | 安装方式 | 核心特点 | 安全模型 | 热度 |
|------|---------|---------|---------|------|
| **Coding Tools MCP**（今日推荐）| `uvx coding-tools-mcp` | 20 个工具、模型无关、三道安全闸门、Git 集成、交互式会话 | 工作区隔离 + Landlock + 三级权限 | ⭐ 706 |
| Anthropic 官方 Filesystem MCP | `npx @anthropic/mcp-server-filesystem` | 仅文件读写，无命令执行、无 Git、无安全分层 | 路径白名单 | ⭐ 官方 |
| Claude Code 内置工具 | 随 Claude Code 安装 | 深度集成 Claude Code，不适用于其他客户端 | 二元审批 | 随 Claude Code |
| pyddock | `pip install pyddock` | Python 执行 + shell 沙箱，声明式策略 | 策略驱动 | ⭐ 新项目 |

  Coding Tools MCP 跟官方 Filesystem MCP 的区别在于：后者只是一个文件读写 MCP 服务器，没有命令执行、没有 Git、没有安全分层——它解决的是"让 AI 读到文件"这一件事。Coding Tools MCP 解决的是"让 AI 安全地在一个代码库里工作"这件事。两者不是替代关系，Coding Tools MCP 覆盖了 Filesystem MCP 的全部功能，然后加上执行、Git、安全、会话管理四层。

  跟 Claude Code 内置工具的区别在于：Coding Tools MCP 是模型和客户端无关的。你今天用 Claude Code，明天换 Cursor 或自己写的 agent，工具层不需要改动。而且 Claude Code 的命令审批是二元的——要么信任要么不信任——Coding Tools MCP 的 `trusted` 模式给了开发场景真正需要的中间地带。
