# AI 实用工具 · 2026-07-30

![[summary.png]]

  今天两个工具瞄向了 AI 编码工作流里两个被忽视的浪费：Agent 每次调用 MCP 工具都把几百行的 JSON Schema 塞进上下文窗口（99% 是噪音），以及 Agent 默认的"过度工程本能"——用 400 行代码和 3 个依赖解决一个原生 `<input type="date">` 就能搞定的事。两个工具合在一起，一个砍 token，一个砍代码。

---

## mcp2cli — 把任何 MCP 服务器、OpenAPI 规范或 GraphQL 端点一键变成 CLI，每次调用省 96-99% token

  给 AI Agent 接 MCP 服务器的开发者迟早会撞上一个问题：Agent 不是直接调工具——它每次对话都要把整个工具列表（JSON Schema）塞进上下文窗口。一个 50 工具的 MCP Server，光是工具描述就能吃掉几千 token。更糟的是，这些 schema 在每一轮对话里都被重复发送，Agent 真正用于理解你的需求的 token 预算反而被挤占了。

  mcp2cli 的解法直接：把 MCP 服务器、OpenAPI 规范和 GraphQL 端点全部转换成命令行工具。Agent 不再需要把工具 schema 加载到上下文中——它只需要知道一个命令 `mcp2cli @myapi list-pets --status available`，跟你在终端里敲的完全一样。这就是 mcp2cli 能省 96-99% token 的核心原因：CLI 的接口描述是一个命令名加几个参数，MCP 的工具描述是完整的 JSON Schema。前者在上下文里占 20 token，后者可能要占 2000。

  实际使用体验被压缩到一行命令。`uvx mcp2cli --spec https://api.example.com/openapi.json --list` 列出所有可用端点，`mcp2cli @myapi list-pets --limit 10` 直接调用。支持四种来源：MCP HTTP/SSE（`--mcp`）、MCP stdio 子进程（`--mcp-stdio`）、OpenAPI 规范（`--spec`，JSON 或 YAML）、GraphQL 端点（`--graphql`）。OAuth 2.0 全流程内置——PKCE 授权码流程、client credentials 机器间认证、token 自动缓存和刷新，不用额外配置。

  值得展开的几个设计细节：

  - **Bake 模式**解决重复输入。`mcp2cli bake create petstore --spec https://api.example.com/spec.json` 把连接配置和过滤规则存成命名配置，之后 `mcp2cli @petstore --list` 直接使用。还能 `bake install petstore` 生成独立的 shell 命令，放进 `~/.local/bin/`。
  - **使用频率感知的智能排序**。`--list` 输出按调用次数排序，Agent 看到的是"你最常用的 10 个工具"而不是"全部 96 个工具按字母排"。配合 `--top 10 --compact`，工具列表从 ~1400 token 压到 ~20 token。
  - **自带 AI Agent Skill**。`npx skills add knowsuchagency/mcp2cli --skill mcp2cli` 安装后，Agent 自动学会用它发现和调用 API。甚至能 `mcp2cli create a skill for https://api.example.com/openapi.json` 从 API 自动生成新 skill。
  - **安全处理敏感值**。`--auth-header` 和 OAuth 密钥支持 `env:` 和 `file:` 前缀，避免在进程列表里暴露明文密钥。跟 `fnox` 这类密钥管理器自然衔接。

```bash
# 直接运行（无需安装）
uvx mcp2cli --help

# 全局安装
uv tool install mcp2cli

# 列出 MCP 服务器的所有工具
mcp2cli --mcp https://mcp.example.com/sse --list

# 调用 OpenAPI 端点
mcp2cli --spec ./openapi.json --base-url https://api.example.com list-pets --status available

# 创建命名配置，之后用 @ 前缀直接调用
mcp2cli bake create myapi --spec https://api.example.com/spec.json
mcp2cli @myapi --list
```

### 同类工具对比

| 工具 | 安装方式 | 核心特点 | 价格 | 热度 |
|------|---------|---------|------|------|
| **mcp2cli**（今日推荐）| `uv tool install mcp2cli` | 四协议统一 CLI（MCP/OpenAPI/GraphQL/stdio），OAuth 内置，bake 持久化，token 省 96-99% | 开源 MIT | ⭐ 2.3K |
| MCPorter | `npm install mcporter` | TypeScript 运行时 + CLI 生成 + 类型代码生成，自动发现 7 种 IDE 的 MCP 配置 | 开源 MIT | ⭐ 4.8K |
| Speakeasy | `brew install speakeasy` | OpenAPI → SDK/CLI/Terraform/MCP Server 全栈生成，企业级 | 开源 + 托管 | 商业产品 |
| mcpc (Apify) | npm | stdio/HTTP/SSE 三传输，会话持久化，CI/CD 集成 | 开源 | ⭐ 723 |

  mcp2cli 的核心差异在于"零代码生成"——它不在磁盘上产出任何文件，所有 CLI 命令都是运行时从 API 规范中实时反射出来的。MCPorter 的热度更高（4.8K vs 2.3K），但它是一个 TypeScript 编程运行时，目标用户是写脚本和 hook 的开发者；mcp2cli 的目标用户是"在终端里敲命令的人"——包括人类和 AI Agent。Speakeasy 更企业级但需要代码生成步骤。如果你需要的是"一行命令调任意 API"，mcp2cli 是目前最轻的选择。

## Ponytail — 74K stars 的 YAGNI 执行引擎，让 AI Agent 在写代码前先爬七级阶梯

  AI 编码 Agent 有一个被反复验证的行为模式：它们默认选择"过度工程"。你让它加一个日期选择器，它装了 date-fns、写了一个 DatePicker 组件、配了 17 个 props、写了 3 个测试文件——总共 404 行。你需要的东西是一个 `<input type="date">`，23 行。

  这不是模型笨，是训练数据的系统性偏见。LLM 的训练语料里堆满了 Stack Overflow 上从 2015 年就开始积累的答案——那是一个没有 `fetch`、没有 `Intl`、没有原生模块系统的年代。"安装一个库"在那时是正确的答案，但现在不是了。模型没有"直觉"，它们有上下文窗口。Ponytail 的做法是把"资深开发的直觉"变成一个强制的决策阶梯，注入到每一个 Agent 会话的上下文中。

  这个阶梯只有七级，Agent 在写任何代码之前必须从第一级开始逐级检查：

```
1. 这东西真的需要存在吗？            → 不需要就跳过（YAGNI）
2. 代码库里已经有了？                 → 复用，别重写
3. 标准库能干吗？                     → 用标准库
4. 原生平台功能覆盖了吗？              → <input type="date"> 而不是装个 picker 库
5. 已安装的依赖能解决吗？              → 用已有的，别加新的
6. 一行能写完吗？                     → 一行
7. 以上都不行：写最小可工作的代码
```

  关键是执行时机：阶梯在 Agent **理解完问题之后、开始写代码之前**运行。Agent 必须先读完相关文件、追踪真实的代码流，然后才爬阶梯做决策——懒惰的是解决方案，从来不是分析过程。

  Ponytail 的 benchmark 数据来自真实场景：在一个 FastAPI + React 的实际仓库上，12 个功能任务，每个跑 4 次（Claude Haiku 4.5），对比有无 Ponytail。结果：代码量平均减少 54%（日期选择器从 404 行降到 23 行，颜色选择器从 287 行降到 23 行），token 消耗减 22%，成本降 20%，速度快 27%，安全检查 100% 保持。有意思的是对照组——直接加一句"遵循 YAGNI 原则，写一行式的解决方案"只能减 33% 的代码，且安全性降到 95%。结构化阶梯比自由发挥的提示词更可靠。

  三个强度级别：**lite**（正常写，但把更懒的方案用一行注释告诉你）、**full**（默认，自动执行阶梯）、**ultra**（不仅写一行，还质疑需求本身是不是也需要砍）。可以在会话中随时 `/ponytail lite|full|ultra|off` 切换。

  安装只有一行 `node ponytail.js -i`，覆盖 14 个 AI 编码工具：Claude Code、Codex、Copilot CLI、OpenCode、Gemini/Antigravity CLI、Cursor、Windsurf、Cline、Aider、Kiro、Zed 等。对于支持插件的平台（Claude Code、Codex），安装的是带生命周期 hook 的完整插件——每个会话自动注入阶梯规则；对于只支持规则文件的编辑器（Cursor、Windsurf），复制对应的规则文件即可。额外提供了 `/ponytail-review`（审查当前 diff 找过度工程）、`/ponytail-audit`（全仓库扫描冗余代码）、`/ponytail-debt`（把标记了 `ponytail:` 注释的快捷方式收集成债务台账）三个命令。

```bash
# 安装（克隆后运行）
git clone https://github.com/0xwilliamortiz/ponytail-improved.git
cd ponytail-improved
node ponytail.js -i

# 在 Claude Code 会话中使用
/ponytail full           # 开启默认模式
/ponytail-review         # 审查当前 diff 的过度工程
/ponytail-audit          # 全仓库扫描
/ponytail-debt           # 收集快捷方式债务
/ponytail off            # 关闭
```

  几个该说清楚的限制。第一，Ponytail 是纯提示词工程——没有 AST 检查、没有 linter 集成、没有运行时验证。如果模型幻觉出一个不存在的浏览器 API，Ponytail 不会拦住它，你只会在运行时发现。第二，它假设模型能准确判断标准库/平台的能力边界——在 Claude/GPT 级别上这个假设基本成立，在弱模型上会翻车。第三，对于确实需要复杂实现的任务（认证系统、状态机、多步骤异步编排），Ponytail 的阶梯开销是纯损耗——独立测试发现认证任务上 Ponytail 反而多花了 33% 的代码和 2.6 倍的 token，因为 Agent 在每一级阶梯上推理了半天，最后结论是"还是得写"。

| 工具 | 安装方式 | 核心特点 | 价格 | 热度 |

| clearcli | `npm install -g clearcli` | 检测并清理 Agent 输出中的套话和 AI 句式 | 开源 MIT | 🆕 |

  Ponytail 解决的是"Agent 写了太多代码"；caveman 解决的是"Agent 说了太多废话"——两者互补，可以一起用。Ponytail 比裸写"遵循 YAGNI"提示词的效果好 64%，核心原因是结构化阶梯迫使模型在每一步做显式决策，而不是直接跳到最后一格"写最小代码"（然后省略了输入验证和错误处理）。100% 安全检查的保持率来自阶梯规则中明确的三条不可触碰底线：信任边界的输入验证、防止数据丢失的错误处理、安全措施和可访问性要求。
