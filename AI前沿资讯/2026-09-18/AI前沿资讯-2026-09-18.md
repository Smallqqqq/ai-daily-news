## 1. Tencent/BrowserSkill — 让 agent 借用你已登录的真实浏览器，单日 +1,350 星

![[browserskill-demo.png]]

**评分: 9.0/10 | 可操作性: 高 | 热度: GitHub +1,350 stars/day（总 4,012）· 中文社区多篇报道**

**是什么：**
腾讯开源的浏览器自动化工具，MIT 协议，含 CLI（`bsk`）和配套浏览器扩展两部分。它解决的问题很具体：Playwright、Puppeteer 这类工具起的是干净 profile。撞上需要登录态的场景，比如公司内网后台、已购 SaaS、需要 MFA 的站点，就得从头做一次认证。BrowserSkill 反过来——agent 向你"借"一个已经登录的标签页，用完还回来，浏览器其余部分不受影响。

数据通路分两段：Agent → shell → `bsk` CLI → 本地 IPC → daemon，再由 daemon 经 `127.0.0.1` WebSocket 连到扩展和 Agent Window。仓库是 Cargo + pnpm workspace，`crates/bsk-cli` 装 CLI 和 daemon。因为入口是 shell 而不是 MCP，任何能执行命令的 agent 都能接（Cursor、Claude Code、Codex、OpenClaw、CodeBuddy、WorkBuddy、Pi、Hermes Agent 等）。

**怎么用：**
```bash
# 手动安装（macOS / Linux）
curl -fsSL https://raw.githubusercontent.com/Tencent/BrowserSkill/main/install.sh | sh

# Windows PowerShell
irm https://raw.githubusercontent.com/Tencent/BrowserSkill/main/install.ps1 | iex

bsk --version        # 验证安装
bsk doctor           # 自检；新装时只有 "extension connected" 失败是正常的
bsk install-skill    # 把 bsk 用法装进你的 agent harness
# 再从 Chrome 应用商店 / Edge 外接程序装浏览器扩展
```
也可以直接把 https://raw.githubusercontent.com/Tencent/BrowserSkill/main/AGENT_INSTALL.md 丢给你的 agent，让它自己装。

**为什么重要：**
省掉的是整条重新认证流程。需要登录态的自动化以前要么手工导 cookie，要么维护一套测试账号，BrowserSkill 直接复用你本机的登录状态。另外它把"需要人"的时刻做成了协议：验证码、OTP、确认弹窗走 `request-help`，借用标签页走 allow-once / always-allow / deny 三档授权。0.3.0 起，扩展里的两个自动化开关（借用前确认、允许请求人工帮助）成为唯一权威，`--unattended` 这类旧 flag 不再能覆盖它。单日 1,302 → 1,350 星，两天内新增约 1,300 星。

**讨论现场：**
- 中文社区（WPS 论坛、站长之家）的关注点集中在"操作全在本地、页面快照经本地通道交给 agent"，以及验证码交回用户这个设计——有评论认为这是国内自动化工具少见的合规取向。
- 待确认项：Firefox 支持仍在计划中，非 Chromium 内核浏览器目前只能靠兼容性猜测。

**来源：** https://github.com/Tencent/BrowserSkill

## 2. TencentCloud/Octop — 腾讯云自托管多用户多智能体助手，一条命令部署

![[octop-demo.png]]

**评分: 8.7/10 | 可操作性: 高 | 热度: GitHub +367 stars/day（总 3,498）· 腾讯云开发者社区专文**

**是什么：**
腾讯云开源的 AI 助手平台，MIT 协议，名字取自 Octopus。和 Open WebUI 这类单用户前端不一样，它的第一性场景是"一个管理员，给家里人或者小团队开账号"：每个成员有独立的多个 Agent、工作区、模型、渠道和定时任务，数据按成员隔离。项目的前身是腾讯云的 LightClaw ACE。

架构是单进程，没有消息队列：一个 `HarnessProcessor` 统一路由 Web UI、IM 和 cron 三类入口，启动时从控制面数据库（`~/.octop/octop.db`）重建状态。后端 Python 3.12 + FastAPI，前端 React 18 + TypeScript + Vite + Ant Design，存储可选 SQLite（WAL，默认）、PostgreSQL 或 S3 兼容对象存储。

**怎么用：**
```bash
# PyPI 安装
pip install octop
octop init    # 交互式向导：建库、生成 JWT secret、建第一个管理员
octop run     # 控制台 http://127.0.0.1:8088

# 或 Docker（生产推荐）
docker compose -f docker/docker-compose.yml up -d

# 或一行脚本
curl -fsSL https://finnie-1258344699.cos.ap-guangzhou.myqcloud.com/octop/install.sh | bash
```
GitHub Releases 里还有 Windows (.exe)、macOS (.dmg)、Linux (.tar.gz) 和飞牛 fnOS (.fpk) 桌面客户端。

**为什么重要：**
能力面上它把几件通常在好几个产品里分散的事收进了一个进程：浏览器自动化（Chromium/CDP）、终端 AI+、跨 Linux/Windows/macOS 的远程桌面（实时看屏 + 键鼠控制）、自然语言定时任务、文档 RAG 知识库。IM 通道覆盖飞书、钉钉、QQ、企业微信、Discord。最有意思的是 ACP（Agent Client Protocol）双向集成——你既可以把 Octop 的 agent 提供给 IDE，也可以把编码任务反向委派给 OpenCode、CodeBuddy、Claude Code 和 Codex。模型层通过 OpenAI 兼容 API、DashScope、Ollama 接入。

**讨论现场：**
- 36Kr 与 C114 的报道把它称为"可自部署、可自行修改版本的工作助手"，但腾讯官方并没有这样定位——官方说法是面向开发者、小团队和企业的自托管方案。
- 社区反馈里被反复提到的是 `octop init` 这个向导：相比多数自托管项目要手工填一堆环境变量，交互式建库 + 自动生成密钥降低了首次上手的门槛。

**来源：** https://github.com/TencentCloud/Octop

## 3. bendlang/bend — 用数学证明堵住 AI 写的 bug，HN 292 分

![[bend-demo.gif]]

**评分: 8.5/10 | 可操作性: 中 | 热度: HN 292 points / 152 comments**

**是什么：**
Victor Taelin（Higher Order Company）发布的 Bend 2 编程语言，标语是 "C speed · CUDA parallelism · Lean proofs"。它的出发点是承认一个前提：人类不再逐行读代码了，所以需要一门无歧义的语言，加上机器可检查的证明，才能信任 AI 写出来的软件。

机制是这样的：`LAWS.bend` 声明应用永远不能违反的不变量，比如"玩家不可能穿墙"、"`array_set()` 不得越界"。你每次改代码，Bend 编译器都要求提交一份写在 `PROOF.bend` 里的数学证明，证明这些 law 仍然成立。少了这份证明，合并就是数学上不可能的。作者自己给的定位是 "`AGENTS.md` backed by proof"，即把"别犯错"这句话做成了类型检查。官方 demo：让 AI 把棋盘改成环绕式，在没有 `LAWS.bend` 时它直接合入了一个破坏 law 的 bug；加上之后，AI 被迫重试直到真的建起一堵墙并给出证明。

**怎么用：**
```bash
curl -fsSL https://bend-lang.com/install.sh | sh
bend guide                      # 了解用法
# 在 AGENTS.md 里写下规则：改完必须跑 bend PROOF.bend
bend PROOF.bend                 # 提交前验证
```
后端开发用起来最顺，支持 Linux/macOS。项目很年轻，作者明说了预期有 bug。

**为什么重要：**
证明检查的速度是它和传统证明助手的核心差异。3,200 个泛型实例化，Bend 检查 0.38 秒，Lean 19.2 秒，Rocq 6.04 秒，Isabelle 和 Agda 要 5 分钟以上——大约比 Lean 快 50 倍。这才使得"agent 每次改动后都验一遍"在实际时间内可行。作者解释这个速度来自完全显式（没有 tactics、没有编译期搜索），代价是啰嗦。性能侧，同一份二进制在 CPU 和 GPU 上都能跑：M4 Max 上 Game of Life 单核约 7.8 秒、16 核 0.65 秒、GPU 0.06 秒，约 124 倍加速。并行是自动的，不用线程、锁或 kernel，拆成两半运行时就铺到所有核上。

**讨论现场：**
- HN 上的批评相当直接：有评论称之为"vibecoded"，并指出 GitHub 仓库被压成了单个 commit。作者回应说编译器/运行时/kernel 是人设计的（kernel 经过大量审计），承认有 AI slop（"我们会逐步清理"），论文由 Claude 撰写（但内容准确），并且为 commit 历史道歉；他同时表示自己并不认为这是值得发表的研究，只是在 C/Rust 与 Lean 之间做的 QTT 式线性类型取舍。
- 中文分析（ic.work）补了另一面：Bend 2 与 Bend 1 的 HVM 图重写架构不兼容，约 19,500 行的 Lean 模型与 TypeScript 实现不同步，缺网络库和调试器，性能数字建立在纯泛型实例化这一种负载上，调度器是刚性的二元 fork-join。

**来源：** https://github.com/bendlang/bend （HN: https://news.ycombinator.com/item?id=49746163）

## 4. PrismML Bonsai 2 27B — 54GB 压到 5.9GB，保留 98.2% 性能

![[bonsai2-demo.png]]

**评分: 8.3/10 | 可操作性: 中 | 热度: HN 239 points / 71 comments · 多家技术媒体报道**

**是什么：**
PrismML（Caltech 背景，CEO Babak Hassibi，Ion Stoica 担任顾问）9 月 17 日发布的旗舰压缩模型，基于阿里开源的 Qwen3.8 27B，Apache 2.0。27.8B 多模态（视觉-语言），在 Google v5 TPU 上训练。

压缩手法是三值权重：每个权重从标准 16 bit 塌成 +1、−1、0 三个取值，每 128 个权重共享一个高精度 scale factor。语言模型部分因此压到约 5.8GB，最小的 GGUF 包 5.95GB（另有 7.21GB 的打包版本），对比 FP16 基线的约 54GB。

**怎么用：**
```bash
# 权重在 Hugging Face 上，Apache 2.0 免费下载
# 注意：紧凑格式需要 PrismML fork 的 llama.cpp，标准运行时读不了三值格式和 Hadamard 激活变换
# 后端覆盖 CUDA / Metal / CPU
```
模型页与下载入口见 https://prismml.com/ 。

**为什么重要：**
数字上：20 项基准的聚合分 83.9，对比 Qwen3.8 27B 的 85.4，即保留 98.2%；RTX 5090 上最高 143 tokens/秒。内存缩减 9–10 倍。第一代 Bonsai 27B 只保留了 95%，这一代把损失又拉近了一截。模型卡上的数字和新闻稿略有出入：14 项 thinking 模式基准是 84.78 vs FP16 的 86.32，实测 129.9 tokens/秒；分类别看，知识/推理 79.86 vs 85.55、视觉 66.19 vs 71.36 有明显损失，编码 89.42 vs 89.07 略微反超。也就是说压缩的代价集中在知识和视觉上，代码能力几乎没掉。

**讨论现场：**
- HN 讨论（239 分）里被提到最多的两点：一是必须用作者 fork 的 llama.cpp，标准生态接不上；二是模型卡和新闻稿指标不一致，有人据此质疑口径选择。
- CEO Hassibi 对压缩损失的态度比较坦率：压缩大概率总会留下一些性能，但他预期几百 B 参数级别的模型（计划在几个月内）会更容易压且保留更多能力——第一代 Bonsai 已被下载超 1,100 万次。

**来源：** https://prismml.com/news/prismml-launches-bonsai-2-27b

## 5. Qwen3.8-Omni-Flash + Qwen-MM-Plugins — 全模态模型配一套"让任何 harness 变多模态"的插件

![[qwen-omni-demo.png]]

**评分: 8.0/10 | 可操作性: 高 | 热度: HN 首页 · 中文社区多篇日报头条 · 两个配套框架同日开源**

**是什么：**
阿里 Qwen 团队发布的原生全模态模型。输入侧接受文本、图像、音频、视频，原生音视频输入最长 1 小时，支持立体声和四声道 FOA 空间音频；上下文 1M token（非思考模式最大输入约 991,808，思考模式 983,616，最大输出 131,072）。输出侧只有文本——视频编辑、声音克隆、TTS 这些要外挂工具，通过 function calling 调度。

同一天更值得装的是两个配套开源框架。`Qwen-MM-Plugins`（Apache 2.0）提供图像/视频/文档/3D 处理能力，装进已有的 agent harness 里；`Qwen-Live-Harness` 负责实时连续多模态交互。另有一个低延迟变体 Qwen3.8-Omni-Flash-Realtime，20 秒音频上约 981ms 响应。

**怎么用：**
```bash
# 装 Qwen-MM-Plugins（支持 Claude Code / CodeBuddy / Codex / Qoder / OpenClaw / Qwen Code / Gemini CLI 引导式安装）
curl -fsSL https://raw.githubusercontent.com/QwenLM/Qwen-MM-Plugins/main/install.sh | bash
bash -s -- update          # 后续更新
```
需要 `uv`/`uvx`。默认 native 模式读本地图片视频不需要 API key；vision、OCR、转写、grounding、SAM3 分割这些要走 DashScope API key，搜索类功能要 Serper/Exa/Tavily 的 key。每个能力独立安装为一个 `qwen-mm-plugins-<capability>` 的 Skill 加可选 MCP server。Windows 目前要走 WSL2，原生 Windows 未验证。Qwen-Live-Harness 的 Host 应用是 macOS 独占。

**为什么重要：**
官方数据是 29 项评测平均比 Qwen3.5-Omni-Plus 提升超过 25%。会议说话人分离错误率从 88.11 降到 3.35（cpWER 89.61 → 17.18）。agentic 视频理解把 OmniVideoBench 从 63.4 提到 67.8，同时 token 用量降 45.7%（145,736 → 79,117）。成本侧，音频输入每小时成本降幅超过 98%，音视频超过 93%（基于 720p/1fps、2 分钟样本的算法）。国际 API 定价 $0.15/M 输入、$0.016/M 缓存命中输入、$0.47/M 输出。

**讨论现场：**
- ic.work 的分析给出了保留意见：基准是公司自报且未独立验证，优势集中在音频和工具调用，深层视频推理仍落后；成本降幅很大一部分是因为上一代基线本来就高。
- 同一篇分析指出更实质的问题：输出只有文本意味着真正的端到端音视频生产仍取决于外部工具和围绕存储、处理、token 预算的工程量。

**来源：** https://qwen.ai/blog?id=qwen3.8-omni-flash ｜ https://github.com/QwenLM/Qwen-MM-Plugins

## 6. jamiepine/voicebox — 本地跑的开源 AI 语音工作室，带 MCP server

![[voicebox-demo.webp]]

**评分: 7.8/10 | 可操作性: 高 | 热度: GitHub +667 stars/day（总 54,880）**

**是什么：**
MIT 协议的本地优先语音合成工作室，定位是 ElevenLabs 的开源替代。桌面端用 Tauri（Rust）而不是 Electron，前端 React + TypeScript + Tailwind，后端 FastAPI，存储 SQLite；Apple Silicon 走 MLX/Metal 加速，其他平台走 PyTorch（CUDA/ROCm/XPU/CPU）。官网 voicebox.sh。

内置 5 个可按次切换的 TTS 引擎：Qwen3-TTS（0.6B / 1.7B）、LuxTTS（CPU 友好的轻量英文引擎）、Chatterbox Multilingual（23 语言零样本克隆）、Chatterbox Turbo（350M 英文，支持 `[laugh]`、`[sigh]`、`[gasp]` 这类副语言标签）、HumeAI TADA（1B / 3B）。

**怎么用：**
```bash
# 从官网或 Releases 下载 macOS（Apple Silicon / Intel）与 Windows（MSI / Setup）安装包
# Linux 暂无预编译二进制，需从源码构建

# 或者用 Docker
docker compose up

# 本地服务监听 127.0.0.1:17493，同时暴露三套接口：
#   - REST API（带 OpenAPI 文档）
#   - MCP server（FastMCP，挂在 /mcp）
#   - Web UI
```

**为什么重要：**
把"MCP server + REST API"做成一等公民是它和闭源 SaaS 的分水岭——可以直接当作 agent 的语音层接进去，而不是只能在图形界面里点。功能面上，克隆只需几秒音频；8 种效果来自 Spotify 的 Pedalboard 库（变调、混响、延迟、合唱/镶边、压缩、增益、高通/低通），带预设；自动分块加交叉淡入支持不限长度的生成；生成队列用 SSE 推状态。还有内录、系统音频捕获和基于 Whisper 的转写。

**讨论现场：**
- 中文技术社区（腾讯云开发者社区）的接入指南把它定性为"给开发者用的私有语音层"，明确不建议当作商业配音流水线的直接替代品，并强调只应克隆你有授权的音色。
- 版本演进上，v0.1.x 是围绕 Qwen3-TTS 的单引擎应用，v0.2.0 是推翻重做（四引擎、23 语言、情绪控制、效果链、异步队列），v0.3.0 把后端重构成模块化架构并大修设置页。

## 7. 中电信 Xing4.0-29B-A4B — 首个全栈国产算力训练的开源智能体模型

![[xing4-demo.png]]

**评分: 7.6/10 | 可操作性: 中 | 热度: 新华社《经济参考报》《通信世界》报道 · HF 193 likes · llama.cpp 社区已提交适配 PR**

**是什么：**
9 月 17 日，中国电信旗下中电信人工智能科技（TeleAI）发布并开源的新一代星辰大模型，定位"面向智能体时代的轻量级代码智能体大模型"。MoE 架构：总参数 29B，每 token 只激活 4B（64 个路由专家加 1 个共享专家，每 token 选 4 个），40 层，隐藏维度 3584，注意力用 MLA。原生 256K 上下文，可扩展到 512K。

训练全程使用昇腾 910C（NPU）和 MindSpore 框架——这是国内首个在这个参数规模上完成全栈国产训练的开源模型。

**怎么用：**
```bash
# 权重与配置（safetensors，兼容 Transformers / vLLM / SGLang / KTransformers）
# https://huggingface.co/XingChen-AGI/Xing4.0-29B-A4B
# 同步上线 GitHub / Gitee / 魔搭 ModelScope / 魔乐 Modelers

# llama.cpp 社区已提交适配 PR #29012：含 safetensors 转 GGUF、CPU/GPU 后端推理、量化
# 实测 Q4_K_M 量化后 PPL 8.4526，对比 F16 的 8.1957，仅上涨约 3%
```
低比特量化后 4-bit 版本约 19GB，消费级显卡可以本地跑。

**为什么重要：**
官方评测：SWE-bench Verified 75.0、Terminal-Bench 2.1 57.5、AIME2026 90.0。工程侧的数字更值得看——通过五类协同优化，训练吞吐相比开箱性能提升约 96%。已完成多种国产及主流 AI 芯片平台的适配验证。对比同档 30B 级开源代码模型，它真正拉开距离的地方是训练栈的国产化程度和量化后的可用性（Q4 只掉 3% PPL 意味着可以在消费级硬件上实际部署）。

**讨论现场：**
- 中文技术媒体（clawpk、通信世界）的关注点是"用国产芯片训完一个 29B 智能体模型"，64 个专家只激活 4B 的稀疏比是能在消费级显卡上跑起来的关键。
- llama.cpp 的适配 PR #29012 说明社区已经在推动它进入主流推理生态，这是国内开源模型能否被真正用起来的关键一环。

## 8. ScienceIDE — 把全球科学代码库转成 agent 可学习的环境

![[scienceide-demo.png]]

**评分: 7.4/10 | 可操作性: 中 | 热度: HF Papers 当日第 2 · 70 upvotes · 45 人作者团队 · venv + RL 配方全开源**

**是什么：**
45 人团队（含 Koutian Wu、Zesen Huang 等）做出的科研 agent 基础设施，arXiv 2609.19134，9 月 16 日提交。它针对的问题是"科学经验瓶颈"：科学代码仓库里积累了几十年的知识，但工具链碎片化、领域约定是隐性的、正确性判据又是领域专有的，这些东西很难转成可靠的学习经验。

ScienceIDE 的做法是把仓库变成可编程环境。每个任务是一个容器化的 episode，跑在固定版本、未修改的上游科学代码上。两种任务形态：Repair 模式注入一个语义缺陷，agent 必须修到物理案例通过（参考答案就是注入的精确逆操作）；Implementation 模式挖空某个例程的函数体，agent 要重新实现到能复现原有结果。评分用物理案例的平均分——奖励来自模拟数值重新变正确，不是 diff 匹配，而且有 floor -adjusted 的修复奖励，所以不动的仓库得零分。

**怎么用：**
```bash
git clone https://github.com/aitofound/ScienceIDE
# environments/  15 个环境（共 64）带完整运行时：容器模板、物理案例、检查、评分、上游许可证
# hard85/        30 个任务（共 85 个 ScienceIDE-Hard 任务）
# SFT/  RL/      微调与强化学习配方、曲线、结果（PSRL 上的异步 GRPO）
```
模型（PhAI-IDE-72B / 9B / 4B）在 Hugging Face 的 ScienceIDE Model Series 下。已发布的任务环境覆盖 athena-*（Athena++ 天体物理 MHD）、mitgcm-*（海洋/大气/海冰/生物地球化学）、gkeyll-vlasov、dscribe-descriptors、nest-noble-element-microphysics、edkit-adaptive-krylov-time-evolution、stim-stab。

**为什么重要：**
RL 下的提升幅度值得看。Qwen3.5-4B 基线在 LAPS 环境从 0.357 升到 0.857 mean verifier reward，在 MITgcm-biogeo 从 0.286 升到 0.571。SFT 的提升明显更小，PhAI-IDE-9B 在 LAPS 只从 0.3125 到 0.500。迁移到通用编码任务上则不均匀：9B 在 BBH Word Sorting 上 +36.00 分，但在 HumanEvalFix Python 上回退了。这本身是个有价值的发现——科学代码上的经验迁移是有条件的。每个已发布任务都通过了执行验证：官方修复得 1.0 分，未修复的构建留有余量，agent 镜像里不含答案材料。

**讨论现场：**
- AI Weekly 的报道强调这是把"科学环境"做成可复用基础设施，配合 RL 配方一起放出，而不是放一个一次性数据集就完了。
- 保留意见也在同一批报道里：完整环境集（64 个里的另外 49 个）和完整任务库（85 里的 55 个）作为测试集保留，作者只承诺"随工作成熟"逐步释出，目前维护在 Gen-Verse/ScienceInfra 下。

**来源：** https://github.com/aitofound/ScienceIDE ｜ https://arxiv.org/abs/2609.19134

## 9. mysetup.ai — 让人分享自己真实 AI 工作流，HN 上吵的是 MCP 权限

![[mysetup-demo.png]]

**评分: 7.0/10 | 可操作性: 高 | 热度: HN 188 points / 103 comments**

**是什么：**
一个社区站，开发者把自己实际在用的 AI 工具、模型和完整工作流发布上去。每条 profile 描述的是一整套配置：驱动哪些编码 agent、在什么硬件上跑哪个模型、外面套了哪些听写和编排工具、这些部件怎么串起来。创始人做这个的动机是发现大家的 setup 碎片散落在 X/Twitter 上滚过去就没了，没有一个专门、可比较、保持更新的地方收集。

形式上的选择是围绕"变化"展开：你可以 follow 一个 setup，看它的主人试了什么、放弃了什么、换成了什么——按创始人的说法，弃用才是有效信号，而各种 roundup 只会做加法。无需账号即可阅读。

**怎么用：**
浏览器打开 https://mysetup.ai/ 直接浏览，可按主题搜索过滤。分享 setup 需要登录，最初只有 MCP 流程，在 HN 反馈后加了手动提交和 Markdown 编辑。

**为什么重要：**
真正有价值的是它聚集起来的信息：HN 讨论里真出现了具体配置——Strix Halo / RTX 3070 / 虚拟机上跑 Qwen 和 Gemma、LM Studio、Copilot Chat、OpenHands、Zed；用 Tailscale 把 homelab、手机和各主机连起来；EC2 + tmux 或 SSH 跑远程 agent。这些是平时要靠翻推文才拼得出来的东西。

**讨论现场：**
- 评论区的主要火力不在产品而在 MCP：多人反对把 GitHub 和 MCP 权限交给一个第三方站点或未知的 MCP server，有人说自己根本不用 MCP。作者随后补了手动提交路径。一位评论者说得很直接："我不用 MCP server，但不希望因此被排除在分享之外。"
- 另一类反馈是要更轻的提交方式：贴 Markdown、链一个 GitHub repo，或者让本地工具生成结构化草稿再人工过一遍——有个被分享出来的提示词专门要求 agent 排除密钥、原始配置和私有项目细节，并且"保存私有草稿、展示精确预览、等到明确批准再发布"。
- 也有人提出了尖锐的反对意见：senior 开发者认为工作流和工具选择现在已经接近商业秘密，直接绑在生产力上；反驳的一方则认为经验和直觉仍然重要，分享不会稀释。

**来源：** https://mysetup.ai/ （HN: https://news.ycombinator.com/item?id=49740105）

## 10. OpenAI Astra for Law — GPT-6 的法律配置版，230M 条法律链接检索

**评分: 7.0/10 | 可操作性: 低 | 热度: HN 326 points / 355 comments · 多家法律与科技媒体报道**

**是什么：**
9 月 17 日发布，需要先说清楚它不是什么：这不是新模型，而是 GPT-6 Astra（9 月 3 日发布）的一个行业配置版——加了法律检索索引、法律专用指令、设置和工具。模型选择器里显示为 "GPT-6 Astra Law"，API 里的模型名是 `gpt-6-astra-law`。

检索索引覆盖美国判例法、成文法、法规、法院规则和行政决定，超过 2.3 亿条 URL，来源每日新增。判例数据来自 Free Law Project 的 CourtListener 数据库（覆盖 99.9% 以上已公布的美国有约束力判例法），OpenAI 表示它与 Thomson Reuters 这类授权内容提供商互补。

**怎么用：**
```text
Trusted Access 计划，面向入选律所（集中在 AmLaw 200），
经 ChatGPT 和 Codex 使用。
API 版本标注 "coming soon"，未公布日期与定价。
Harvey 和 Legora 是已公布的 API 客户。
```
同一天 ChatGPT for Word 正式可用。

**为什么重要：**
官方数字是在 Vals AI Legal Research Bench 私有验证集的 200 道美国法律研究题上得出的：Astra for Law 的整体正确性检查通过率 54.0%，GPT-6 Astra 单用网页搜索是 38.7%，相对提升 40%，两者都在最高推理档位。判例题上多找到 24% 的参考案例，从正确意见里多检索最多 54% 的目标段落，答案平均长约两倍。生态侧有 26 个合作方插件（Thomson Reuters、Harvey、Legora、iManage、Relativity、Clio、Intapp、DeepJudge 等）、9 个社区插件和 47 个自定义 skill。Sullivan & Cromwell、Ropes & Gray、Cooley 等律所已经做了合同分析、交易尽调、IPO 准备这类流程工具。

**讨论现场：**
- 最值得记住的保留意见来自 HN 和行业分析：这些数字是厂商自报、跑在私有验证集上、没有独立复现，而 Vals AI 的公开对比里 GPT-6 Astra 大约是 39.42%。第三方的工作流测试也显示改进不均匀——Legora 在财务报表勾稽上约 40% 提升，但它所有 agentic reasoning 任务的平均只有约 3%。
- 悬而未决的问题被列得很清楚：API 何时开放、定价多少，以及发布时没有公布 SOC 2 / ISO / HIPAA 认证或数据驻留方案。

**来源：** https://openai.com/index/astra-for-law/
