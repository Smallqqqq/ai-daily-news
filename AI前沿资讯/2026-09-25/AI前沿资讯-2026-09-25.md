## 1. vectorize-io/hindsight — Agent 记忆系统，单日 +1,668 星登顶全站

![[hindsight-benchmarks.png]]

**评分: 9.0/10 | 可操作性: 高 | 热度: GitHub 今日全站第一（+1,668 stars/day，总 27.8k），本周累计 +3,363 星**

**是什么：**
Vectorize.io 开源的 agent 记忆系统，MIT 协议，与 Virginia Tech Sanghani Center 和 Washington Post 合作研发（论文 arXiv:2512.12818）。它和主流方案的分歧点在目标。Mem0、Zep 解决的是"把对话历史捞回来"，Hindsight 要的是"记住之后会变聪明"。
记忆拆成四类：世界事实、自身经历、观察摘要、带置信度的主观信念，对应 retain / recall / reflect 三个操作。
检索层同时跑四路：语义向量（HNSW）、BM25 关键词、图遍历、时间过滤。融合用 Reciprocal Rank Fusion，再过一遍 cross-encoder 重排。

**怎么用：**
```bash
# Python API
pip install hindsight-api hindsight-client -U

# 一键起服务（Docker，API 8888 / UI 9999）
docker run -p 8888:8888 -p 9999:9999 ghcr.io/vectorize-io/hindsight:latest

# 给编码 agent 装上记忆
npx @vectorize-io/hindsight-coding-agents install all

# CLI
curl -fsSL https://hindsight.vectorize.io/get-cli | bash
```
支持 PostgreSQL/pgvector 或 Oracle AI Database 23ai 存储，25+ LLM provider、60+ 集成，自带 MCP endpoint。

**为什么重要：**
LongMemEval 上跑出 91.4%（Gemini-3 后端），是第一个越过 90% 的 agent 记忆系统。同榜对比：Supermemory + Gemini-3 为 85.2%，Zep + GPT-4o 为 71.2%，纯全上下文塞入 GPT-4o 只有 60.2%。在 OpenAI GPT-OSS-120B 这种开源模型上也能到 89.0%，说明收益不全来自后端模型。BEAM 基准 10M token 档位排第一（64.1%，第二名 Honcho 40.6%）。

**讨论现场：**
- 第三方审计（carsteneu/ai-memory-comparison）复现了 91.4% 这个数字，但列出四项缺失能力：没有显式 delete/forget、没有去重、没有衰减、没有 supersede 机制——长期跑下去记忆会单调膨胀。
- Hindsight 官方博客反手质疑基准本身：LongMemEval 和 LoCoMo 诞生于 32K 上下文时代，"已经无法区分真正的记忆系统和上下文堆填"，这也是他们自己做 BEAM 的原因。

**来源：** https://github.com/vectorize-io/hindsight

## 2. HKUDS/CLI-Anything — 给任意软件自动生成 CLI，让 agent 接管 GUI 程序

![[cli-anything-architecture.png]]

**评分: 8.5/10 | 可操作性: 高 | 热度: GitHub 今日 +413 stars/day，总 50.3k 星，本周趋势榜在列**

**是什么：**
港大数据智能实验室（HKUDS）的项目，一句话概括：扫描软件源码，自动生成一套封装真实后端的 CLI，让 agent 用命令而不是点鼠标去操作专业桌面软件。它绕开了截屏加坐标点击那套 UI 自动化，也不要求软件先有 API，直接调用底层库：PDF 走 LibreOffice，3D 渲染走 Blender，音频走 sox。生成的每个 CLI 都带 REPL、`--json` 结构化输出、undo/redo，外加一份自动生成的 SKILL.md 给 agent 读。

**怎么用：**
```bash
# 装社区现成的 CLI
pip install cli-anything-hub
cli-hub search blender
cli-hub install blender

# 给 Claude Code 装插件，然后为任意软件现场生成
# /plugin marketplace add HKUDS/CLI-Anything
# /plugin install cli-anything
# /cli-anything ./gimp

# 用生成的 CLI
cli-anything-gimp project new --width 1920 --height 1080 -o poster.json
```
支持 Claude Code、Codex、OpenClaw、OpenCode、Goose、GitHub Copilot CLI 等编码 agent 宿主。

**为什么重要：**
生成管线是七阶段全自动的：Analyze → Design → Implement → Plan Tests → Write Tests → Document → Publish，Phase 6.5 自动产出 agent 用的 SKILL.md。仓库自称 40+ 软件、2,461 个测试用例 100% 通过。覆盖的软件里包括 FreeCAD、QGIS/ArcGIS Pro、Draw.io、OBS 这些原本完全没有脚本接口的 GUI 工具。对这类软件，这是唯一不靠 UI 自动化的接入方式。

**讨论现场：**
- 中文技术社区盯的是增速："8 天 3 万星，刷新 AI 开源项目增速记录"（腾讯云开发者社区），不过同一篇文章正文里写的其实是 38 天到 3 万星，标题和正文对不上。
- 测试数字在不同来源间打架：仓库 README 说 2,461 个测试，另一处说 1,436 个场景跨 9 个应用，百度百科词条写 1,588+ 测试跨 13 个应用。三个数字互不吻合，选型时别把测试覆盖率当作硬指标。
- README 自己也提醒：生成的 CLI 只是壳，跑之前得先把 GIMP / Blender / LibreOffice 这些上游软件装好。

**来源：** https://github.com/HKUDS/CLI-Anything

## 3. strands-agents/harness-sdk — 把 agent harness 本身做成一个可控 SDK

**评分: 8.0/10 | 可操作性: 高 | 热度: GitHub 今日 +455 stars/day，总 8.3k 星**

**是什么：**
Strands Agents 开源的 agent harness 与 SDK，Apache-2.0，Python + TypeScript 双实现。核心卖点是"不替你托管"——agent 跑在你自己的进程里，没有厂商控制平面。SDK 把 agent 生命周期里那些每家公司都要重写一遍的东西打包好：轮次上限、token 预算、取消、工具调用、结构化输出、MCP、多 agent 模式、记忆、session、流式、护栏、trace、eval。模型侧不绑定，Amazon Bedrock、Anthropic、OpenAI、Gemini 都是一等公民。monorepo 里同时装了 Python/TS harness、Python/TS SDK、`strands` CLI、MCP server 和文档站。

**怎么用：**
```bash
# Harness 快速上手
pip install strands-harness
python -c "from strands_harness import create_harness; agent = create_harness()"

# TypeScript
npm install @strands-agents/harness

# 底层 SDK（要更细的控制）
pip install strands-agents strands-agents-tools   # Python >= 3.10
npm install @strands-agents/sdk                   # Node.js >= 22
```
```python
from strands import Agent
agent = Agent(tools=[calculator])
```

**为什么重要：**
它把"自己手搓 agent loop"这件事的成本压到几行代码，同时保留了换模型、换云的余地。对已经在用 Bedrock 但不想锁死 Anthropic 或 OpenAI 的团队，这是少数同时提供 Python 和 TypeScript 第一方实现、且不带托管层的选择。文档明确鼓励连文档一起提 PR，说明还在快速迭代期。

**讨论现场：**
- 项目定位直指一个具体痛点：harness 里写死的假设会过期。Anthropic 同期发的 Managed Agents 工程博客讲了同一个问题的另一面——Sonnet 4.5 时代的"上下文焦虑"需要靠 context reset 打补丁，到 Opus 4.5 就不需要了，那些补丁变成纯粹的负担。harness 越大，这种死重量越难清。
- monorepo 同时塞 CLI、MCP server、双语言 SDK，好处是版本一致，代价是任何一处 breaking change 都会牵连全部。

**来源：** https://github.com/strands-agents/harness-sdk

## 4. stepfun-ai/Step-Code — 阶跃星辰开源终端编码 agent，Terminal Bench 2.1 通过率 80.9%

**评分: 7.8/10 | 可操作性: 高 | 热度: 9 月 25 日发布并开源，MIT 协议，394 星（新仓库）**

**是什么：**
阶跃星辰（StepFun）开源进 GitHub 的终端编码 agent。主线是三个词：执行快、长任务稳、token 省。长任务会被拆给多个并行 subagent，各自跑隔离上下文，避免单一上下文被撑爆。比较少见的是内置了 StepPage 插件——一条命令把本地目录推成可分享的静态站点，带版本和回滚，适合把 agent 的产出直接变成可交付物。

**怎么用：**
```bash
# macOS / Linux / WSL
curl -fsSL https://static-openapi.stepfun.com/stepcode/install.sh | bash

# Windows（beta）
irm https://static-openapi.stepfun.com/stepcode/install.ps1 | iex

# 更新
step update

# 从源码
pnpm install --ignore-scripts && pnpm run build && pnpm step
```
`/init` 生成 AGENTS.md（已有 CLAUDE.md 会复用），`/goal` 跑长任务，`/cron` 定时，`Shift+Tab` 切换权限模式（Ask / Read Only / Bypass / Autopilot）。

**为什么重要：**
Terminal Bench 2.1 上 80.9% 通过率，官方强调是并列领先者里 token 消耗最低的——对按量计费的编码 agent 来说，这个指标比通过率更影响账单。兼容性上明确写了"大多数 Claude Code 插件可直接使用"，MCP server 和 Agent Skills 开箱即用，也能自动导入 Claude Code / Codex 的 MCP 配置，迁移成本接近零。

**讨论现场：**
- 仓库只有 394 星、18 个 commit，是典型的"产品成熟度远高于开源活跃度"——3.14.3 版本的 ZCode 也走过同样路线（成熟产品直接开源成 code dump）。选型时要看的是它背后跑着的付费产品，不是仓库本身的热度。
- 权限模式做到了四档，其中 Autopilot 完全放权。配合 `/goal` 长任务使用时要留意：这个组合等于让 agent 在你睡觉时连续改仓库。

**来源：** https://github.com/stepfun-ai/Step-Code

## 5. GitHubSecurityLab/seclab-taskflow-agent — GitHub 把 AI 模糊测试流水线开源了

**评分: 7.8/10 | 可操作性: 中高 | 热度: 9 月 24–25 日 GitHub Security Lab 官方发布，MIT 协议**

**是什么：**
GitHub Security Lab 研究员 Antonio Morales 放出的 LLM 驱动 fuzzing 流水线，专门针对 C/C++ 项目，底层是 GitHub 自家的 Taskflow Agent 框架（"一个构建 LLM 驱动安全自动化的框架"）。默认模型是 Claude Sonnet 5，在 `src/seclab_taskflows_fuzzing/configs/model_config.yaml` 里改。设计原则一句话：LLM agent 负责决策，MCP 工具负责执行。八个阶段串起来跑完发现漏洞到出补丁的全流程。

**怎么用：**
```bash
# 在 Codespace 里打开仓库，然后一条命令指定目标项目
./scripts/fuzzing/run_fuzzing.sh tukaani-project/xz
./scripts/fuzzing/run_fuzzing.sh DaveGamble/cJSON   # 冒烟测试用
```
监控面板在 8765 端口。想跑通需要先装好 AFL++ 和 clang。

**为什么重要：**
阶段划分很具体：找入口点 → 自动写 harness → 调 AFL++ → 读覆盖率报告 → 按覆盖率重写 harness → 分类崩溃 → 出统一 diff 格式的漏洞报告和补丁建议。覆盖率反馈用倍增时间预算：30s、60、120、240、480、960 秒，每个目标累计约 32 分钟，每轮结束 agent 都重新读覆盖率。结构感知 fuzzing 做了四层（格式字典+自定义 mutator、从源码抽字典、动态生成 AFL 字典、语料拼接）。崩溃分七类打标（真漏洞 / 库加固 / harness bug / OOM / 超时 / 断言失败 / 重复），先用 `afl-tmin` 最小化再按调用栈去重。

对比 Google OSS-Fuzz 是两种路线：OSS-Fuzz 从 2023 年就在试 LLM 生成 fuzz target，但主要解决"写 harness"这一步，且要接入它的基础设施；GitHub 这套是可移植工具箱，不用平台注册，还自带分类和报告生成。

**讨论现场：**
- 官方自己列了三条硬警告，其中一条最要紧：**没有容器隔离**。流水线直接在宿主机上跑 AFL++、clang 和 LLM 现场决定的任意构建命令。官方建议只在一次性环境（Codespace 或临时 VM）里跑，绝不给高权限。被 prompt injection 的 agent 能拿到用户能拿到的一切权限。
- 效果指标全部未公开：xz 和 cJSON 上各崩溃多少次、多少是真漏洞、有没有拿到 CVE 编号、token 花销多少、误报率多高，都没发。Morales 自己的说法是这些结论"是交给人的一份准备充分的起点"，不是最终结果。

**来源：** https://github.com/GitHubSecurityLab/seclab-taskflow-agent

## 6. google/mantis — Google 开源 agentic 安全审计技能包

**评分: 7.3/10 | 可操作性: 中 | 热度: 1.7k 星，Apache-2.0，9 月 24 日进入工程日报的推荐清单**

**是什么：**
Google 开源的一套安全审计技能，外加一个 ADK 参考 harness。它的出发点是承认 LLM 做安全审计的两个老毛病：幻觉和严重性通胀。流程里专门设计了环节去压制这两点。中间产物是自动生成的威胁模型，然后由 agent 提假设、调查、去重、分流。补丁环节带一个对抗式验证循环。

**怎么用：**
```bash
cd reference && ./install.sh
gcloud auth application-default login
python3 scripts/configure.py --auto
python3 scripts/configure.py --test --probe

./run.sh path/to/code
./run.sh path/to/code --focus "look for IDOR"
./run.sh path/to/code --no-budget --parallel 32
./run.sh path/to/code --objective "Audit for Server-Side Request Forgery and SSRF in webhook handlers"
```
配置工具是 `mantis-configure` 和 `mantis-launch`。装之前先 `sudo apt install python3-venv`。

**为什么重要：**
针对性最强的设计是那个评分环节：用 rubric 给每个发现打分，对抗严重性通胀。README 的原话是"把最关键的风险暴露给人，而不是喷出几千个 'critical'"。其次是复现深度的可调：从静态利用猜测，到单元测试，再到 mock server，按需要选。工具链整套是 Python + ADK，跑之前要 `gcloud auth application-default login`。Google 那边对外报过内部验证阶段的数字：分流时间压到一分钟以内，精度超过 92%。

**讨论现场：**
- README 的语气在 Google 官方项目里相当罕见，原话直接抄三条："USE AT YOUR OWN RISK. BE EXTREMELY CAREFUL." / "USE THIS ONLY IN ISOLATED, RESTRICTED ENVIRONMENTS." / "This is not an officially supported Google product."——`--no-budget --parallel 32` 这种参数能让 agent 并行开 32 路去扫代码，跑在非隔离环境里后果自负。
- 官方要求所有发现必须由安全专家人工复核后才能上报，明确写了 agent 可能产生幻觉或跑不稳定代码。

**来源：** https://github.com/google/mantis

## 7. vLLM 原生无损文本水印 — Gumbel-max 做进采样器，开销低于 2%

**评分: 7.2/10 | 可操作性: 高 | 热度: 随 vLLM v0.30.0 发布（9 月 24 日官方博客），PR #54053 / #56122 / #56233 密集合并**

**是什么：**
vLLM 把文本水印做成了框架原生能力。原理是 Gumbel-max 技巧：采样时注入由密钥、近期 token 上下文和候选 token 共同决定的伪随机 Gumbel 噪声，然后取 argmax。噪声对全部候选 token 同分布地加，所以 token 选择概率在密钥期望下与普通采样一致，这就是"无损"的来源，官方说法是精确的非失真保证。
实现在 Model Runner v2 的采样管线里（`GPUWatermarkSampler`），排在 temperature、min-p、top-k、top-p 之后。temperature=0 的贪心请求直接跳过。

**怎么用：**
```bash
# 装带水印支持的 vLLM
pip install vllm>=0.30.0

# 文档：https://docs.vllm.ai/en/latest/features/watermarking/
# 生成与检测走同一套 API，需要持有密钥和匹配的 tokenizer
```
文档和 API 参考在 docs.vllm.ai 的 "Text watermarking" 页；PR #54053 是生成+检测的主体实现。

**为什么重要：**
开销集中在采样那一步的一个融合 GPU kernel，vLLM 官方称不引入显著延迟。对照的是外挂式水印方案，那种做法要么跑第二遍模型、要么改 logits 分布，通常带来可测量的质量损失或吞吐下降。
另一个工程细节是它加了个 watermark sample warmup 模块，把 `_philox_gumbel_kernel` 按 specialization（key、logits dtype、skip-mask、USE_FP64）提前 JIT 编译好，避免第一个真实请求在推理路径里等编译。

**讨论现场：**
- PR 审查里有个没解决透的取舍：默认 PRF 选 Philox，GPU 原生、快，但不是密码学安全的；有人建议换 `hmac_sha256`，代价是这个版本会退回 CPU 计算，拿性能换安全性。选哪个取决于你把水印当作合规证据还是防伪手段。
- 猜测性解码会稀释水印强度（草稿 token 跨密钥），所以有了 #56122 的双密钥 Gumbel-max；`allow_target_only_watermarking` 开关让被接受的草稿 token 可以不带水印。检测端需要密钥和匹配 tokenizer，短输出或高可预测输出的信号本身就很弱。水印能不能用，取决于输出长度。
- PR #54053 自己的性能章节状态还挂着 "In progress"，官方吞吐/延迟基准数字尚未公布。

**来源：** https://vllm.ai/blog/2026-09-24-watermarking-in-vllm

## 8. Vercel Drives — 给 agent 一块跨运行存在的硬盘

**评分: 7.0/10 | 可操作性: 高 | 热度: Vercel 官方 changelog 公开 beta（9 月 22 日），开发者社区多篇拆解**

**是什么：**
Vercel Sandbox 的持久化存储，公开 beta。Sandbox 原本的磁盘是临时的，跑完就没了；Drive 是一块可以挂载成目录的存储，不绑定单个 sandbox，跨运行、跨实例复用。官方给的用法就是保住 agent 的工作区或磁盘记忆，以及复用数据集、模型、依赖树。一次只能有一个读写挂载，写完之后其他 sandbox 可以通过时间点快照并发只读。

**怎么用：**
```javascript
import { Sandbox, Drive } from '@vercel/sandbox';

const workspace = await Drive.getOrCreate({ name: 'agent-workspace' });
const sandbox = await Sandbox.create({
  mounts: { '/data': workspace }
});
// sandbox 停掉后 /data 下的内容仍在 Drive 上
```

**为什么重要：**
定价透明：iad1 区域存储 $0.05/GB-月，读 $0.0015/GB，写 $0.004/GB；Hobby 档每月含 15 GB 存储和 30 GB 读写。每个 sandbox 最多挂 4 个 Drive，分在不同路径。默认上限 1 TiB（Hobby 1 GiB），可配到 16 TiB。限制也说清楚了：Drive 建在哪个区域就留在哪个区域，挂载它的 sandbox 必须跑在同一区域，没有 failover。

**讨论现场：**
- dev.to 的拆解给了个精准的概括："persist the workspace, not the run"——sandbox 磁盘保持单次运行的草稿区定位，Drive 装 agent 的工作树、编辑和装好的依赖。这个切分比"给 sandbox 加大磁盘"更贴近 agent 实际的工作方式。
- Rauch 之前在采访里的说法可以对照看：他把 Vercel Sandbox 描述成把 agent 关进"小笼子"以便管控数据和审计，并主张"世界正从页面走向 agent"、agent 才是新的云原语。Drives 补的正是这个原语的持久化缺口——agent 要连续想几分钟、几小时甚至几天，中间不能因为 sandbox 重启就失忆。

**来源：** https://vercel.com/changelog/drives-for-vercel-sandbox-are-now-in-public-beta
