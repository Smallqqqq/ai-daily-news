## 2. anthropics/financial-services：Anthropic 官方开源 10 个金融 Agent + 11 个 MCP 连接器

**评分: 8.8/10 | 可操作性: 高 | 热度: GitHub Trending 单日 +424 stars，当日新入榜第 5 位**

**是什么：**
Anthropic 官方开源的 Claude for Financial Services 工具包，面向投行、股票研究、私募、财富管理、基金管理与运营等场景。核心设计是"一份源码、两种封装"：每个工作流只写一次，既能作为 Claude Cowork 插件交互使用，也能通过 API 部署成 Claude Managed Agent（CMA）做无头编排。仓库全部是 markdown 和 JSON，没有构建步骤。

内置的命名 agent 包括 Pitch Agent、Meeting Prep Agent、Market Researcher、Earnings Reviewer、Model Builder、Valuation Reviewer、GL Reconciler、Month-End Closer、Statement Auditor 和 KYC Screener。MCP 连接器覆盖 Daloopa、Morningstar、S&P Global、FactSet、Moody's、MT Newswires、Aiera、LSEG、PitchBook、Chronograph、Egnyte、Box。

**怎么用：**
```bash
# 通过 Claude Code 插件市场安装
claude plugin marketplace add anthropics/claude-for-financial-services

# 部署成 Managed Agent（需要 ANTHROPIC_API_KEY）
export ANTHROPIC_API_KEY=sk-ant-...
scripts/deploy-managed-agent.sh gl-reconciler --dry-run
scripts/deploy-managed-agent.sh gl-reconciler
```
注意仓库 slug（`anthropics/financial-services`）与插件市场名（`claude-for-financial-services`）不一致，这是最容易踩的坑。

**为什么重要：**
这是 Anthropic 把"垂直行业 agent"从演示推进到可部署资产的一步。`plugins/vertical-plugins/` 作为领域技能、斜杠命令和 MCP 连接器的唯一真源，`check.py` 负责 lint 和漂移检测，`sync-agent-skills.py` 保证同一份定义在插件与 CMA 两侧不跑偏——解决了此前垂直 agent 做两份实现、两边行为不一致的问题。11 个 MCP 连接器意味着一套插件可以直接接上投行实际在用的数据源，而不是只读本地文件。局限也要说清楚：`callable_agents` 子 agent 委派仍是研究预览，MCP 连接器需要各自订阅或 API key，不是免费的数据管道。

**讨论现场：**
- 社区实测反馈集中在安装环节：连接器 JSON 格式错误、hooks schema 不匹配、Bedrock 区域 model ID 报错是三个高频问题。
- 关于定位，有讨论指出这套东西的价值不在于"让 Claude 会算 DCF"，而在于把编译、DCF、LBO、三表模型、deck QC、Excel 审计这些重复动作固化成可审计的脚本入口（`/comps`、`/dcf`、`/earnings`、`/ic-memo`），让模型只负责判断而不是从零铺表格。

**来源：** https://github.com/anthropics/financial-services · https://agentpedia.codes/blog/anthropics-financial-services-guide

## 3. akitaonrails/ai-memory：一个 Rust 二进制，让 Claude Code 和 Codex 交接上下文

**评分: 8.6/10 | 可操作性: 高 | 热度: GitHub Trending 单日 +167 stars，DEV 社区与 Product Hunt 同步讨论**

**是什么：**
给 agent 编码 CLI 做长期记忆、并支持跨厂商交接的工具。解决的问题很具体：你在 Claude Code 里干到一半退出，换 Codex 或 Cursor 在同一个目录里继续，一切都要重新解释一遍——架构、试过但失败的路子、还没想清楚的问题。ai-memory 通过生命周期钩子自动抓取 prompt、工具调用、压缩检查点和会话边界，编译成 Git 版本化的 Markdown 页面（借鉴 Karpathy 的 compile-not-retrieve 思路），可 grep、可用 Obsidian 打开、可 rsync，不需要向量数据库。

检索层是 Rust 服务，SQLite FTS5 索引加混合排序：FTS5 + 实体匹配 RRF + 图邻居 RRF + 可选向量 RRF，再叠一层有界来源权威度调整。下次会话启动时，agent 会收到一个有界的"你上次停在哪"交接块。

**怎么用：**
```bash
# Arch Linux
yay -S ai-memory-bin

# Docker（默认监听 127.0.0.1:49374）
git clone https://github.com/akitaonrails/ai-memory
cd ai-memory && ./docker/run.sh

# 接入各客户端
ai-memory install-hooks
ai-memory install-mcp

# 常用命令
ai-memory bootstrap          # 从现有仓库的 git log / README / docs 播种 wiki
ai-memory search "xxx"       # 终端 FTS5 检索
ai-memory run claude         # 托管式跨 harness 工作流，带原生会话恢复
```

**为什么重要：**
支持 Claude Code、Codex、Cursor、Gemini CLI、Devin CLI、OpenCode、Kimi Code、Kiro CLI 等 20 多个客户端，是当前覆盖面最广的一层。LLM 是可选的：零 LLM 模式下仍有 FTS5、实体和图检索加规则摘要；配上 provider 才启用合并、矛盾 lint 和带评估门控的自动改进循环。记忆页有生物式衰减加访问强化——情节页会淡忘，语义/程序/置顶页豁免，这是多数"永久记忆"方案没处理的检索污染问题。平台支持 Linux（Docker 主目标）与 macOS，Windows 走 WSL2，原生 Windows 仍是实验性。

**讨论现场：**
- 作者自己在 README 里写明是和 Claude Code 协作完成的，社区关注点因此转向"这套记忆到底减了多少重复解释"而非实现细节。
- 争论集中在"Markdown wiki + FTS5 是否够用"：支持方认为 grep 可得、可版本回滚、可人工修订是 agent 记忆的必要属性；质疑方认为纯文本检索在跨项目语义关联上不如向量方案，RRF 混排只是在补这个短板。

**来源：** https://github.com/akitaonrails/ai-memory

## 4. Jakubantalik/thinking-orbs：给 agent 界面做"思考中"动画，3,111 星首次上榜

![[thinking-orbs-demo.png]]

**评分: 8.3/10 | 可操作性: 高 | 热度: GitHub Trending 首次入榜，3,111 stars（单日 +168），libraries.dev 显示累计 4,220,214 次安装**

**是什么：**
一套点阵式"思考球"加载指示器，专给 AI 与 agent 界面用。作者 Jakub Antalik 认为多数产品还在用脉冲圆点或旋转 spinner 表示"模型在干活"，而这类动画在一段交互里可能占据 30% 以上的感知时长，值得认真做。库里带九个手工调过的动画状态，对应 agent 的动作语义：working（粒子在倾斜轨道上绕行）、searching（扫描经线扫过点阵球）、solving（色带先乱后"咔"地归位）、listening（波形穿过圆环）、connecting、weaving、composing、breathing、shaping（圆 → 三角 → 方）。

两个尺寸预设是分别设计而非等比缩放：64px 用于聊天头像位，20px 用于行内文字位，各自有独立的点数、点径和速度参数。纯 Canvas 2D 实现，不用 WebGL、不用滤镜，Chrome / Safari / Firefox 渲染一致。

**怎么用：**
```bash
npm install thinking-orbs
```
```tsx
import { ThinkingOrb } from "thinking-orbs";

// 状态跟随 agent 实际动作切换
<ThinkingOrb state="searching" size={64} theme="auto" />
```
无障碍与性能都做了：每个状态带 `aria-label`，`prefers-reduced-motion` 下退化为静态帧，离屏或标签页隐藏时自动暂停，所有实例共享一个时钟。

**为什么重要：**
在一个"模型能力趋同、产品靠体验细节拉开差距"的阶段，把加载态做成有语义的反馈通道，比再堆一个功能更容易被用户感知。生态扩散速度印证了需求：Flutter（`thinking_orbs_flutter`）、React Native/Expo（`expo-thinking-orbs`，用 Skia + Reanimated 跑在 UI 线程）、SolidJS（`solid-thinking-orbs`）、甚至 Pi 编码 agent 的终端扩展（`pi-thinking-orbs`，通过 Kitty/iTerm2 图像协议渲染 64×64 PNG 帧）都已出现。项目已从 orbs.jakubantalik.com 迁至 libraries.dev。

**讨论现场：**
- 社区移植者指出原库的关键取舍："每个状态都是纯 CPU 数学，每帧只吐几十个点的数组"——这是它能做到跨浏览器像素级一致、且不抢 GPU 的原因。
- 有前端工程师把它当作 AI 产品差异化的具体样本：模型能力收敛之后，用户感知到的"快"很大程度上由加载动画的节奏决定，而不只是端到端延迟。

**来源：** https://github.com/Jakubantalik/thinking-orbs · https://libraries.dev/

## 5. zhouxiaoka/autoclip：一条命令起一个 AI 视频切片工作站

![[autoclip-demo.jpg]]

**评分: 8.0/10 | 可操作性: 高 | 热度: GitHub Trending 单日 +250 stars，Trendshift 日榜在列**

**是什么：**
AutoClip 是一个自托管的 AI 视频切片与高光提取工具。支持 YouTube、B 站一键下载和本地上传，用 AI 分析后自动找出高光片段并切好，按类别归入合集。前端 React 18 + TypeScript + Ant Design，后端 FastAPI + Celery + Redis + SQLite（可升 PostgreSQL），下载走 yt-dlp，进度通过 WebSocket 实时推。

模型侧兼容面很宽：通义千问、任何 OpenAI 兼容 API、Gemini、SiliconFlow，也支持 Ollama 和 LM Studio 跑本地模型（不填 API key、完全离线）。除了 Web 界面，还带 CLI、内置 MCP server 和 Agent skill，可以从 Cursor / Claude 里直接调用。

**怎么用：**
```bash
git clone https://github.com/zhouxiaoka/autoclip
cd autoclip

# Docker 一键起（推荐，4GB 内存起，建议 8GB）
./docker-start.sh

# 或本地模式
./start_autoclip.sh

# CLI 用法，指定本地模型
autoclip run video.mp4 --provider ollama
```
也提供桌面版：AutoClip Desktop v1.2.1 有 macOS（Apple Silicon，ad-hoc 签名）和 Windows（x64，未签名）安装包，内置便携 Python 运行时和静态 ffmpeg/ffprobe，不需要额外装依赖。

**为什么重要：**
把"下载 → 转写 → AI 打分找高光 → 切片 → 归集"这条原本需要四五个工具串起来的流程，收进一个自托管服务。模型层不锁厂商，本地 Ollama 也能跑完整个流程。参数可调：`chunk_size` 和 `min_score_threshold` 控制切片粒度与阈值。桌面版 v1.2.0 起支持无字幕视频一键装 Whisper、切片标题可编辑、B 站多账号管理、合集拖拽排序。已知限制：无 GPU 时速度偏慢，B 站下载需要浏览器登录态。

**讨论现场：**
- 中文开发者社区的实际反馈集中在硬件成本上：有人租 AutoDL 4090 实例跑批量切片，认为 GPU 是这类工具的实际门槛，而非模型选择。
- B 站下载的登录态问题是最高频的报错来源——需要选对浏览器配置，否则直接失败；这一点在 README 里只以一句提示带过。

**来源：** https://github.com/zhouxiaoka/autoclip

**讨论现场：**
- 中文社区把它称作"一台真正离线的生存 AI 电脑"，讨论焦点是自然灾害、野外作业、网络审查三类场景下的实际可用性。
- 硬件社区围绕 benchmark 排行榜组织内容：项目自带硬件评分与社区榜（benchmark.projectnomad.us），用户按跑分决定配置，形成了少见的"先看能不能跑动再决定装不装"的讨论方式。

## 7. coder/coder：自托管 agent 开发环境，2.34 把 AI Gateway 设为默认开启

![[coder-demo.png]]

**评分: 7.7/10 | 可操作性: 中高 | 热度: GitHub Trending 单日 +460 stars，9 月 18 日起连续在榜**

**是什么：**
Coder 是自托管的云开发环境与 AI 编码 agent 平台。工作区用 Terraform 定义（EC2 实例、Kubernetes Pod、Docker 容器），通过 WireGuard 连接，空闲自动关机。2.34 版本（当前 ESR）的核心变化是把 AI Gateway 默认打开（`CODER_AI_GATEWAY_ENABLED=true`），并推进 Coder Agents 的 beta：agent 流量出现在 AI Gateway 的审计与会话视图里，支持把只读 agent 会话分享给同事、用斜杠命令调用 markdown 写的 Personal Skills、新模型自动配置推荐默认值，以及 GitLab 集成（MR 状态、diff、分支到 MR 的解析）。

对多模型团队更实用的是 provider key 故障转移：每个 provider 最多配 5 个 OpenAI 或 Anthropic key，遇到限流或鉴权失败自动重试切换，密钥不写日志。User Secrets（beta）让每个用户把自己的 key-value 存一次，自动注入到所有工作区。

**怎么用：**
```bash
# 用官方安装脚本部署服务端（需要 PostgreSQL 13+ 与外部访问 URL）
curl -fsSL https://coder.com/install.sh | sh

# 或用 Helm 装到 Kubernetes
helm repo add coder-v2 https://helm.coder.com/v2
helm install coder coder-v2/coder \
  --namespace coder --create-namespace \
  --set coder.env[0].name=CODER_ACCESS_URL \
  --set coder.env[0].value=https://coder.example.com
```
AGPL-3.0。官方支持的编码 agent 包括 Claude Code、Codex 和 OpenCode。

**为什么重要：**
agent 的编码循环跑在控制平面、你自己的基础设施上，工作区里不存 API key——这是企业采纳编码 agent 时最常被合规卡住的一点。Coder 9 月 2 日还发布了 Agent Relay：在 Cursor 的云端 agent 会话与自有 Coder 工作区之间做代理，把 Coder 注册成一个算力池，让文件操作和命令执行发生在客户自己的基础设施内，推理与规划仍留在 Cursor，工具调用的归属通过与组织 IdP 匹配，提交记录与人写的代码同源可溯。

**讨论现场：**
- Coder CEO Rob Whiteley 的说法被反复引用："公司从来没有拒绝 AI agent，他们拒绝的是部署模型。"配套数据是 1% 的 Coder 工程师消耗了 40% 的 token 预算。

## 8. Kev：花 95 美元 H100 时间，把 Jev 式决策模型复刻到 Qwen3.5 上

**评分: 7.5/10 | 可操作性: 中高 | 热度: HN 408 points / 184 comments，中文、日文、韩文社区同步转载**

**是什么：**
Jared Palmer（Cognition 工程 VP，Turborepo 与 Vercel v0/AI SDK 作者）发布的开源项目，在阿里 Qwen3.5 基座之上实现了一族"类 Jev"的极小型决策模型，三个规格：0.8B、4B、9B，Apache-2.0 许可，训练代码、评估数据和模型卡一并公开，权重可从 HuggingFace 和 GitHub Releases 取。

与 Jev 一样，Kev 不生成文本，只返回带类型的概率：yes/no（noul）、多选（choice，最多 255 个选项）、有序打分三类 schema。定位是"嵌在软件工作流里的小型语义判断"——工单路由、升级路径选择、客户情绪打分这类场景。架构上每个检查点是冻结 Qwen3.5 基座上的 rank-16 LoRA 适配器加一个小型指针式读出头，读出头给传入的选项打分，因此支持开放词表、零样本分类，不用重训。

**怎么用：**
```bash
# 权重
huggingface-cli download jaredpalmer/kev-9b

# 训练代码与评估数据
git clone https://github.com/jaredpalmer/kev
```
训练用两个 epoch、约 1 万条来自十个公开数据集的样本，加 896 条生成的策略样例和 1,680 条规则样例，损失函数用交叉熵。整个移植成本约 95 美元的 Modal H100 时长，加 0.03 美元的 Jev API 调用。README 明确说明训练没有使用任何 Jev 输出。

**为什么重要：**
Kev-9B 在锁定测试集上准确率 0.837，托管版 Jev 为 0.857；外部测试结果分裂——SemIf 的 144 条自撰决策上 Jev 领先（0.965 vs 0.917），而 scienthoon 的 900 条客服工单路由上 Kev-9B 反超（0.952 vs 0.897）。作者自己提醒这不是受控的架构对比，因为 Jev 的训练数据未知。已知回退：Apple M5 上有明显延迟退化，Kev-4B 处理五个问题要 779ms，而此前 Qwen3 版本只要 174ms，作者建议低延迟 Mac 场景先用旧 Qwen3 模型，等 MLX 后端上线。训练方法上 Kev 用的是交叉熵，与 Jev 的 RLCD 不同——这也成了"能不能叫 Jev-like"的争议点。

**讨论现场：**
- HN 上的核心分歧是"这到底是不是新东西"。Oras 的评论被广泛引用："vibe coder 们刚刚发现了分类器。"BoorishBears 强烈反对把它类比成 BERT，认为指针式读出头的开放词表能力与固定标签分类不是一回事。
- 实用性建议倒是很一致：把这类模型放进编码 agent 当验证器、做工具调用前的削减代理、游戏 AI、垃圾信息过滤。

**来源：** https://hn.nuxt.dev/item/49783999 · https://explainx.ai/blog/kev-open-source-jev-clone-qwen35-family-2026

## 10. Mini-AGI：8GB 显存笔记本上从零训练的持续学习模型

![[mini-agi-demo.png]]

**评分: 7.0/10 | 可操作性: 中 | 热度: Show HN 248 points，HN 讨论线与多个聚合站转载**

**是什么：**
volotat 发布的一个实验性持续学习语言模型，目标是在只有 8GB 显存的消费级 GPU 上从零训练，数据以 batch-1 的连续流喂入（作者用的是 RTX 3070 Laptop）。核心设计是把权重视为磁盘上的文件：只有当前活跃的"工作集"专家被换入显存，因此模型总容量由磁盘空闲空间决定，而不是显存。模型是字节级的（256 个值，无 tokenizer），用无学习参数的旋转位置编码，使上下文可以通过持续训练增长。每个字节经过两个稠密前置块，再经过最多 24 次应用的循环块，配一个 PonderNet 式停机头按字符动态调整深度，以及每块应用上的 soft top-8 MoE 路由。

**怎么用：**
```bash
git clone https://github.com/volotat/mini-AGI
cd mini-AGI
# 按 README 安装依赖后开始训练/推理；读取与训练是同一个前向过程
```
权重尚未发布，作者说按当前阅读速度还需两周左右。

**为什么重要：**
真正的发现在灾难性遗忘的处理上。只训练 52.4 万个字符的国际象棋数据后：主干（嵌入、注意力、路由、停机头）与专家同学习率时，另外七门学科退化 +2.2300 nats，只保留 50.68% 的进度；把主干学习率降到专家的 0.1 倍后，退化收敛到 +0.0067 nats，相对随机水平保留了 99.84%。主干承载了 97.6% 的平方梯度范数，它的学习率是让持续学习成立的关键机制。反直觉的是，专家池本身并不是防遗忘的原因——冻结工作集只解释了约 13.8% 的效果，损害的本质是"位移而非摧毁"，被破坏的知识在重新学习时恢复速度快约 380 倍。局限也要讲：目前只读完 78 亿字符语料的第一部分（约 2.43 亿字符），生成的文本语法通顺、话题切题但会重复循环；作者称这是玩具规模的实验，不足以支撑泛化性结论。

**讨论现场：**
- HN 反应以好奇和鼓励为主，"proto-AGI""让人耳目一新"是常见评价，随后迅速转向"泛化还是记忆"的追问，以及和 RAG、上下文管理的比较。
- 最有价值的一条批评针对标题本身：给下一课上机不等于持续学习，真正的基准是保留率核算——这一点作者自己在 README 里承认了，也是在数据里唯一给出了严谨对照的地方。

**来源：** https://github.com/volotat/mini-AGI
