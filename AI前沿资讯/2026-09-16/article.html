5. Droid ASC — 把 APK 当只读数据库查，352MB 全局交叉引用 1.79 秒

![droidasc-demo](./droidasc-demo.png)
影响力 8.2/10

是什么：

面向 agent 和移动安全研究者的高速 Android 反编译前端，Apache 2.0，Python 写的。它放弃传统反编译器的路子——不再把 APK 完整解压再建庞大的全局索引，而是把编译好的 APK 当成只读数据库按需查询，零预处理。

四个关键技术点：直接在 Deflate 位流里探测（密集 Huffman 查找表，跳过完整解压）；把 R8 编译器的优化特性反过来当反编译原语用（确定性常量重定位、指令去重）；一个 O(1) 的指令定位原语，不用映射表就能把字节码偏移映回方法；在内存里动态重建最小自洽 DEX，只反编译目标类和它的依赖。

怎么用：

pip install droidasc          # 需要 Python 3.10+

droidasc getclass app.apk com.poc.Main -o Main.java
droidasc getmanifest app.apk
droidasc findrefs app.apk string token --fuzzy-class
droidasc findrefs app.apk --threads 8 -o refs.txt
python main.py app.apk --gui

为什么重要：

在同一份 352MB 商业 APK 上：全局交叉引用搜索 1.79 秒，目标类反编译 177 毫秒，峰值内存 141MB。Jadx、JEB、Bytecode Viewer、APKtool 这类工具在同样文件上要几分钟、几个 GB 内存。作者用 Agent + ASC 的组合在荣耀和小米产品里挖到两个 RCE 漏洞，据称并行分析了 10 个以上 APK——这是 agent 驱动批量漏洞挖掘的一个具体样本。

讨论现场：

  • 国内安全社区的标题是"Android 反编译核武器"，FreeBuf、安全牛等多家媒体做了报道
  • 被 BlackHat EU Arsenal 收录，议题标题《Droid ASC: R8 Compiler Optimization as a DeCompiler Primitive》
  • 定位是 Jadx MCP 的替代品，agent/LLM 集成里明确列出了 Cursor 和 Claude/GPT 模型

来源：https://github.com/MG1937/ASC

6. Kimi-K3 DSpark — vLLM 开源投机解码器，数学推理从 110 冲到 435 tok/s

![dspark-demo](./dspark-demo.png)
影响力 8.0/10

是什么：

vLLM 用自家 Speculators 训练库给 Kimi K3（2.8T 参数）训的 DSpark 投机解码器：5 层、5B 参数的 draft model，每步提 8 个 token。DSpark 本身是 DeepSeek DFlash 块级投机解码的扩展——DFlash 用非因果骨干一次预测整个 token 块（比 EAGLE-3 的顺序草拟快 2.5 倍），代价是并行位置之间没法互相参照，会出现"后缀衰减"。DSpark 保留并行骨干，加两个轻量组件：一个 Markov logit-bias 头（低秩转移矩阵做顺序修正）、一个置信度头（硬件感知的前缀调度）。

怎么用：

# 权重（Apache 2.0）：https://huggingface.co/RedHatAI/Kimi-K3-speculator.dspark
# 底座：moonshotai/Kimi-K3
# vLLM 通过 --speculative-config 启用，method 选 dspark

DSpark draft model 的格式是标准 Hugging Face 兼容格式，vLLM 直接加载。

为什么重要：

验收序列比 DFlash 长 16–18%，比 EAGLE-3 长 27–31%。发布的 speculator 宏平均验收长度 4.11 tokens/验证轮（数学 6.42、HumanEval 4.96、翻译 4.65），在 LongBench-v2 的 378K token 提示上能到 5.31 tokens/迭代。并发从 1 提到 16，聚合输出吞吐从 177 tok/s 涨到 683 tok/s。单流数学推理从约 110 tok/s 提到约 435 tok/s。

训练用多节点方案：Kimi K3 塞不进单个 GB300 节点，所以把隐藏状态抽取和 draft 训练放在不相交的节点组上，通过 Mooncake store 流式传隐藏状态。

讨论现场：

  • vLLM 博客明确划了边界：435 tok/s 是 GB300 NVL72 上数学推理的数字，跟更早 SPEED Bench 上 370 tok/s（118 → 370，3.14 倍单用户加速）不是一回事
  • 官方提醒 DSpark 对硬件配置敏感，收益随工作负载类型和并发数变化很大
  • 支持正在往昇腾等平台扩展，vllm-ascend 已经有对应 PR（#13277）

来源：https://vllm.ai/blog/2026-09-15-kimi-k3-dspark

Google 发布的两款实时对话模型。gemini-3.8-live 走规模和成本效率路线，做对话智能 + 流畅对话 + 视觉基础定位：支持近实时视觉输入，对话中自动检测并切换 97 种语言，工具和 API 调用在后台执行、不打断对话。gemini-3.8-live-extended-thinking 走复杂多步任务，核心是"边说边想"——推理和说话同时进行，用"让我查一下……"这类话术填住沉默，并且能边做多步后台任务边播报进度。

10. Atria Dawn Preview — 上海 AI Lab 的 744B 科研 agent 模型，MIT 开源，16 项基准里 5 项第一

![atria-dawn-demo](./atria-dawn-demo.png)
影响力 7.5/10

是什么：

上海人工智能实验室（InternLM 团队）的基础型 agent 语言模型，底座是 744B 参数的 MoE（GLM-5.2 血统），目标是科研和工程工作流，把开放性问题变成"可执行、可验证、可复现"的结果。纯文本模型，MIT 协议，标准权重和 FP8 检查点都在 Hugging Face 和 ModelScope 上。

训练方法叫"可验证经验流水线"（Verifiable Experience Pipeline）：每个训练任务挂在真实执行环境上，模型观察状态、调工具、产出中间产物、根据反馈调整；结果由外部信号验证（测试、指标、文件状态、来源证据、人工标准）。通过验证的经验轨迹——包括失败的路径——都保留下来当能力建设材料，模型不给自己打分。

怎么用：

# 权重：Hugging Face / ModelScope，MIT 协议
# 代码：https://github.com/atria-asi/Atria-Dawn-Preview
# 论文：https://arxiv.org/abs/2609.15818
# 上下文窗口 256K

BF16 权重约 1.5TB（约 353 个 safetensors 分片），FP8 约 756GB。

为什么重要：

16 项覆盖研究、工程和数字工作的基准里，官方称与前沿 agent 相当，其中 5 项拿到最高分。公开数字：DeepSearchQA 96.0、BFCL v4 77.0、CyberGym 86.5、AutomationBench 53.8。论文还分析了模型自身开发过程中 56 名参与者的 769 条任务记录：同等条件下评估已完成任务时，参与者认为约三分之一的 AI 辅助任务离开 AI 就做不出来。agent 经常提方法、做修改，最终决定权多数还在人手里。

讨论现场：

  • HF Papers 上 364 upvotes
  • 开源节奏本身也有信息量：HF 仓库 9 月 11 日左右上线，9 月 12 日放 FP8 检查点，没有博客也没有定价，论文 9 月 14 日才提交
  • 有一处数据冲突：官方模型卡和 GitHub 写 256K 上下文窗口，但 OrcaRouter 报告可下载的 config 设的是 1,048,576 tokens

来源：https://github.com/atria-asi/Atria-Dawn-Preview
