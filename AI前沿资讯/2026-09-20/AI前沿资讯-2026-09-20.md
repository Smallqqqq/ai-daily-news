## 1. browser-use/jev-ultrafast — 把浏览器 agent 的每步决策压成一次前向传播

![[jev-ultrafast-demo.gif]]

**评分: 9.2/10 | 可操作性: 高 | 热度: GitHub +1,739 stars/24h（趋势榜第 2），总 8.7k stars；HN 89 分 / 14 评论**

**是什么：**
Browser Use 团队与 TypeSafe 合作的浏览器 agent，核心是"动态索引动作空间"。每一步把当前页面 DOM 抽成一张带索引的元素表，然后一次 TypeSafe Jev 请求同时带上动作头和候选目标头（`click_target`、`type_text_target`、`select_target`），一轮往返做完"做什么"和"对谁做"两个决策。只有当动作是 `TYPE_TEXT` 时才调用小 LLM 生成文本，默认的 agent loop 里完全没有截图。

**怎么用：**
```bash
git clone https://github.com/browser-use/jev-ultrafast.git
cd jev-ultrafast
uv sync
cp .env.example .env      # 填入 TYPESAFE_API_KEY 和 TEXT_MODEL_API_KEY
uv run jev                # 打开 127.0.0.1:8766 的 inspector，选 "Start demo → Run automatically"
uv run browser-harness --doctor   # 排查 Chrome 连接问题
```

代码里当库用：
```python
from jev_ultrafast import Agent
agent = Agent(url="https://...", goal="找到 10 月 1 日苏黎世飞伦敦最便宜的直飞")
for step in agent.run():
    print(step["elapsed_ms"], step["status"])
```

**为什么重要：**
六轮交替实测（同一模型同一设置）中位任务耗时从 9.450s 降到 7.092s，降幅 25%；浏览器协议调用次数从 1,092 次降到 101 次，降了 91%。单次 Google Flights 苏黎世→伦敦搜索 7,073ms 跑完，视频是 1× 速度。省下来的是"截图 → 视觉编码 → 定位坐标"这条路上的往返开销，模型本身的推理时间没怎么变。README 自己注明这只是一个任务重复三次的结果，不是通用可靠性基准。

**讨论现场：**
- README 明确划了边界：`DONE` 选择之后仍需要独立验证结果，DOM 读取器不覆盖 shadow root、iframe、canvas、文件上传和嵌套滚动。
- HN 上 89 分、14 条评论（id 49735979），讨论集中在"没有截图的前提下如何保证目标元素定位不漂移"。

**来源：** https://github.com/browser-use/jev-ultrafast

## 2. NandhaKishorM/laya — 33ms 出结果的多语言决策引擎，HN 1095 分

![[laya-vs-jev.png]]

**评分: 9.0/10 | 可操作性: 高 | 热度: HN 1095 分 / 270 评论；GitHub +467 stars/24h（趋势榜第 12），总 1.4k stars**

**是什么：**
Convai Innovations 做的非自回归"System 1 决策引擎"，不生成文本。对 `choice`（从候选项里选一个）、`score`（打有序分）、`noul`（无标签）三类问题，它在一次前向传播里直接返回完整概率分布，再配一个 router 按请求挑 checkpoint。三个权重都是纯 encoder：`laya` 基于 ModernBERT-large（421M，512 上下文），`laya-multilingual` 基于 mmBERT-base（322M，1024 上下文，覆盖 100+ 语言），`laya-typed-decisions` 面向类型化决策流程。训练用的是严格 proper scoring rule 下的强化学习（RLCD）。

**怎么用：**
```bash
pip install laya
```
```python
from laya import Router
router = Router(preload=True)
result = router.predict(state, questions)   # 一次前向，无 token 解码
```

**为什么重要：**
T4 上单问题延迟 39.5ms；批量 10 个问题时多语言版只要 72.3ms（7.2ms/条），吞吐 103–332 q/s。对照 TypeSafe Jev 实测的 p50 236–276ms，快 6–7 倍。在 2,000 条 typed-decisions 上，微调后的 checkpoint 准确率 0.766，对上 Jev 公布的 0.727；温度重标定后 ECE 从 0.466 压到 0.081（Jev 为 0.246）。短板也很清楚：Banking77 这种 77 类高基数场景只有 0.425，Jev 是 0.870；高基数选项集和 `score` 类问题是最弱的地方。

**讨论现场：**
- HN 1095 分主帖吵得最凶的地方在叙事层，不在技术层。@johnfn 说 Jev 这个名字"一眼就懂"，而作者当初的发布帖标题叫《用纯强化学习从对话中预测销售转化概率》，"Dropbox 不就是个用 curlftpfs 挂载的 ftp 账号吗"。
- @Oras 实测后的结论是"它只是喂了更多数据的 BERT"，不算突破；@fastball 反驳说约束解码依然会产出幻觉概率，而 Jev 给的是标定过的概率，还有大约一个数量级的价差。
- 也有人质疑作者的工作本身：@XTXinverseXTY 指其"从第一天就是泄漏的糊糊"，称结果变量被当成输入特征。

**来源：** https://github.com/NandhaKishorM/laya

## 3. trycua/cua — CUA-S1-FORMS：70 万参数、2.8MB 的填表决策模型

![[cua-s1-card.gif]]

**评分: 8.8/10 | 可操作性: 高 | 热度: GitHub 24.5k stars，单日 +383~859（多榜口径）；HN 66 分 / 7 评论**

**是什么：**
Cua（YC S25）开源的 CUA-S1 模型家族第一个成员，定位是给 computer-use 场景做"System 1"决策层。它是一个一次前向的选项打分器，不做文本生成：给它一个 UI 元素和一组候选动作（`FILL` / `CHECK` / `CLICK` / `SKIP`，候选来自上游文档抽取器给出的标签-值对），它返回每个选项的概率。元素之间并行独立打分，"先填字段、再勾选框、最后授权提交一次"的执行顺序由应用层代码控制。架构是字节级 embedding + 2 层、宽 128、4 头的 Transformer encoder，每个选项作为 query 对上下文做 attention。

**怎么用：**
```bash
git clone https://github.com/trycua/cua
cd cua/libs/cua-s1        # 模型代码、合成数据生成、训练与评估都在这里（MIT）
```
权重和数据集分开托管：
```python
from huggingface_hub import hf_hub_download
hf_hub_download("cua-ai/cua-s1-forms", "cua-s1-forms.safetensors", local_dir="./ckpt")
hf_hub_download("cua-ai/cua-s1-forms", "cua-s1-forms.json",        local_dir="./ckpt")
# 加载器会校验格式、版本和 tensor 签名；出于安全设计拒绝 pickle 格式的 .pt/.pth
```
完整的 snapshot → score → order → execute 循环见仓库里的 `cua_s1/planner.py`。macOS/Linux 上的驱动安装：`/bin/bash -c "$(curl -fsSL https://cua.ai/driver/install.sh)"`。

**为什么重要：**
706,048 个可训练参数，checkpoint 只有 2.8MB。合成测试集上 top-1 准确率 99.95%；在"3 张真实表单 + 3 份真实 PDF、196 个决策、零合成数据"的现场评估里 100%。打乱上下文的对照组掉到 37%，说明模型确实在读元素而不是在猜选项分布。对手是没有微调的直接调 Jev API：整体 99.7% vs 83.6%；"已经是填好的字段应当跳过"这一项是 100% vs 74%。本地打分 7–9ms，对照托管 Jev 单次调用 260–280ms（含网络延迟，不是端到端表单完成时间）。训练成本：10,000 个合成 episode、6 个 epoch、不到 30 分钟。

**讨论现场：**
- HN 上 @AM1010101 提出的方向被顶得最高：未来是不是"一大堆细分专家模型 + 一个父模型（本身可能也是专家）负责派活"，LLM 只下发大目标、触发一连串专家级联。
- 回帖 @ShakataGaNai 认为这就是"AI 的下一步"：少数又大又聪明的模型，配大多数又小又专用的模型——后者做起来快、跑起来便宜，而前沿模型已经贵到个人和多数企业都难以为普通工作量买单。
- @badatnames 半开玩笑地求一个"通用 cookie 同意弹窗关闭器"，@hbarka 则追问这跟 RLCD、RLHF 是什么关系——@adastra22 直言 TypeSafe 之外没人知道 RLCD 指什么。

**来源：** https://github.com/trycua/cua ｜ 权重：https://huggingface.co/cua-ai/cua-s1-forms

## 4. NVIDIA/SkillSpector — 装 skill 之前先扫一遍，26.1% 的技能带漏洞

**评分: 8.7/10 | 可操作性: 高 | 热度: 17.9k stars，1.5k forks，494 commits**

**是什么：**
NVIDIA 开源的 AI agent skill 安全扫描器，覆盖 Claude Code、Codex、Gemini CLI 和 MCP。两段式流水线：先做快速静态分析（正则、Python AST、YARA 特征、查 OSV.dev 的 CVE），再可选叠加 LLM 语义审查。它的信任模型是"绝不执行被扫描的 skill"——传 `--no-llm` 时内容完全不出本地（只有依赖名和版本会发给 OSV.dev）。扫描产出 0–100 的风险分和 `safe_to_install` 判定，是 NVIDIA Verified Skills 流水线（扫描 → 评估 → 签名 → 发布）的入口环节。

**怎么用：**
```bash
uv tool install git+https://github.com/NVIDIA/skillspector.git     # 纯 CLI
uv tool install 'skillspector[mcp] @ git+https://github.com/NVIDIA/skillspector.git'  # 带 MCP

skillspector scan ./my-skill/                  # 也可以扫 SKILL.md、Git URL 或 .zip
skillspector scan ./my-skill/ --no-llm         # 完全本地，内容不外发
skillspector scan ./my-skill/ --format sarif --output report.sarif   # 接 CI
skillspector baseline ./my-skill/ -o .skillspector-baseline.yaml     # 建基线后增量比对
claude mcp add skillspector -- skillspector mcp                       # 注册成 MCP server
```
退出码可直接当门禁：`0` 干净或低风险，`1` 风险分过 50 或有规则命中，`2` 出错。

**为什么重要：**
背后是论文《Agent Skills in the Wild: An Empirical Study of Security Vulnerabilities at Scale》（Liu et al., 2026）：从主流市场抓了 42,447 个 skill，实际分析了 31,132 个，其中 26.1% 至少含一个漏洞，5.2% 表现出明显恶意意图；带可执行脚本的 skill 出漏洞的概率是不带的 2.12 倍。检测规则共 71 条，横跨 17 个类别——prompt 注入 6 条、反拒答 3 条、数据外泄 4 条、提权 3 条、供应链 9 条、过度代理 5 条、MCP 工具投毒 4 条等。评分权重是 CRITICAL +50 / HIGH +25 / MEDIUM +10 / LOW +5，可执行脚本再乘 1.3。加上 LLM 语义审查后精确率约 87%。

**讨论现场：**
- 项目的信任声明写得比多数安全工具都干脆：`--no-llm` 下正文不离开本机，理由是"扫描一个可疑 skill 的扫描器本身不该成为新的外泄通道"。
- 报告里点名了 MCP 的两个高危面——最小权限缺失（4 条规则）和工具投毒（4 条规则），这两类在 31,132 个样本里贡献了相当大的比例。

**来源：** https://github.com/NVIDIA/skillspector

## 5. TianyuCodings/NanoJev — 用 Qwen3-0.6B 复刻 Jev，迷宫尝试次数只有 1/11

![[nanojev-maze.gif]]

**评分: 8.5/10 | 可操作性: 高 | 热度: GitHub +358 stars/24h（趋势榜第 18），总 942 stars**

**是什么：**
Jev 的"纳米复刻版"：0.6B 的并行决策模型，状态和问题进、完整概率分布出，零输出 token 解码。骨干是 Qwen3-0.6B 加三个决策头——Dynamic Choice（2–255 个候选，每个候选一个概率，共享标量头 + set attention）、Boolean（单路 sigmoid）、Ordered Score（2–10 级有序评分，返回概率加权期望）。一次前向可以同时处理多个状态/问题，带持久化 serving 和 GPU 上的批量运行。

**怎么用：**
```bash
git clone https://github.com/TianyuCodings/NanoJev.git
cd NanoJev
python -m pip install -r requirements-toy.txt      # CUDA 环境

# 起服务（权重从 HF 的 C-Tianyu/NanoJev 取，数据在 C-Tianyu/NanoJev-Data）
python scripts/serve_decisions.py \
  --checkpoint-dir checkpoints/NanoJev \
  --web-root web --port 8765
# 服务加载一次后持续收批量请求：POST /api/evaluate

# 看回放
python3 -m http.server 8080 --bind 127.0.0.1 --directory web
# 浏览器打开 side-by-side.html
```

**为什么重要：**
50×50 迷宫任务里，NanoJev 用了 244 次尝试、36 次碰撞走到终点；Jev 是 2,738 次尝试、1,044 次碰撞；没调过的 Qwen3-0.6B 是 4,726 次尝试、2,044 次碰撞。也就是说，一个 0.6B 的模型在这个任务上的尝试次数只有 Jev 的 1/11、原版 Qwen3 的 1/19。40 张地图导航（T=1 采样）上 4×4 测试集 19/20（95%）、6×6 分布外 18/20（90%），Jev 是 20/20 和 19/20，未调优的 Qwen3-0.6B 只有 7/20（35%）和 3/20（15%）。训练管线全开源：query 构建 → 同 split 分组关联 map/rule → 初始化 Qwen3-0.6B → 预热决策头 → 用完整问题分布损失训练 → 评估概率质量 → 跑游戏控制器 → 服务化与可视化。

**讨论现场：**
- README 强调训练目标不是分类准确率而是概率质量：CE/Brier 训练、成对 proper-reward 学习、梯度检查，成对 reward 那一支的分布误差到了 0.11844（测试）/ 0.06202（分布外）。
- 本地安全模型测试题准确率 77.84%，50×50 分布外 76.56%——作者把这两条也放进来了，没有只报最好看的数。

**来源：** https://github.com/TianyuCodings/NanoJev

## 6. latent-spaces/brag — 一条 `/brag`，把项目变成带音乐的发布视频

![[brag-hero.png]]

**评分: 8.3/10 | 可操作性: 高 | 热度: GitHub +821 stars/24h，连续第三天守住趋势榜第 5，总 5.8k stars**

**是什么：**
一个 Claude Code skill（也能被其他 agent 通过 symlink 或技能发现路径调用），把当前项目转成一段短的发布视频，连带配乐、动效和分享文案。分工是这样：`/brag` 负责叙事角度，决定讲什么故事、给谁讲；Hyperframes 拿到 brief 之后做构建、时轴和渲染。

# 其他 agent 走 skills CLI
npx skills add https://github.com/latent-spaces/brag --skill brag        # 加 -g 全局安装

产出在 `brag-output/`：计划、composition brief、分享文案，以及渲染好的 `brag.mp4`。前置要求 Node.js 22+、PATH 里有 FFmpeg、以及 Hyperframes CLI（`npx hyperframes doctor` 自检）。

**讨论现场：**
- 连续三天停在趋势榜第 5（+821/24h），热度来自一个很具体的痛点：项目做完了，宣传素材还得另外找人做。
- `--tone "fake Series A launch from 2016"` 这类参数说明它在文案层面的可玩性比渲染层面更受关注——目前 31 个 commit、MIT 协议。

## 7. arcboxlabs/arcbox — 从零用 Rust 写的容器/VM 运行时，给 agent 开微虚拟机沙箱

**评分: 8.2/10 | 可操作性: 中（macOS Apple Silicon） | 热度: GitHub +504 stars/24h（趋势榜第 9），总 5.8k stars**

**是什么：**
macOS 上的开源容器与虚拟机运行时，VMM、VirtIO 设备、文件系统共享、网络数据通路全是 Rust 从零写的，定位是 Docker Desktop 和 OrbStack 的开源替代。一个 daemon 加一个 CLI 管四类负载：Docker 兼容容器 + k3s Kubernetes、给 AI agent 和不可信代码用的一次性微虚拟机沙箱、完整 Linux 虚拟机、用完即弃的 macOS guest。目前 public beta。

**怎么用：**
```bash
brew install --cask arcboxlabs/tap/arcbox
# 或者
curl -fsSL https://get.arcbox.dev | bash

abctl daemon start
abctl docker enable
docker run -d -p 8080:80 nginx        # 只替换引擎，Docker CLI 照用

abctl sandbox create                   # 给 agent 开一个一次性微虚拟机
abctl claude                           # 直接进一个带 agent 的沙箱
abctl top                              # 看资源
abctl migrate from orbstack            # 迁移
```

**为什么重要：**
网络这块是自研用户态协议栈（DHCP、DNS 转发、NAT、连接跟踪、用户态 TCP），明确不用 `pf` NAT 也不用 `utun` 设备。实测单流 host→VM 吞吐 22.7 Gbps，大约是同样测试下 Apple VirtIO-net 的两倍；多流上限 10–12 Gbps。沙箱是嵌在 guest 里的 Firecracker 启的微虚拟机，仓库简介宣传"<100ms 启动"，README 里给的目标是冷启动 <1.5s、热启动 <500ms，对照 OrbStack 的约 2s 和 <1s——上线前这两个数的差距需要留意。需要 root 的操作走代码签名对端认证的特权 helper，daemon 本身不以 root 运行。双协议 MIT OR Apache-2.0。

**讨论现场：**
- 平台限制写得比宣传语诚实：macOS on Apple Silicon（Intel 支持开发中），沙箱和 `abctl claude` 需要 M3 及以上 + macOS 15+，macOS guest 最多 2 个且数据目录必须在 APFS 上。
- 集群注册等功能标着 "In development"，`abctl migrate from docker-desktop` 也在同一批里。

**来源：** https://github.com/arcboxlabs/arcbox

## 8. deeplethe/utopia — 一个 Rust 二进制 + 一个 Postgres 的企业知识图谱

![[utopia-banner.webp]]

**评分: 8.0/10 | 可操作性: 中 | 热度: GitHub +880 stars/24h（趋势榜第 4，停榜三天后回归），总 9.1k stars**

**是什么：**
DeepLethe 做的企业知识系统，核心是一张"双时态"知识图谱——每条事实同时带两个时间：它什么时候为真，以及系统什么时候学到它。定位是和 Palantir 不同的另一条路：从知识治理自底向上搭，可以完全离线、气隙环境跑在公司自己控制的硬件上。
架构被概括成"一个 Rust 二进制加一个 Postgres"。全文检索在二进制内跑（Tantivy），向量走 pgvector，任务队列就是一张表，不额外起服务。任何 OpenAI 兼容端点（DeepSeek、Qwen、GLM、Ollama、vLLM）都能接。

**怎么用：**
```bash
git clone https://github.com/deeplethe/utopia.git
cd utopia
docker compose --profile app up -d
# 打开 http://localhost:1516 注册，第一个账号自动成为管理员
# 模型端点在 Administration → Models 里配
```
从源码构建：`docker compose -f docker-compose.yml -f docker-compose.build.yml --profile app up -d --build`。本地开发：`docker compose up -d db`，然后 `cargo run -p utopia-server`（后端 :1516）+ `cd web && pnpm install && pnpm dev`（前端 :5173）。

**为什么重要：**
本体（ontology）在这里是有实际作用的：本体公理会被编译成规则（传递性、对称性、逆关系、关系层级）并前向链推出新事实——推导默认关闭，且推导出的事实和已断言的事实冲突时，以断言为准。内置五个词表（schema.org、W3C Org、PROV-O、FOAF、IOF Core），遇到不认识的词先计数，确认后才提升。查询侧可以把 Postgres/MySQL/Trino（Iceberg/Delta/Hive）/Databricks/Snowflake 挂上来，由 agent 提出"表到本体"的映射候选、人工确认，走 Ontology2SQL。每个知识库都可以起一个 MCP server，给 Claude Desktop、Cursor、Workbuddy 这类框架接，带细粒度权限，同一批只读工具也通过 MCP 暴露。

**讨论现场：**
- 状态标注很克制：版本 v0.1，schema 迁移只向前不向后——官方建议锁住 `UTOPIA_IMAGE` 并在升级前备份。
- Roadmap 上还没做的是"执行门"：用本体规则和符号逻辑去校验 agent 的每一次调用，以及基于实体事实的决策推理和业务规则。当前 agent 能查、能走图、能查挂载的库，但还不能被本体约束住。

**来源：** https://github.com/deeplethe/utopia

代码仍在准备发布，仓库目前只有论文 PDF、项目主页和 BibTeX。发布计划表里，论文和项目页可用，arXiv 在投，发现的程序、完整代码库和复现脚本都还在准备。先看项目主页和论文：
