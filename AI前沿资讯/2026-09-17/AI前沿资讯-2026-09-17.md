## 1. cloudflare/security-audit-skill — Cloudflare 官方开源六阶段安全审计 skill，单日 1,249 星

**评分: 9.2/10 | 可操作性: 高 | 热度: GitHub Trending 当日 +1,249 stars（另一快照 +927），总星 7.4k，429 forks**

**是什么：**
Cloudflare 把内部漏洞挖掘流水线做成了一个编码 agent 技能。它把审计拆成六个阶段：侦察（产出 `architecture.md` 和 `coverage-ledger.json`）→ 按覆盖账本派发隔离 hunter → 每个候选漏洞交给全新 verifier 尝试证伪 → 输出结构化 `findings.json` → 独立 agent 复核记录来源 → 生成目标中立的报告。核心设计是"检查者永远不是发现者"：任何候选都要由没参与发现的 agent 独立验证才能升级为 `confirmed`。仓库只有 22 个文件、143 KB，58.9% 是 markdown。

**怎么用：**
```bash
# 装到当前项目的 agent 里
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit

# 或者装成用户级（所有项目可用）
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit \
  --global

# 然后在 agent 里直接说
#   security audit this codebase
#   find security vulnerabilities in ./src
#   do a security review, output to ~/audits/my-project
```
需要 Node.js 跑两个零依赖校验器（`validate-coverage-ledger.cjs`、`validate-findings.cjs`）。要真正执行目标代码（编译、跑测试、起浏览器）还需要 OS 级沙箱，否则线索只会停在 `needs_validation` 状态。

**为什么重要：**
同类 agent 安全审计工具通常只给一份报告，问题是你没法判断哪条是真漏洞。Cloudflare 这个用三态判定把不确定性显式化了：`confirmed` 要求完整来源追踪和可观测结果，`needs_validation` 必须挂一个未解决的具体事实且不给严重等级，`rejected` 记录被证伪的候选。仓库自己公布的一个数据点很关键：单次运行大约只能找到重复运行总漏洞数的一半，所以它设计了增量模式，对同一仓库反复审计会继承之前的账本和结论，不把过期工作算作已覆盖。

如果今天只挑一条动手试，我会选它：装上一个 skill 的成本是几分钟，换来的是一条可复现、能增量跑的审计流程。

**讨论现场：**
- 仓库设计原则原文："Adversarial validation."，checker is never the finder；"Severity requires impact."，严重等级取"可能性 × 影响"，不看检查清单偏离项；纵深防御缺口只记为加固建议，不算漏洞。
- 这批技能过去一周连续霸榜 GitHub，社区把它和 anthropics/skills、addyosmani/agent-skills 归为同一波"agent skills 变成 agent 应用层"的浪潮：技能正在取代 prompt 成为分发单元。

**来源：** https://github.com/cloudflare/security-audit-skill

## 2. Tencent/WeKnora — 腾讯开源的 LLM 知识平台，单日 +1,201 星

![[weknora-demo-1.png]]

![[weknora-demo-2.png]]

**评分: 8.9/10 | 可操作性: 高 | 热度: GitHub Trending +1,201 stars/day，总星 25.4k，3.5k forks，3,037 commits**

**是什么：**
WeKnora 把企业文档处理的三件事合到一个栈里：可查询的 RAG、自主推理的 ReAct Agent、agent 自己维护的 Wiki。Wiki 模式会生成互相链接的 markdown 页面并附带知识图谱，还有跨会话长期记忆、树状目录、带修订历史的 chunk 编辑。v0.8.0 支持 13 种文档格式、20+ 家 LLM 供应商（OpenAI / Anthropic / DeepSeek / Qwen / 智谱 / 混元 / Ollama 等）、8 种向量库、10 个 IM 渠道。

**怎么用：**
```bash
git clone https://github.com/Tencent/WeKnora.git
cd WeKnora
cp .env.example .env   # 按需改配置
docker compose pull
docker compose up -d

# Web UI     http://localhost
# 后端 API    http://localhost:8080
# Langfuse   http://localhost:3000

# 可选 profile：full / neo4j / minio / langfuse，可叠加
docker compose --profile full --profile neo4j up -d
```
它还带一个 agent-first 的 CLI（默认输出 JSON）和一个 MCP server：
```bash
# CLI
weknora profile add prod --host https://kb.example.com --use
weknora auth login
weknora kb list
weknora link --kb my-knowledge-base    # 把当前目录绑上去
weknora doc upload notes.md
weknora chat "summarise the design doc"

# MCP server：29 个工具，支持 stdio / SSE / HTTP
pip install tencent-weknora-mcp
```

**为什么重要：**
企业 RAG 的常见失败模式是"文档灌进去就烂在那里"，索引不更新、chunk 改不了、没人知道检索到了什么。WeKnora 的 Wiki 模式让 agent 反过来维护知识本身，v0.5.2 起可扩展到 4 万篇文档的知识库，chunk 编辑带修订历史意味着知识库可以被人工纠偏，不必只能重建。安全侧做了 AES-256-GCM 静态加密、应用与 docreader 之间的 gRPC TLS、SSRF 防护客户端、OIDC JWKS 校验，RBAC 是 Owner / Admin / Contributor / Viewer 四级矩阵并带工作区审计日志。这套东西是给要过合规的企业场景准备的，不是 demo。

**讨论现场：**
- 仓库本周从 Trending #17 一路爬到 #5，是腾讯系项目里增长最快的开源 AI 仓库之一。
- 迭代节奏说明问题：3,037 次提交、约 50 页文档覆盖 360 个 API 端点和 150 个环境变量。这是长期维护的产品线，不是一次性开源。

**来源：** https://github.com/Tencent/WeKnora

## 3. qorl — 4B 模型生成比 Postgres 默认快 81% 的查询计划，HN 408 分

![[qorl-demo.png]]

**评分: 8.8/10 | 可操作性: 中 | 热度: HN 首页 408 points / 84 comments，代码全开源**

**是什么：**
有人做了个实验：一个 4B 的开源权重模型，能不能通过 SFT + agentic RL 学会给 Postgres 打 `pg_hint_plan` hint，从而产出比默认 planner 更好的执行计划。答案是能。基底是 `empero-ai/Qwen3.8-4B-Distill`（Empero 把 Qwen 3.8 2.4T 教师蒸馏进 Qwen 3.5 4B），4.66B 可训练参数，训练方式是先对 GPT-6 Astra 的轨迹做 off-policy 蒸馏，再跑 agentic RL。agent harness 叫 `qo-agent`，带六个工具：`inspect_relation`、`get_column_stats`、`get_plan`、`evaluate_candidate`、`keep_default`、`finish`。

**怎么用：**
```bash
git clone https://github.com/polyphilz/qorl
# 项目全部代码在该仓库；作者原实验在 4 个 Postgres 容器
# （每个 4 核 8GB，shared_buffers=2GB，work_mem=4MB）上跑评测
```
模型推理侧用 vLLM，训练在租来的 2x H100 SXM 节点上完成。评估用的是标准执行时间查询：
```sql
EXPLAIN (ANALYZE, TIMING OFF, BUFFERS, FORMAT JSON) <query>;
```

**为什么重要：**
这条新闻里最硬的数字是成本：总共 **$1,200**（H100 节点约 95 小时约 $800，OpenAI API 教师轨迹约 $400），换来的是在 JOB 的 113 条 join-heavy 查询上 **1.81x 加速 / 44.7% 延迟下降**（best-of-15 选择，0 次回归）。对比同样是 best-of-5 的前沿模型：Astra 是 2.54x，Qwen 3.8 2.4T 是 2.26x。4B 模型没赢，但用不到两千美元追平了"能打"这条线。RL 阶段的进步曲线很清楚：SFT 起点 1.16x → 600 步 1.35x（113/113 全部有效，0 回归）→ 1,200 步 1.41x。

我的判断是这条的价值不在 81% 这个数字，而在于它把"训一个专用 planner 要花多少钱"这个问题第一次摆到了 $1,200 这个量级上。

**讨论现场：**
- **perrygeo** 指出评测口径问题："they must improve the combined time - planning + query - based on live database statistics"。规划时间不能被忽略，而原文用的是执行时间指标。
- **Sesse__** 提出落地难点："The immediate problem: How do you know which one is better without running them?"，不知道哪个计划更好就只能先跑一遍，那省下的时间又被吃回去了。
- **refibrillator** 质疑数据规模："on an 8 GB dataset that fits entirely in memory, with shared_buffers constrained to a fraction of that"，全内存数据集对 planner 的考验和真实生产不是一回事。
- **dragontamer** 抛了个反直觉方案："At a certain point we should seriously talk about CUDA accelerating Postgres instead."
- 也有读者 **sgarland** 指出 schema 除主键外没有任何索引、没有额外统计信息，这会放大 planner 的改进空间。

**来源：** https://rohanbansal.com/qorl ｜ 代码：https://github.com/polyphilz/qorl

## 5. multimodal-art-projection/YuE2 — 开源音乐生成追平 Suno，零样本翻唱 CLEWS 从 0.006 到 0.647

![[yue2-demo-1.png]]

**评分: 8.3/10 | 可操作性: 中 | 热度: GitHub Trending +370 stars/day，总星 9.4k，1.0k forks**

**是什么：**
YuE2 把符号音乐生成和音频生成统一到一个模型里。给歌词和风格 prompt，它先写出旋律与和弦的符号计划（人类和 agent 都能读、能改），再把这份计划实现成带人声和伴奏的完整歌曲。架构是 AR-NAR 的 Mixture-of-Transformers 主干：自回归预测乐谱和语义 token，再用 flow matching 生成声学 latent，最后 VAE 解码成立体声。配套放出了两个模型：MERT2（15 项 MARBLE 指标里 14 项 SOTA，GTZAN 流派准确率 91.72%）和 SheetSage2（13 项基准里 10 项 SOTA，RWC-Pop 人声旋律音级 F1 82.51%）。

**怎么用：**
```bash
git clone https://github.com/multimodal-art-projection/YuE.git
cd YuE
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install .
python examples/generate.py --output outputs/first-song
```
Python 侧的分阶段 API，cover 流程演示：
```python
from pathlib import Path
from yue2 import YuE2Pipeline

with YuE2Pipeline.from_pretrained("m-a-p/YuE2-3B", device="cuda") as pipe:
    cover = pipe(
        style="English, jazz-funk, warm lead vocal, Rhodes, bass and drums",
        lyrics=Path("cover-lyrics.txt").read_text(encoding="utf-8"),
        abc=Path("cover-score/score.abc").read_text(encoding="utf-8"),
        cot="melody",   # 旋律计划 + 自由伴奏，翻唱推荐
        seed=42,
    )
    cover.save_artifacts("outputs/cover")
```
环境要求 **Linux + Python 3.12 + 支持 BF16 的 NVIDIA GPU，24GB 显存**，输出 48kHz 立体声无量化。`cot="full"` 出可编辑的旋律和弦计划（新歌默认），`cot="melody"` 用旋律计划配自由伴奏，`cot="off"` 直接从歌词和风格生成。

**为什么重要：**
WildSongBench（192 个 prompt，自动评测，2026-09-12）上 YuE2 的 SongBench 均值 **6.9632**，Suno v5 是 6.8721、Suno v5.5 是 6.7150、Suno v6 是 6.5562、上一代 YuE v1 只有 4.9165。翻唱能力是数量级差别：948 首作品的零样本翻唱 CLEWS mAP 拿到 **0.647**，不给乐谱时只有 0.006。也就是说"给一段旋律计划"这个符号通道，是翻唱能力从无到有的开关。代码和 agent skill 是 Apache 2.0，权重 CC BY-NC 4.0。个人创作者可以无版税商用，公司要商用得单独谈。

**讨论现场：**
- 仓库自己标注了诚实边界："the small gap between the highest means does not establish statistical significance"，6.9632 对 Suno v5 的 6.8721 领先幅度不足以宣称统计显著，这一点比营销口径可信。
- 同时放出了公开听测擂台（Music Arena）和 demo 站点，让用户自己听，不必只看自动指标。

**来源：** https://github.com/multimodal-art-projection/YuE ｜ Demo：https://map-yue2.github.io/ ｜ 权重：https://huggingface.co/m-a-p/YuE2-3B

## 6. anthropics/knowledge-work-plugins — Anthropic 官方开源 11 个职能插件，纯 markdown 无构建

**评分: 8.0/10 | 可操作性: 高 | 热度: GitHub Trending +110 stars/day，总星 24.3k，2.9k forks，977 commits**

**是什么：**
Anthropic 把面向知识工作者的 11 个插件开源了：productivity、sales、customer-support、product-management、marketing、legal、finance、data、enterprise-search、bio-research、cowork-plugin-management。每个插件是一包技能 + 连接器 + 斜杠命令 + 子 agent，全部是 markdown 和 JSON 文件，没有代码、没有基础设施、没有构建步骤。为 Claude Cowork 设计，也兼容 Claude Code，Apache-2.0。

**怎么用：**
```bash
# Claude Code 先加 marketplace
claude plugin marketplace add anthropics/knowledge-work-plugins

# 再装具体插件
claude plugin install sales@knowledge-work-plugins
```
装完自动激活，技能按情境触发，斜杠命令直接可用，比如 `/sales:call-prep`、`/data:write-query`、`/finance:reconciliation`、`/product-management:write-spec`。Cowork 用户从 claude.com/plugins 装。

自定义的入口也全部是文件：
```text
plugin-name/
├── .claude-plugin/plugin.json   # 清单
├── .mcp.json                    # 工具连接
├── commands/                    # 你显式调用的斜杠命令
└── skills/                      # Claude 自动取用的领域知识
```
换连接器就改 `.mcp.json`，加公司上下文就往 skill 文件里写术语、组织架构、流程。

**为什么重要：**
这批准官方插件的价值在于把"接内部系统"这件事的接口面收窄了。finance 插件预接了 Snowflake、Databricks、BigQuery，legal 接了 Box、Egnyte，bio-research 接了 PubMed、bioRxiv、ClinicalTrials.gov、ChEMBL。这份连接器清单本身就是一份"企业数据源该怎么暴露给 agent"的参考答案。11 个插件覆盖的角色几乎包含了所有非工程岗，配合上周 Anthropic 公布的 Small Business 扩展（43 个工作流 + 27 个集成），路线就清楚了：先把每个职能的 agent 工作流标准化成可分发文件，再让企业自己改。

**讨论现场：**
- 24.3k 星 / 977 commits 但只有 68 个 issue、11 个 PR。绝大多数人是直接拿来改，不提问题，典型的"模板仓库"使用模式。
- 仓库结构本身在传递一个观点：企业 agent 落地不需要写代码，需要的是把领域知识写成文件，这也解释了为什么这批插件里 `cowork-plugin-management` 自己也是一个插件。

## 7. OpenSpec — 规格驱动开发框架，68.6k 星，HN 72 分

![[openspec-demo.png]]

**评分: 7.8/10 | 可操作性: 高 | 热度: HN 首页 72 points / 26 comments，总星 68.6k，4.7k forks，支持 30+ AI 工具**

**是什么：**
OpenSpec 在编码 agent 和代码之间插了一层规格。每个变更单独一个文件夹，里面放 proposal、specs、design、tasks 四份文档；AI 写纯 markdown 的规格（用 WHEN/THEN 描述需求场景），你先审计划再让它写代码。它自称"fluid not rigid"，迭代式而非瀑布式，同时支持棕地和绿地项目。最新在 beta 的 Stores 功能允许把规格放在独立仓库里，用 git 跨团队共享。

**怎么用：**
```bash
# 需要 Node.js 20.19.0+
npm install -g @fission-ai/openspec@latest

cd your-project
openspec init
```
默认工作流的四个命令：
```text
/opsx:explore          动手前先当思考伙伴
/opsx:propose <idea>   主命令
/opsx:apply
/opsx:archive

# 扩展档（openspec config profile / openspec update 切换）

```

## 8. TranslateGemma — Google 开源翻译模型，55 种语言可离线跑

![[translategemma-demo.png]]

**评分: 7.6/10 | 可操作性: 高 | 热度: Google 官方发布（9/16），Hugging Face 上月下载 9,628、341 likes，社区已出 Ollama / ComfyUI 集成**

**是什么：**
Google 放出了 TranslateGemma，一个基于 Gemma 3 架构、专门为翻译任务微调的开放权重模型家族，支持 55 种语言两两互译，可以完全离线运行。三个规格对应三档硬件：**4B**（移动端/边缘，量化后约 2.5GB）、**12B**（消费级笔记本，约 7GB）、**27B**（最高保真，约 16GB，单张 H100 或 TPU 可跑）。除文本外还支持图片内文字翻译。Google 同时说明其语言技术整体覆盖已经超过 300 种语言、约 86% 的世界人口。

**怎么用：**
权重在 Hugging Face 和 Kaggle Models 上，走 Gemma Terms 门控许可（需要登录接受条款）。本地跑最省事的是 Ollama：
```bash
# 社区已把这套模型接进 Ollama，完全本地推理
ollama run translategemma
```
官方侧也可以直接用 transformers：
```python
from transformers import AutoProcessor, AutoModelForImageTextToText

model_id = "google/translategemma-12b-it"
processor = AutoProcessor.from_pretrained(model_id)
model = AutoModelForImageTextToText.from_pretrained(model_id)
```
Vertex AI Model Garden 提供托管部署路径，Android/LiteRT-LM 有量化包（`barakplasma/translategemma-4b-it-android-task-quantized`），ComfyUI 有对应节点。

**为什么重要：**
开放权重的翻译模型此前基本是 NLLB / MADLAD 那一代，质量和前沿差一截。TranslateGemma 走的是"从 Gemini 蒸馏 + Gemma 3 架构"这条路，把翻译质量拉到了能用水平，代价是**上下文只有 2,000 token**，长文档必须分段，这是选型时要先确认的限制。另外它只是模型不是产品：本地部署意味着访问控制、安全策略、运维责任全部转移给部署方，官方也建议重要内容仍需人工复核。第三方发布的基准里，图片翻译只测了单文本图，复杂版式和手写体没有覆盖。

**讨论现场：**
- 发布后一周内生态反应很快：第三方 Web UI（`realies/translategemma-ui`，走 Ollama 完全本地）、ComfyUI 节点、Android 量化包都出来了，说明上手门槛确实低。
- 一处落空：Google 提到训练中用过近 500 组额外语言对，发布时却没给出这些语言对的评测指标，55 种之外的语种质量目前没有数据支撑。

## 10. BITCOS — 打破三值 LLM 的 1.58-bit 下限，29 个模型里 26 个变密，HN 146 分

**评分: 7.2/10 | 可操作性: 低 | 热度: HN 首页 146 points / 19 comments，arXiv 2609.16338**

**是什么：**
三值模型通常声称达到信息论下限 log₂3 ≈ 1.585 bits/权重，但实际部署格式是"每字节塞 5 个 trit"，等效 1.625 bits——这个数字建立在"三个符号等概率"的假设上。Intel 的 Evangelos Georganas、Alexander Heinecke、Pradeep Dubey 检查了 29 个三值模型，发现零权重的占比远高于该假设，最高达 **51.5%**。他们提出 BITCOS：用一个稠密的存在位图加一个紧凑的符号向量来编码，成本是 2 − z bits/权重，z 为零密度。

**怎么用：**
论文（arXiv:2609.16338），配套给出了针对 AVX-512、AVX2 和 Intel Xe2 GPU 调优的解包例程。目前**没有公布代码仓库**，要复现得自己按论文实现位图打包和解包。
```bash
# 论文
https://arxiv.org/abs/2609.16338
```

**为什么重要：**
在 29 个模型中有 26 个 BITCOS 比"每字节 5 trit"更密，最稀疏的那个达到 **1.485 bits/权重**。性能上，对抗生产级三值矩阵向量内核，在实际零密度下最高 **1.28x** 提升；端到端推理在 5 个平台（客户端/服务器 CPU、集成与独立 Xe2 GPU）上，CPU 解码吞吐最高 1.18x、GPU 最高 1.27x。意义在端侧：三值模型每个权重只有加、减、空操作三种，本来就对 CPU 和 ASIC 友好，把存储再压 10% 左右直接换算成同内存下能装更大的模型。

**讨论现场：**
- **infogulch** 顺着思路往前推了一步："get down from 1.58 to 1.48 bits per weight by exploiting the fact that actual weights in practice are 0 51% of the time"，利用零稀疏性继续压。
- **janalsncm** 点出三值模型的本质优势："In a ternary LLM every weight is an add, subtract, or no-op so it is fast on CPU."，没有乘法器才是端侧友好的根源。
- **yalok** 给出应用方向："sounds like a perfect fit for ASIC-optimized models ... achieving record power efficiency for on-device inference"。
- **om8** 反对路线："Ternary quantization does not make any sense. Vector quantization and trellis based methods are better in this region"，认为在同等比特率下向量量化和 trellis 更优。
- **Vetch** 补了训练侧背景："QAT, which bitnet training is a form of, helps a ton in preserving accuracy at such low bits per parameter."
- 注意：论文本身没有报告精度数据，全篇聚焦存储位宽和吞吐，判断能否上线还需要精度侧的独立验证。

**来源：** https://arxiv.org/abs/2609.16338
