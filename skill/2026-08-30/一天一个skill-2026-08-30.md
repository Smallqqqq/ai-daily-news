# playwright-skill — 让 AI 写代码操作浏览器，而不是让浏览器操作 AI

  你让 Claude Code "测一下注册流程通不通"。它调起 playwright-mcp，打开页面、点一下、抓一页 accessibility tree、再点一下、再抓一页——一个三分钟的表单测试还没做完，上下文已经被一页页快照吃掉了大半，回答开始变慢变贵。lackeyjb/playwright-skill 换了一条路：agent 直接把 Playwright 代码写出来，执行器跑完只回截图和 console 输出。3056 stars，MIT 协议，189 分的 HN 讨论帖，一条命令装完。

### 它解决什么问题

  playwright-mcp 的设计面向逐步交互：每执行一个动作，就把当前页面的 accessibility tree 送回模型，让模型"看着"页面决定下一步。这套机制对探索式浏览合理，代价是上下文——微软官方仓库 issue #889 讨论的就是它吃 token 的问题。动作一多，窗口很快被历史快照塞满，模型开始退化。

  这个 skill 把交互模型倒过来。用户描述要测什么，agent 一次性写出完整的 Playwright 脚本，本地执行器跑完，回传三样东西：执行结果、截图、console 输出。中间过程不进上下文。作者在 HN 上给的对比很直白：314 行指令文件对抗一个常驻 MCP 服务器，完整 API 文档只在需要时才加载。HN 用户 yomismoaqui 的实际体验是：playwright-mcp 截全页截图失败，换这个 skill 让 Claude 写原生 JS，一次通过。

  另一个容易被忽略的收益：脚本是完整产物。MCP 的逐步操作用完即弃，skill 产出的是一段能存下来、能改、能重跑的 Playwright 代码。测试做完，脚本还在。

### 核心原理

  机制分三层，全部落在本地：

  **第一层，指令精简（progressive disclosure）**。SKILL.md 只有几百行，写清"什么时候用、怎么组织代码、怎么跑"。完整的 Playwright API 参考放在 `API_REFERENCE.md` 里，覆盖选择器、网络拦截、认证、移动模拟、性能测试等专题，只有任务真正需要时才加载进上下文。常驻加载的只有操作手册，不是整套 API 文档。

  **第二层，通用执行器 run.js**。agent 生成两种形态的代码：临时脚本（写进临时目录）和内联脚本（直接传给执行器）。run.js 负责一件事——稳定的模块解析。Playwright 装在技能目录的 node_modules 里，不管脚本在哪，`require('playwright')` 都能解析到，避免"本地能跑、技能目录下报 Module not found"这类环境问题。

  **第三层，安全清理与辅助函数**。临时文件用完即删，清理逻辑避开了脚本还在运行时被删的竞态；`lib/helpers.js` 提供一批可选工具函数处理常见重复劳动。截图默认存系统临时目录，`PW_ARTIFACT_DIR` 环境变量可以改到别处。

  默认配置值得注意：浏览器可见（`headless: false`），你能亲眼看着自动化跑；慢动作 `SLOW_MO` 默认 0ms，想观察细节再开。

### 安装配置

  推荐 Vercel 的 skills CLI，一条命令全局安装：

```bash
# 全局安装（所有项目可用）
npx skills add lackeyjb/playwright-skill --skill playwright-skill --global --yes

# 装完后进入技能目录跑一次 setup（装 Playwright + Chromium）
cd ~/.claude/skills/playwright-skill
npm run setup
```

  或走 Claude Code 插件市场（自动更新、团队分发）：

```bash
/plugin marketplace add lackeyjb/playwright-skill
/plugin install playwright-skill@playwright-skill
cd ~/.claude/plugins/marketplaces/playwright-skill/skills/playwright-skill
npm run setup
```

  装完用 `/help` 确认技能已加载，然后说一句"Test if google.com loads"验证。依赖只有 Node.js；Chromium 由 setup 脚本下载。

### 使用指南

#### 场景一：本地页面冒烟测试

  开发服务器跑着，改完一个页面想快速验证。直接说"测试首页""检查联系表单能不能用""验证注册流程"。agent 会先探测本地 dev server（不需要你手动告诉它端口），然后写脚本、开浏览器、跑完回传截图和 console 输出。适合每次提 PR 前花三十秒过一遍核心路径。

#### 场景二：多视口截图与响应式检查

  移动端适配是最容易漏的。说"截 dashboard 在手机和桌面两种尺寸下的截图"或"测不同 viewport 下的响应式布局"，agent 写脚本遍历你指定的视口列表，产出一组截图对比。比手动开 DevTools 切设备快得多，截图还能贴进 PR 描述。

#### 场景三：生成可以进 CI 的 E2E 脚本

  这是 HN 用户 cadamsdotcom 给的用法，也是这个 skill 和 MCP 最本质的分野：让 agent 写出脚本后，把脚本存进代码库。今天它在本地替你验证，明天它就是 CI 里的回归测试。一开始写个登录流程，之后每次让 agent 补一段新的用户路径，E2E 套件像滚雪球一样长大。脚本是普通 Playwright 代码，CI 里照常跑，不依赖任何 agent 运行时。

### 进阶技巧

  **网络拦截与调试**。需要验证"接口挂了页面显示什么"时，让 agent 写 `page.route` 拦截特定请求返回 mock 数据，或者延迟响应模拟慢网。API_REFERENCE.md 里有完整的网络拦截专题，agent 按需加载。调试卡住时开 `SLOW_MO` 慢动作，或者让脚本在关键步骤截图留档。

  **固定产物目录**。默认截图进系统临时目录，用 `PW_ARTIFACT_DIR=/path/to/artifacts` 把截图归到项目目录下，方便归档和对比多次运行结果。

### 常见踩坑

  **别在敏感数据上跑它**。console 输出和页面内容会作为上下文发给模型厂商（作者在 HN 上明确提醒过：截图留在本地 /tmp，但 console 和页面内容会出去）。生产数据、真实用户账号都别用，dev 环境和假数据是它的主场。

  **长链路自动化别指望一次跑通**。多位 HN 用户提到 LLM 写浏览器自动化时容易陷入"死亡螺旋"：定位元素失败、改脚本、再失败。简单表单、点击路径没问题，跨多个页面状态跳转的长流程（尤其是 OAuth 授权、日期选择器、跨域 iframe）会明显吃力。作者的定位也很清楚：它是本地"可脚本化的手动测试"工具，不是 CI 级或自主浏览 agent。

  **run.js 会执行 agent 生成的任意 Node 代码**。HN 上 AftHurrahWinch 指出这一点：生成代码直接本地执行，是一个命令注入面。个人开发机上问题不大，但在共享环境或公司机器上跑之前想清楚。这也是它和 MCP 工具白名单模式的差别。

### 同类技能对比

| 技能 | 安装方式 | 核心特点 | 适用场景 | 热度 |
|------|---------|---------|---------|------|
| **playwright-skill**（今日推荐）| `npx skills add` | code-first：写完整脚本执行，产物可留存 | 测试、截图、生成 E2E 脚本 | ⭐ 3.1K |
| playwright-mcp | `npx @playwright/mcp@latest` | 逐步操作 + a11y 快照回传 | 探索式浏览、逐页调试 | ⭐ 微软官方 |
| @playwright/cli | `npm i -g @playwright/cli` | CLI 命令式，token 高效 | 交互式浏览会话 | ⭐ 微软官方 |
| agent-browser | `npm i -g agent-browser` | Rust 原生 CLI + 守护进程 | 多 agent 通用浏览器控制 | ⭐ 41K |

  三个方案微软官方自己也有区分：CLI 适合交互浏览，MCP 适合需要持久状态和迭代推理的场景，skill 适合"自动化代码本身是有用产物"的场景。如果你的目标是要一段能存进仓库、能上 CI 的脚本，选 skill；如果是在页面上东点西点找线索，MCP 的逐步反馈仍然值得它的 token 开销。
