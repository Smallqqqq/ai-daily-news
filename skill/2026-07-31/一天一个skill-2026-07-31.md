# KubeShark — AI 写的 K8s 配置，它来把关

  你用 Claude Code 写了个 Deployment。它跑起来了，一切正常。三个月后你发现：securityContext 是空的、resource limits 没设、readinessProbe 指向了一个不存在的端口、RBAC 用了 `*` 通配符、apiVersion 是已经在 1.22 废弃的 `extensions/v1beta1`。你的集群没炸，只是因为还没被攻击、还没遇到流量洪峰、还没升级到 1.31。

  LLM 写 Kubernetes 配置有一个系统性问题：**它能写"看起来对"的 YAML，但它不知道什么会出问题。** KubeShark 填的就是这个坑。325 stars，MIT 协议，专为 Claude Code 和 Codex 设计的 Kubernetes 技能——一条命令安装，装上之后 AI 不再凭空捏造 K8s 配置，而是按 6 大故障模式逐一诊断后才动笔。

---

### 它解决什么问题

  LLM 在处理 Kubernetes 时有六类"系统性幻觉"——不是偶尔犯错，而是模型默认行为倾向于跳过安全检查：

  1. **不安全的工作负载默认值**。不设 securityContext，容器以 root 跑；不加 capabilities drop，攻击面全开。
  2. **资源饥饿**。不设 requests/limits，一个 Pod 吃光节点；不加 PDB，滚动更新时服务全挂。
  3. **网络暴露**。Service 用错了 selector，流量去了错误的后端；NetworkPolicy 拼错了标签，策略形同虚设。
  4. **权限蔓延**。RBAC 用 `*` 通配符；ServiceAccount 挂载了不该挂的 Secret。
  5. **脆弱发布**。用了 `latest` 标签、没设探针、updateStrategy 是默认值。
  6. **API 漂移**。生成了已废弃的 apiVersion（训练数据里大量 pre-1.22 内容），kubectl apply 直接报错。

  这六类问题有一个共同点：**Kubernetes 不会在 apply 时报错**。配置被接受了，故障在运行时才暴露。KubeShark 的核心设计就是：**让 AI 在写 YAML 之前，先走一遍诊断流程。**

### 核心原理

  KubeShark 不是一个"Kubernetes 参考手册"。它的架构基于一个关键洞察：**AI 不需要再读一遍 Kubernetes 文档，它需要的是一个"故障模式检查清单"。**

  它的 `SKILL.md` 是一个紧凑的操作工作流（约 650 token 激活成本），强制 Claude Code 走七步流程：

  1. **捕获上下文** — 集群版本、目标平台（EKS/GKE/AKS/OpenShift）、现有配置
  2. **诊断故障模式** — 匹配六大故障模式中的哪一个
  3. **按需加载参考** — 通过 CRR（条件参考检索），只加载与当前任务相关的参考文件
  4. **提出修复方案** — 带显式风险控制
  5. **交叉资源验证** — 检查 label/selector/port 一致性
  6. **验证修复** — 策略引擎检查（Kyverno/OPA/Gatekeeper/kubeconform）
  7. **交付结构化输出** — 带假设、权衡、回滚说明的完整交付物

  CRR 是 KubeShark 最聪明的设计。26 个参考文件不会一次性全塞进上下文——只有工作流检测到相关信号时才加载对应文件。比如你在 AWS 上提到 IRSA，它才会加载 `eks-patterns.md`；你提到 Argo CD，才会加载 `gitops-controllers.md`。写一个普通 Deployment 不会为 OpenShift SCC 和 GKE Autopilot 约束付 token 费。

### 安装配置

  **方式一：Skills CLI（推荐）**

  ```bash
  npx skills add https://github.com/lukasniessen/kubernetes-skill --skill kubernetes-skill
  ```

  **方式二：手动克隆**

  macOS / Linux：
  ```bash
  git clone https://github.com/LukasNiessen/kubernetes-skill.git ~/.claude/skills/kubernetes-skill
  ```

  Windows（PowerShell）：
  ```powershell
  git clone https://github.com/LukasNiessen/kubernetes-skill.git "$env:USERPROFILE\.claude\skills\kubernetes-skill"
  ```

### 使用指南

#### 场景一：生成生产级 Deployment

  你让 Claude Code："帮我写一个 Nginx Deployment，3 个副本，配 Ingress 和自动扩缩容。"

  不装 KubeShark：Claude 生成一个能跑的 Deployment——但 securityContext 为空、resources 没设、HPA 用了 `autoscaling/v2beta2`（已废弃）、Ingress 用的是 `networking.k8s.io/v1beta1`（1.22 移除）。

  装了 KubeShark 之后：Claude 先生成诊断报告，指出当前集群版本下哪些 apiVersion 可用、PSS restricted profile 要求什么 securityContext、HPA 应该用 `autoscaling/v2`。然后生成带完整 securityContext、resource requests/limits、正确 apiVersion、readinessProbe + livenessProbe 的 Deployment。输出末尾附上假设列表和验证步骤。

  ```
  /kubernetes-skill Create a production-ready Deployment with an Ingress and autoscaling
  ```

#### 场景二：安全审计已有配置

  你有一段已经在跑的 `deployment.yaml`，想确认有没有安全隐患。

  ```
  /kubernetes-skill Review my Deployment for security issues and add proper RBAC, NetworkPolicies, and resource limits
  ```

  KubeShark 会逐项对照 NSA/CISA Hardening Guide 和 OWASP Kubernetes Top 10 检查：有没有以非 root 用户运行？有没有 drop 所有 capabilities？有没有设置 seccompProfile？RBAC 有没有用通配符？NetworkPolicy 有没有默认拒绝规则？每项给出 PASS/FAIL，FAIL 项附带修复后的 YAML 片段。

#### 场景三：跨平台迁移

  你有一个跑在 EKS 上的 Helm Chart，想迁移到 GKE Autopilot。

  KubeShark 的 CRR 机制在这里最显价值：检测到 "EKS" 和 "GKE" 两个信号后，同时加载 `eks-patterns.md` 和 `gke-patterns.md`。它会逐条对比差异——GKE Autopilot 不允许 privileged 容器、不允许 hostNetwork、不允许 `nodeSelector` 指向特定节点、资源 requests 必须等于 limits——然后生成迁移清单和修改后的 values.yaml。

  ```
  /kubernetes-skill Migrate our Helm chart from EKS to GKE Autopilot, handling all Autopilot constraints
  ```

### 进阶技巧

  **和 kyverno/OPA 组 CP**：KubeShark 的 `validation-and-policy.md` 参考文件包含 Kyverno 和 OPA/Gatekeeper 的集成模式。你可以让 KubeShark 在生成 YAML 的同时，输出对应的 Kyverno ClusterPolicy 或 OPA Rego 规则，一条命令在 CI pipeline 里拦住不合规配置。

  **作为 Code Review 的前置步骤**：在 `.claude/skills/` 里装好 KubeShark 后，每次 PR 涉及 K8s 配置文件时，让 Claude Code 走一遍诊断流程再给出 review 意见。比人肉眼找 selector 拼写错误可靠得多。

### 常见踩坑

  **CRR 并非万能**：条件参考检索依赖工作流从用户请求中正确提取信号。如果你说"帮我写个 Deployment"但实际要部署到 OpenShift，KubeShark 不会自动加载 OpenShift 参考文件——你需要明确提到 OpenShift。一个简单的习惯：在提问时带一句目标平台。

  **和 kubectl 插件不冲突**：KubeShark 管的是"怎么写对配置"，不是"怎么操作集群"。`kubectl` 命令、`k9s` 操作、`helm install` 这些照常用。KubeShark 是事前把关，不是事中操作。

## 今日小结

  如果你经常让 AI 写 Kubernetes 配置，KubeShark 是今天最值得装的技能。安装只需要一条命令，不占上下文（激活成本 ~650 token），但每一次 K8s 相关的对话都会被它接管诊断流程。对于"安全配置默认缺失"这个 LLM 的系统性弱点，目前没有比"故障模式优先工作流"更务实的解法。花五分钟装上，以后让 Claude Code 写的每一个 Deployment 都自带安全审计、资源规划和回滚方案——不用再手动补 securityContext 了。
