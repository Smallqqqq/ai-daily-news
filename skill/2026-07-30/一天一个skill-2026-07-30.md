# fvadicamo/dev-agent-skills — AI 写的 commit 和 PR，它来把关

  你让 Claude Code 帮你提交代码、创建 PR、处理 review 意见。它在终端里一顿操作，三秒完事。然后你打开 GitHub：commit message 写成了 "update code"，PR 开到了 main 分支，label 选了一个不存在的标签，review 回复用了早已废弃的 `-f in_reply_to=` 语法。你叹了口气，开始手动收拾残局。

  dev-agent-skills 就是给这个问题兜底的。67 stars，MIT 协议，一套 Claude Code 插件，专治 AI agent 在 Git/GitHub 工作流里的各种低级错误。安装之后，agent 的每次 commit、PR、merge、review 都走标准化流程——不是限制它，而是让它别翻车。

---

### 它解决什么问题

  Claude Code 能写代码，也能调 `git` 和 `gh` 命令。但它对 Git 工作流没有肌肉记忆。不像你做了十年开发，手指自己知道该 rebase 到哪个分支、commit message 第一行不能超 50 字符、PR label 要先 `gh label list` 确认存在。

  裸装的 Claude Code 在 Git 操作上有六个高频翻车点：

  1. **commit 格式漂移**：同一个会话里，第一条是 `feat(auth): add login`，第三条变成了 `fixed the bug`——没有 scope、过去式、末尾带句号。
  2. **PR 分支搞错**：不问你就直接往 main 开 PR，事后才发现应该合到 develop。
  3. **不查任务文档**：你的 `.kiro/`、`.s2s/`、GitHub Issues 里明明写了任务拆解，它不搜，PR 描述里只有一句 "implemented feature"。
  4. **label 不存在**：建议的标签在项目里根本没有。
  5. **review 回复语法错误**：`gh api` 的 `-f in_reply_to=` 早就被 `--input -` JSON 语法替代了，它还在用老的。
  6. **merge 前不检查**：没确认 CI 通过、没查还有未回复的 review 意见，直接就合了。

  dev-agent-skills 不走"在 CLAUDE.md 里加一段提示词"的路线。它是四个独立的结构化 SKILL.md 文件，每个覆盖一个完整工作流阶段。Agent 在收到 "commit"、"create PR"、"merge"、"review" 相关指令后自动加载对应技能，按流程走，不漏步骤。

### 核心原理

  插件结构分三层：

  ```
  dev-agent-skills/
  ├── plugins/
  │   ├── github-workflow/     ← 核心：git-commit, github-pr-creation, github-pr-merge, github-pr-review
  │   ├── skill-authoring/     ← 辅助：creating-skills（写 SKILL.md 的参考资料）
  │   ├── guardrails/          ← 安全：PreToolUse hook 拦截危险命令
  │   └── privacy-guard/       ← 隐私：公开仓库自动检查敏感信息
  └── .claude-plugin/          ← Claude Code 插件清单
  ```

  每个技能的关键设计是**动态上下文注入**——不是静态的规则列表，而是运行时从当前仓库抓实际数据。比如 `git-commit` 技能的第一步是执行 `` !`git log --oneline -5` `` ，把项目最近的 commit 风格实时拉进来，而不是假设"所有项目都用 Conventional Commits"。`github-pr-creation` 先跑 `gh label list` 确认有哪些标签，再建议匹配的标签。

  技能采用 `model-invoked` 模式——Agent 根据用户指令自动匹配加载，不需要手动输入 `/git-commit` 这样的命令。你说"帮我提交一下"，Agent 就知道该加载哪个技能。

### 安装配置

  **方式一：Claude Code 插件市场（推荐）**

```bash
# 添加插件市场
/plugin marketplace add fvadicamo/dev-agent-skills

# 安装插件
/plugin install github-workflow@dev-agent-skills
/plugin install skill-authoring@dev-agent-skills
/plugin install guardrails@dev-agent-skills
/plugin install privacy-guard@dev-agent-skills
```

  重启 Claude Code 会话后生效。四个插件可以按需安装，不强制全装。

  **方式二：手动复刻技能目录**

```bash
git clone https://github.com/fvadicamo/dev-agent-skills.git
# 复制需要的技能到个人技能目录
cp -r dev-agent-skills/plugins/github-workflow/skills/* ~/.claude/skills/
```

  手动安装后需要检查每个 SKILL.md 里 `` !`cmd` `` 引用的路径是否正确。

### 使用指南

#### 场景一：让 AI 写一条规范的 commit

  你在开发用户认证模块，改了三个文件。你对 Claude Code 说：

  > "帮我提交一下这几次改动，跟认证相关的"

  没装这个技能时，Claude 可能输出：

```bash
git add -A
git commit -m "update auth code"
```

  装了之后，它先跑 `git log --oneline -5` 看项目习惯，然后输出：

```bash
git add src/auth/login.ts src/auth/middleware.ts src/auth/types.ts
git commit -m "feat(auth): add JWT token refresh middleware

Implement automatic token refresh for expired JWT tokens in
the auth middleware layer. Tokens within 5min of expiry are
silently refreshed using the refresh token.

Closes #142"
```

  类型用 `feat`、scope 用 `auth`、subject 是祈使句、不超 50 字符、body 解释了做了什么和为什么。格式自动对齐项目已有的 commit 风格。

#### 场景二：开一个带任务校验的 PR

  你在 `feature/task-3-user-profile` 分支上完成了用户资料页的开发。你说：

  > "帮我给这个分支开个 PR"

  技能加载后的完整流程：

  1. **确认目标分支**："Creating PR from feature/task-3-user-profile to develop. Correct?" 等你回复 yes。
  2. **搜索任务文档**：自动扫描 `.kiro/specs/`、`.s2s/plans/`、GitHub Issues，找到 Task 3 的拆解清单。
  3. **逐项校验子任务**：发现 Task 3.1（头像上传）和 Task 3.2（昵称编辑）已提交，但 Task 3.3（密码修改）没有对应的 commit。停下来问你："Task 3 INCOMPLETE: 1/3 sub-tasks missing. Task 3.3: MISSING. Proceed anyway?"
  4. **跑测试**：`npm test` 必须通过才继续。
  5. **匹配标签**：先 `gh label list`，确认项目里有 `enhancement` 标签，然后建议打上。
  6. **生成 PR**：标题 `feat(profile): add user profile editing with avatar upload`，正文用七种模板中的 `feature` 模板，附带子任务完成状态。

  整个过程不需要你在旁边盯着——你只需要在关键决策点回复 yes/no。

#### 场景三：处理 PR review 意见不踩坑

  PR 上收到了三条 review 意见：一个 Gemini bot 标记的安全问题、一个人工 reviewer 的架构建议、一个 CodeRabbit 的拼写提示。你对 Claude Code 说：

  > "处理一下这个 PR 上的 review 意见"

  没装技能时，agent 可能按收到的时间顺序一条条回，每条单独 commit、push 一次——触发 CI 跑三遍、bot review 跑三遍、reviewer 收到三封邮件。

  装上后的标准流程：

  1. **按严重度排序**：CRITICAL（安全问题）→ HIGH（架构建议）→ MEDIUM（拼写提示）
  2. **逐条验证**：每条意见先读代码确认是否属实，不是盲改
  3. **批量提交**：功能性修复各一个 commit，装饰性修改合并成一个 batch
  4. **用正确的 API 语法回复**：`gh api --input -` 的 JSON 格式，不是已废弃的 `-f in_reply_to=`
  5. **避免 review loop**：一次 push 包含所有修复，如果 reviewer 的评论里带了 `[skip]` 标记则跳过
  6. **提交正式 review**：`gh pr review --approve` 或 `--request-changes`

### 进阶技巧

  **和 CLAUDE.md 联动**：`git-commit` 技能的第一步就是检查项目根目录的 `CLAUDE.md`，看有没有自定义的 commit 约定。比如你的 CLAUDE.md 里写了"scope 必须用中文拼音缩写"，技能会自动适配，不会强行套 Conventional Commits。

  **Privacy Guard 公开仓库保护**：`privacy-guard` 插件在每次 commit 前自动扫描 diff 中的 API key、token、内网地址等敏感字符串。如果检测到，PreToolUse hook 直接拦截 commit，并告诉你哪一行有问题。适合同时维护公开和私有仓库的开发者。

  **Guardrails 无人值守模式**：如果你在 `--dangerously-skip-permissions` 模式下跑 Claude Code（比如 CI 脚本里），`guardrails` 插件的 PreToolUse hook 会在每个 Bash 命令执行前过一遍安全规则——禁止 `rm -rf /`、禁止修改 `.git/config`、禁止未经确认的 force push。

### 常见踩坑

  **坑 1：插件安装后技能没加载**。插件安装完需要重启 Claude Code 会话，或者在当前会话里跑 `/reload-skills`。只安装不重启等于没装。

  **坑 2：`gh` CLI 未登录**。四个 GitHub 工作流技能都依赖 `gh` CLI。安装前确认 `gh auth status` 显示已登录，否则技能加载后所有 `gh` 命令都会报权限错误。

  **坑 3：Windows 路径问题**。`git-commit` 技能里的 `` !`git log --oneline -5` `` 动态注入在 Windows 的 Git Bash 环境下正常工作，但在 PowerShell 里可能因路径编码问题失败。建议在 Git Bash 终端里使用 Claude Code。

### 同类技能对比

| 技能 | 安装方式 | 核心特点 | 适用场景 | 热度 |
|------|---------|---------|---------|------|
| **dev-agent-skills**（今日推荐）| `/plugin install` | 四个独立技能覆盖全流程，动态上下文注入，自动匹配项目风格 | Claude Code 用户的日常 Git/GitHub 工作流 | ⭐ 67 |
| addyosmani/agent-skills (git-workflow) | `npx skills add` | 24 个生命周期技能中的一部分，规范导向 | 需要完整工程规范体系的团队 | ⭐ 80.9K |
| rk-skills | `/plugin install` | 端到端自动化（issue→PR→review loop），带 complexity score | 需要全自动 issue-to-merge 流水线的项目 | ⭐ 未知 |

  dev-agent-skills 的定位是做一件事但做透：Git/GitHub 工作流。不像 addyosmani 那样覆盖整个软件生命周期，也不像 rk-skills 那样走全自动 issue-to-merge 的路线。它更像一个"纠错插件"——Agent 本来就会 git commit，这个技能确保它每次 commit 都按规矩来。67 stars 不高，但安装量在持续增长，最近一次更新在 2026 年 7 月，维护活跃。

## 今日小结

  这个技能适合每天用 Claude Code 写代码、用 Git/GitHub 管理仓库的开发者。安装两条命令，配置零步。装上之后你不会觉得"多了个新功能"——你只会发现 Agent 的 commit message 突然规范了、PR 描述里有了任务校验、review 回复不再用错误的 API 语法。它的价值不是"能做以前做不到的事"，而是"以前每次都要手动纠错的事，现在不用了"。对于一个每天都在终端里过日子的开发者来说，每天省下五分钟纠错时间，一个月就是两小时。
