2026-09-11

写代码的 agent 越来越能干，管项目的方式却没跟上。ccpm 把「想法 → PRD → Epic → GitHub Issue → 并行 agent → 代码」串成一条查得到头的流水线，让 AI 干的每一步都能对回原始需求。

它解决什么问题

用 Claude Code 做稍大一点的功能，很快会撞上三个麻烦。

需求只活在对话里。聊了半小时，你说「按刚才说的做」，agent 开始写，写到一半上下文压缩了，它记不得你要什么，你也记不得自己说过什么。

并行不起来。一个 issue 里其实塞着数据库迁移、服务层、API 接口、前端、测试好几块，但你只能串着让 agent 一件件做，因为没人理得清哪几块互不依赖。

做完没有留痕。翻提交记录看不出哪次提交对应哪条需求，code review 只能靠回忆。

ccpm 的作者把这三个麻烦收敛成一条规则：每一行代码都必须能追溯到一份规格说明。实现方式很朴素：把项目管理那套纪律塞进 agent 的工作流，并用 GitHub Issues 当人和 AI 共同的真相来源。

核心原理

ccpm 是一个 Agent Skill，仓库里绝大部分是 bash 脚本和 Markdown，没有 SDK、没有第三方运行时，遵循 agentskills.io 的开放标准，所以 Claude Code、Codex、OpenCode、Cursor、Amp、Factory 都能用。

它把工作拆成五个阶段。

Plan：agent 先引导你做一轮结构化头脑风暴，把模糊想法逼成一份 PRD，落在 .claude/prds/<名字>.md；再把 PRD 解析成 epic，写清架构决策和技术路线。

Structure：epic 拆成编号任务文件（001.md、002.md……），每个任务带验收标准、工作量估计，以及三个关键字段——depends_on（依赖谁）、parallel（能否并行）、conflicts_with（和谁抢同一个文件）。默认一个 epic 不超过 10 个任务，超了就说明这个 epic 本身该拆。

Sync：推成 GitHub 上的 epic issue 加子 issue，本地任务文件名从 001.md 重命名成真实 issue 号（比如 1234.md），同时建一个专用 git worktree。

Execute：这部分是它跟普通任务管理工具的分水岭。ccpm 不把 issue 当原子单位——一个「实现密钥使用追踪」的 issue 会拆成迁移、服务逻辑、API 端点、UI、测试五条独立工作流，在同一个 worktree 里由多个 agent 同时推进。提交信息统一带 Issue #N: 前缀，事后能直接对回 issue。

Track：状态、站会、搜索、验证全部走 bash 脚本，仓库里一共 14 个（status.sh、standup.sh、blocked.sh、next.sh、validate.sh 等）。这部分刻意不经过 LLM，零 token 成本，输出格式也稳定。

GitHub 那边它只认 labels 和 milestones，不用 Projects API。本地文件先更新，同步到 GitHub 是显式动作，所以你断了网也能继续规划。

安装配置

# 1. 克隆
git clone https://github.com/automazeio/ccpm.git

# 2. 挂进 Claude Code（软链接，之后升级只需 git pull）
ln -s /path/to/ccpm/skill/ccpm .claude/skills/ccpm

# 3. 可选但建议：装上 gh 的 sub-issue 扩展，父子 issue 关系才完整
gh extension install yahsan2/gh-sub-issue

Windows 上没有 ln -s，改用符号链接或直接复制目录：

New-Item -ItemType SymbolicLink -Path ".claude\skills\ccpm" -Target "C:\path\to\ccpm\skill\ccpm"

前提只有三个：git、已经 gh auth login 过的 GitHub CLI、一个 GitHub 仓库。没有 GitHub 仓库的话它跑不起来，这点要先确认。

使用指南

ccpm 用自然语言触发，不需要背命令。以下场景里的引号内容是你说的话。

场景一：把模糊想法做成 PRD

你说「我想给项目加一个操作审计日志」，agent 会进入 Plan 阶段，一轮轮问你：谁产生日志、要记哪些字段、保留多久、谁能查。问完把结论写成 .claude/prds/audit-log.md。

预期结果：PRD 落盘，你可以在编辑器里直接改。改完再让它「把这个 PRD 转成 epic」，它输出一份带架构决策和技术路线的 epic 文件。

场景二：拆任务并同步到 GitHub

说「break down the audit-log epic」，它把 epic 拆成带依赖关系的任务文件；说「sync the audit-log epic to GitHub」，它创建 epic issue 和全部子 issue，把本地文件名改成 issue 号，建好 worktree。

预期结果：打开 GitHub 就能看到像截图里那样的一棵 issue 树，epic 的正文列着 Core Components 和 Integration Points，每个子 issue 带勾选框形式的验收标准。

场景三：让一个 issue 真正并行跑起来

说「start working on issue 19」，ccpm 先分析这个 issue 里哪些工作流互不依赖，再把它们分派给多个 agent 同时执行，每个 agent 只碰自己那几条文件。完成后按 Issue #19: 描述 的格式提交。

预期结果：原本串行要跑五轮的活，一轮并发做完。README 里那张对比表写得很直白：串行 1 个 agent 花 5 倍墙钟时间，5 个 agent 并行花 1 倍。

场景四：每天开工先看板

说「standup」，standup.sh 直接读 .claude/epics/ 下的本地状态，输出昨天完成了什么、今天该做哪个、哪些被卡住。说「what's blocked」走 blocked.sh，说「what's next」走 next.sh。

预期结果：秒回，且不消耗 token。这三个查询你可以挂在每天早上第一件事做。

进阶技巧

我自己用下来，conflicts_with 字段最值得专门填。多个 agent 并行时最容易翻车的地方是两个 agent 同时改同一个文件，写这个字段等于提前把冲突标注出来，ccpm 调度时会避开。任务拆得越细，这个字段的价值越大。

worktree 是可以横向扩展的。ccpm 默认给一个 epic 建一个 worktree，但你可以给同一仓库开多个 worktree、每个挂不同的 epic，做到多人多 agent 同时推进而不互相踩。/task fleet 那类跨 worktree 的汇总视图在同类工具里也有对应实现，思路是一样的。

常见踩坑

没装 gh-sub-issue 扩展时，父子 issue 关系会退化成正文里的一个 task list 复选框。功能不算坏，但 GitHub 侧的层级结构就丢了，用 gh issue list --label task 也筛不出归属。装扩展是一行命令的事，别省。

任务文件改名这件事要提前知道。同步之前文件叫 001.md，同步之后叫 1234.md。如果你自己写了脚本去遍历 .claude/epics/，得按 issue 号去匹配，按 00X 编号匹配会全部落空。

一个 epic 默认最多 10 个任务，这是设计约束不是 bug。如果你发现拆到第 10 个还没拆完，说明这个 epic 承载的东西太多了，应该先拆 epic。

同类技能对比

ccpm（今日推荐）

安装方式：git clone + 软链接

核心特点：GitHub Issues 当真相源，一 issue 多 agent worktree 并行

适用场景：多人协作的并行交付

热度：⭐ 8.4k

mattpocock/skills

安装方式：claude plugins install mattpocock-skills

核心特点：to-spec / to-tickets，讲的是规格与工单的写法

适用场景：个人工程纪律

热度：⭐ 259k

Spec-Driven Develop

安装方式：/plugin marketplace add zhu1090093659/spec_driven_develop

核心特点：七阶段流水线，带 drift_score 漂移控制

适用场景：大型改造与迁移

热度：⭐ 979

claude-gh-task-manager

安装方式：npx claude-gh-task-manager install

核心特点：统计会话时长与上下文词数，量化人工审查负担

适用场景：想量化 ROI 的团队

热度：⭐ 1

mattpocock/skills 热度高得多，但它解决的问题偏「怎么写规格、怎么拆工单」，落点是文档本身；ccpm 往后多走了一大步，管到 issue 同步和 agent 并行调度。如果你只想要纪律不要 GitHub 集成，选前者；如果你要的是「一个需求进来、多个 agent 并行出去」的流水线，ccpm 更贴。Spec-Driven Develop 的漂移控制在长周期重构里更实用，但生态成熟度还不如 ccpm。

⭐ 8.4k · MIT · GitHub：https://github.com/automazeio/ccpm

今日小结

ccpm 适合已经在用 GitHub 管项目、并且开始让 agent 接手成规模开发的团队。配置成本很低，克隆加一条软链接，装个 gh 扩展就完事。换来的是一件事：需求不再是聊天记录里的过期指令，而是一条从 PRD 到那次 commit 都查得到的记录，同时把原本串行的活真正摊开并行。如果你的项目还停留在「改个 bug、加个按钮」的粒度，它反而是负担，先别装。
