# planning-with-files — 上下文会死，计划不会

  AI 编程 agent 最大的软肋是失忆：`/clear`、崩溃、上下文压缩，干到一半的任务状态说没就没，新会话一切从头再来。这个 skill 把任务计划落到磁盘上的三个 Markdown 文件，每轮对话自动重注入，会话断了，计划不断。

### 它解决什么问题

  Claude Code 内置的 TodoWrite 列表存在一个致命缺陷：它活在上下文窗口里。窗口一满，列表跟着消失。做过长任务的人都经历过这种循环——agent 重新读一遍仓库、让你复述一遍目标、把已经做完的活重新"发现"一遍。

  具体到日常开发，问题有四个：

  - **易失记忆**：上下文一重置，任务清单归零
  - **目标漂移**：50 次以上的工具调用之后，最初的目标被新信息挤出窗口，agent 开始"自由发挥"
  - **错误失忆**：失败没有被记录，同一个坑掉两次
  - **上下文塞爆**：什么信息都往窗口里堆，而不是往磁盘上存

  author 的内部恢复 benchmark 给了个直观数字：带着这三个文件恢复一个新会话，平均 5.0 轮回到正轨；裸 agent 要 13.3 轮。仓库自带 417 个测试全绿，96.7% 的通过率。26K stars 说明了这个痛点的普遍性。

### 核心原理

  一句话：**把上下文窗口当 RAM 用，把文件系统当磁盘用。** 易失的放窗口，重要的写磁盘。

  对每个复杂任务，先创建三个文件：

```
task_plan.md    → 阶段划分 + 勾选框，也是 /clear 之后的恢复点
findings.md     → 调研结论和决策，边做边追加
progress.md     → 会话日志和测试结果
```

  落地到项目里就是三个平铺的 Markdown（v2.36.0 起并行任务改用 `.planning/YYYY-MM-DD-slug/` 隔离目录，配 `.active_plan` 指针）。

  agent 在每个决策点停下来对照六步阶梯，从上到下第一个命中的就执行：

```
1. 任务需要 3+ 步骤或 5+ 次工具调用？  → 先建三个文件
2. 学到了什么？                        → 追加到 findings.md
3. 做了什么？                          → 记入 progress.md
4. 一个 phase 完成？                   → 在 task_plan.md 勾掉
5. 上下文死了（/clear、崩溃）？        → 会话恢复流程重读三个文件
6. 所有 phase 完成？                   → Stop 门才放行（gated 模式）
```

  第 2 到第 6 步不是靠 agent 自觉，而是靠 hooks 机械化执行：Claude Code 装 5 个 lifecycle hooks，Codex 7 个，Pi 8 个，每个回合开始前把计划重注入上下文、写入后提醒、停止前检查完成度。

  会话恢复的机制值得单说。上下文满了之后你敲 `/clear`，skill 会：查 agent 的 session store（Claude Code 是 `~/.claude/projects/`，Codex 是 `~/.codex/sessions/`）→ 找到三个文件最后更新的时间点 → 提取那之后可能丢失的对话 → 生成一份 catchup 报告供你确认。消失的那段上下文，至少结论留在了盘上。

### 安装配置

  Claude Code 插件方式（skill + hooks + slash commands 一次装全）：

```
/plugin marketplace add OthmanAdi/planning-with-files
/plugin install planning-with-files@planning-with-files
```

  其他 60+ 种 agent 走 npx skills：

```bash
npx skills add OthmanAdi/planning-with-files
```

  装完建议顺手改一个设置——关掉自动压缩，让窗口在 `/clear` 前尽量多撑一会，配合恢复流程效果最好：

```json
{ "autoCompact": false }
```

### 使用指南

#### 场景一：长任务被 /clear 打断，新会话直接续上

  触发条件：上下文快满，任务才做了一半。操作：直接 `/clear`，开新会话，什么也不用解释。预期结果：新会话读到磁盘上的三个文件，从当前 phase 接着干，不需要你复述目标，不需要它重读仓库。原本 13 轮的"重新认识项目"过程压缩到 5 轮以内。

#### 场景二：50+ 次调用之后，目标不再漂移

  触发条件：一个持续一下午的大重构，agent 越干越偏。操作：什么都不用做——hooks 每个回合都把 task_plan.md 重注入窗口。预期结果：agent 每个回合开始都看得见原始目标、已完成项、当前 phase，偏离目标的行为在下一回合被自动拉回。

#### 场景三：多个任务并行，各自状态互不污染

  触发条件：同时推进两个以上的独立任务（v2.36.0+）。操作：正常开工，skill 为每个任务建 `.planning/YYYY-MM-DD-slug/` 隔离目录，用 `.active_plan` 标记当前激活的计划。预期结果：切换任务时读对应目录的三件套，A 任务的进度不会覆盖 B 任务的计划。

### 进阶技巧

  **开 gated 模式，治半途谎报完成。** 默认模式下 agent 说"做完了"就完事；gated 模式要求 task_plan.md 里每个 phase 都勾掉、Stop 门才放行。长期无人值守的任务用它，完成度有据可查。

  **三个文件默认 gitignored，需要团队共享时记得放出来。** 单机使用没感觉，但如果你想让同事接手你进行到一半的任务，把这三个文件纳入版本控制，接手的 agent 读盘即上岗。

### 常见踩坑

  **旧版本（<2.36）并行任务会互相覆盖。** 老版本三个文件固定写在项目根目录，多个任务同时跑会打架。症状是 plan 内容莫名变成了另一个任务的。升级到 2.36+ 用隔离目录解决。

  **hooks 没生效，等于只装了一半。** 如果发现 agent 写了文件但从不重注入，大概率是插件安装不完整（比如只拷贝了 SKILL.md 没带 hooks），或你用的 agent 不支持该 hook 类型。检查方式：看 agent 每个回合开头有没有出现 `===BEGIN PLAN DATA===` 注入块。

  **和内置 TodoWrite 二选一，别叠加。** 两者都是任务追踪，叠加会让 agent 维护两份状态、互相矛盾。装了它，就让它接管计划。
