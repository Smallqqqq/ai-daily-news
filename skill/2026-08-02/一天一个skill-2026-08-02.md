# triage — 让 AI 按状态机管理你的 Issue 队列

  每天打开 GitHub，未归类的 Issue 堆了几十个——哪些是 bug、哪些是需求、哪些该交给 AI 做、哪些必须人工处理。Matt Pocock 的 triage 技能把这件事变成了一条流水线：归类→验证→追问→产出 agent-ready 简报，全程由 AI 按固定状态机执行。

---

### 它解决什么问题

  项目越做越大，Issue 和外部 PR 就越积越多。没有分类的 Issue 就像没贴标签的快递——每一件都得打开看一遍才知道是什么。triage 把 Issue 管理建模成一个简单的状态机：

  - 未标记 → `needs-triage`（待评估）
  - 信息不足 → `needs-info`（等回复）
  - 评估完毕 → `ready-for-agent`（交给 AI 做）或 `ready-for-human`（必须人工）
  - 不处理 → `wontfix`（四种细分原因，各有不同处置）

  每个 Issue 遍历这个状态机，每一步都有明确的出口和产物。对项目维护者来说，`/triage` 一句话就能看清哪些需要关注，不用再对着几十条通知发呆。

### 核心原理

  triage 不是一个"自动分类器"——它不会猜测 Issue 的类型然后自作主张。它是一套由 AI 执行的严格工作流：

  1. **搜集上下文**：读取 Issue 正文、评论、标签、作者信息；对 PR 还会读取 diff。搜索代码库确认这个需求是不是已经实现了，读取 `.out-of-scope/` 目录检查是不是之前就被拒绝过。

  2. **推荐分类**：给维护者提出类别（bug/enhancement）和状态（needs-triage/ready-for-agent/needs-info/wontfix）的建议，带上推理过程。

  3. **验证断言**：bug 就复现一下，PR 就 checkout 跑一下测试——确认问题真实存在，不是幻觉。

  4. **追问补全**（可选）：如果需求不够具体，启动 grilling 追问流程，一个问题一个问题地把需求问清楚，同时更新项目的 `CONTEXT.md` 和 ADR。

  5. **产出简报**：对 `ready-for-agent` 的 Issue，自动生成 agent brief——一份结构化的任务描述，后续 AI 编码助手可以直接拿去执行。对 `ready-for-human` 的，也生成类似简报，但注明为什么不能交给 AI。

  每条 AI 发出的评论都会带上 `> *This was generated by AI during triage.*` 标记，人和 AI 的边界始终清晰。

### 安装配置

  triage 是 mattpocock/skills 仓库中的一个工程技能，199k+ stars，MIT 协议。两种安装方式：

  **方式一：Claude Code 插件（推荐，自动更新）**

  ```bash
  claude plugins install mattpocock-skills
  ```

  或在 Claude Code 会话内：

  ```
  /plugin install mattpocock-skills
  ```

  **方式二：npx skills 安装（可编辑）**

  ```bash
  npx skills@latest add mattpocock/skills
  ```

  安装时选 triage 和 setup-matt-pocock-skills 两个技能。装完后在每个仓库跑一次初始化：

  ```
  /setup-matt-pocock-skills
  ```

  它会问你三个问题：用什么 Issue 追踪器（GitHub/Linear/本地文件）、分类标签怎么映射、文档存哪里。答完就能用了。

  **依赖**：需要 `gh` CLI 已认证（`gh auth login`），以及项目 Issue tracker 的读写权限。

### 使用指南

#### 场景一：早晨巡检——"有什么需要我关注的？"

  打开 Claude Code，输入 `/triage` 即可。AI 会列出三个桶：

  - **未标记的**（从未被 triage 过的新 Issue）
  - **needs-triage**（评估进行中的）
  - **needs-info 且报告者有新回复的**（信息已补全，需要重新评估）

  每条只显示一行摘要和计数，一目了然。你说"看第 3 个"，它就开始深入分析。

#### 场景二：处理一条具体的 Issue

  ```
  /triage 看看 #42
  ```

  AI 会完整读取 #42 的内容和全部评论，然后：
  - 搜索代码库确认这不是已实现的功能
  - 检查 `.out-of-scope/` 确认这不是之前被拒绝的需求
  - 如果是 bug：尝试按报告者的步骤复现
  - 如果是 PR：checkout 代码跑相关测试

  然后给你推荐："这是 enhancement，建议标记为 ready-for-agent，因为它的实现范围明确、不涉及外部依赖。"你确认或调整，它执行。

#### 场景三：需求不够清晰，启动追问

  当 Issue 描述只有一句"希望能支持暗色模式"时，triage 会先标记为 `needs-info`，但不是简单地丢一句"请提供更多信息"。它会：

  1. 用 grilling 流程一个问题一个问题地问——"哪些页面需要暗色模式？""主题切换是跟随系统还是手动？""有没有设计稿可以参考？"
  2. 同时更新项目的 `CONTEXT.md`，把讨论中确定的术语和约束沉淀进去
  3. 产出标准化的 triage notes，列出已确认的点和还需要报告者补充的信息

#### 场景四：快速状态切换

  ```
  /triage 把 #42 移到 ready-for-agent
  ```

  如果你已经评估过，只是想改个标签，triage 会直接执行，不追问。但会提醒你：要不要顺便写个 agent brief，让后续 AI 能直接接手？

### 进阶技巧

  **与 `/to-tickets` 联动**：triage 产出的 agent brief 可以直接交给 `/to-tickets`，后者把一份简报拆成多个有依赖关系的 tracer-bullet ticket。从 Issue 归类到任务拆分，一条流水线走通。

  **与 `/implement` 联动**：ready-for-agent 的 Issue 配上 agent brief 后，`/implement` 可以直接接手——按 brief 中的验收标准、测试策略、实现约束来写代码，走完 TDD 流程后自动 code review。

  **自定义状态映射**：`/setup-matt-pocock-skills` 初始化时可以自定义标签映射。你的项目用 `bug`/`feature`/`chore` 而不是 `bug`/`enhancement`？没问题，配一次就记住。

### 常见踩坑

  **标签映射不对导致状态不同步**：triage 依赖 `setup-matt-pocock-skills` 中配置的标签映射。如果换了 Issue tracker 或者改了标签体系，需要重新跑一次 `/setup-matt-pocock-skills`。否则 triage 推荐的标签找不到对应的实际 label，状态更新会失败。

  **gh CLI 权限不足**：triage 需要 `gh` CLI 有 repo 和 project 的读写权限。如果你看到 GraphQL 权限错误，运行 `gh auth refresh -h github.com -s repo -s project` 刷新 token。

  **大量 Issue 的性能**：`/triage` 列出所有待处理 Issue 时不会分页。如果你有上百条未分类 Issue，建议先手动批量关掉陈旧的，或让 AI 按创建时间筛出最近 30 天的。

## 今日小结

  如果你在维护有 Issue 队列的项目——无论开源还是团队内部——triage 是那种"装完就能看到效果"的技能。花 3 分钟配置，换来的是每天早上 `/triage` 一句话看清全局、每条 Issue 都有结构化的处理记录和 agent brief。Matt Pocock 的这些技能已经在 60,000+ 开发者的日常使用中验证过，工程味很足，没有花哨的 AI 噱头——把软件工程中本就该做的事，交给 AI 按规程执行。
