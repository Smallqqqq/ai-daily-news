# i-have-adhd — 让 coding agent 把答案放在第一行

　　编码助手很少答错，更多时候是答对了而你没找到：开场先来一句"好问题"，中间铺三段背景，真正该执行的那条命令藏在第四段，结尾再问一句"需要我继续吗"。i-have-adhd 是一份写给 LLM 的输出契约，把可执行的动作顶到第一行。

　　它五月建仓，这个月冲上 GitHub 周 trending，一周涨了 1.7 万星，现在 46.3k。装完调一次 `/i-have-adhd`，整个会话里 agent 的每一句回复都被这套规则重塑。

### 它解决什么问题

　　短问答里这个毛病不明显，长会话里会被放大。你让 agent 改一个鉴权流程，它回一大段：中间件怎么走、token 怎么验、cookie 怎么处理，顺带提一句你的依赖版本旧了、README 过期了、要不要顺手一起改。你得自己从段落里捞出"原来是要我跑 npm install"。

　　跨轮次的进度丢失更烦。做完第三步，agent 问一句"下一步继续吗"，你已经忘了总共五步走到哪。规则里有一条专门治这个：每轮都要重述状态，写成"第 3 步，共 5 步已完成：schema 更新完，下一步回填新列"。

　　还有两类细节每天都在消耗耐心。报错时 agent 先写"哎呀，似乎出了点问题"，而你需要的是哪一行挂了、期望值多少、实际值多少、改哪里。收尾那句"希望这对你有帮助，随时可以问我"也是，读到它的时候你早就在编辑器里定位下一条命令了。

　　作者把这些问题归到一个读者画像上：读你输出的人，工作记忆装不下屏幕外的东西。

### 核心原理

　　它是一份 SKILL.md，放在仓库的 `skills/i-have-adhd/SKILL.md`，通过 plugin marketplace 分发。定位不是"让回答变短"，而是按五条关于 ADHD 读者的事实重排信息：

- 工作记忆容量小，屏幕上没有的东西等于不存在，所以不要让人"记住 X"
- 知道答案不等于做完，从"懂了"到"做了"之间才是工作真正卡死的地方
- 启动是最难的一步，第一个动作必须小到可以立刻执行
- 模糊的时间估计等于没有，"有点工作量"和"几小时"在读的人眼里一样
- 进展需要被看见，埋在总结里的成果不算数

　　十条规则全部从这五条推出来：

1. **先给下一步动作**。第一行就是能做的事，不是背景、不是计划。答案是一条命令或一个路径片段，它排在最前面。
2. **多步任务编号**。超过一步就写编号列表，每一步是一个有边界的动作，不出现两次"然后"。
3. **结尾给一个具体动作**。有未完成的事就点名一件两分钟内能做的，哪怕只是"打开那个文件"。
4. **砍掉枝节**。第二个问题先记下，等第一个处理完再单独问，不在同一个回复里堆。
5. **每轮重述状态**。宿主有任务工具就用工具承载，"第 3 步/共 5 步"这类进度由清单承担，不要再用散文复述一遍完整计划。
6. **时间估计具体化**。"有测试覆盖的话十五分钟，没有的话一下午"。
7. **把完成的部分显性化**。说清楚现在什么能用了，以及怎么试。
8. **报错平铺直叙**。禁掉"哎呀""好像有点问题"，直接给原因和修法：哪一行失败、期望什么、实际什么、怎么改。
9. **列表不超过 5 项**。超了就按相关性排序、分组，内部该保留的还是要保留，这条只约束呈现方式，不允许因此丢掉相关内容。
10. **无开场白、无复述、无收尾客套**。"好问题""让我看看""希望对你有帮助""随时问我"全部禁掉。从答案开始，答案说完就结束。

　　规则的生命周期是整个会话。SKILL.md 里写得很硬：不确定是否还生效时，就按还生效处理。只有听到 `stop adhd mode` 或 `normal mode` 才关闭。这一条比规则本身更要紧，否则十轮之后 agent 就会滑回默认腔调。

　　另有两段设计是这份 skill 区别于普通 prompt 模板的地方。

　　一段是 When to break the rules，列了六条例外。用户要求"解释一下"时该展开就展开，开场白和收尾依然禁止。破坏性操作前必须先确认。连续三轮 debug 没进展，就停止改代码，改为指出一个可能错的假设并问一个诊断问题。请求本身有歧义时，先问一句再动手。

　　另一段是 Pre-send check：发送前删五类句子，包括宣布自己要做什么的第一句、问"还有别的吗"或复盘的最后一句、"顺便说一下"式的旁枝、不承载信息的不确定副词，以及"回头再看""对齐一下"这类比喻说法。删完做一次自检，只读第一行和最后一行，能否知道接下来做什么、刚刚发生了什么。

　　仓库结构上，`.claude-plugin`、`.codex-plugin`、`.cursor/skills`、`.opencode`、`gemini-extension.json`、`kimi.plugin.json`、`qwen-extension.json` 各占一份清单文件，`skills/i-have-adhd/SKILL.md` 是唯一的内容源。`evals/` 和 `tests/` 里放了可复现的效果评测，最近几次提交在测技能的输入开销与成本，作者在拿数据盯规则有没有副作用。

### 安装配置

Claude Code 两条命令：

```bash
claude plugin marketplace add ayghri/i-have-adhd
claude plugin install i-have-adhd@i-have-adhd

claude plugin list          # 校验是否装上
```

装完输入 `/i-have-adhd` 调用。它带 `disable-model-invocation: true`，也就是说 agent 不会自己偷偷启用，必须你显式点名。想让它在每次新会话里默认生效：

```bash
touch ~/.claude/.i-have-adhd-always
rm ~/.claude/.i-have-adhd-always      # 取消
```

同一份 SKILL.md 分发到了十几个宿主，对应命令：

```bash
# Codex
codex plugin marketplace add ayghri/i-have-adhd --ref main
codex plugin add i-have-adhd@i-have-adhd

# Cursor / GitHub Copilot / 其他走 agent-skills 规范的宿主
npx skills add ayghri/i-have-adhd -a cursor -y
npx skills add ayghri/i-have-adhd -a github-copilot

# Gemini CLI，扩展方式装完即生效
gemini extensions install https://github.com/ayghri/i-have-adhd

# OpenCode
git clone https://github.com/ayghri/i-have-adhd ~/.config/opencode/vendor/i-have-adhd
```

除此之外还有 Grok、Kimi Code、Qwen Code、Zed、Pi、Antigravity、Hermes、AstronClaw 的对应流程，`INSTALL.md` 里逐个写了安装、校验、更新、卸载和 always-on 的做法。

### 使用指南

#### 场景一：排查一个线上报错

　　触发条件是丢进去一段堆栈或者一句"这个接口 401 了"。默认风格下，agent 先分析架构、再摆几种可能性，方案放在最后。开启后第一条回复的第一行就是你该敲的命令。

　　预期结果长这样：`src/auth.ts:42` 校验失败，期望 200 实际 401，原因是缺 `Authorization` 头，改法是在请求里补上 `Bearer ${token}`，下一步跑 `npm test -- auth.spec.ts` 把第一条失败行贴回来。没有"哎呀"，没有"似乎"。

#### 场景二：一次跨五个文件的重构

　　让它改一处接口签名并同步所有调用方，规则 2 会把这件事拆成编号步骤，规则 5 保证每轮回复都带进度。我中途去吃饭回来，往下翻两条消息就知道上一个 agent 停在哪一步、下一个动作是什么，不用重读全部输出。

　　这里的实际收益是上下文重建成本降下来了。传统写法里你要把前几轮的输出重新读一遍才能接上，现在每轮末尾自带状态摘要。

#### 场景三：长会话里连续开发一整天

　　一个 session 从早上开到晚上，中间切过七八个话题。默认情况下 agent 的输出风格会随上下文漂移，中午之后又开始"让我来看看"。规则里那条"规则的生命周期是整个会话，不确定时按仍生效处理"就是防这个。

　　想临时退出，说一句 `stop adhd mode`，agent 一行确认后回到默认风格；再喊 `/i-have-adhd` 又能切回来。我的用法是平时挂着 always-on，需要它慢慢讲清楚一件事时再喊 `normal mode`。

#### 场景四：让 agent 一次扫一堆问题

　　你在一个陌生仓库里让它做体检，默认输出会甩出十五条发现，每条一段。规则 9 会把它们按相关性排序、分组，每组控制在五项以内，同时明确要求不得因此丢掉内容，你追问时还能拿回完整清单。

### 进阶技巧

　　**按自己的口味改规则**。整套规则就是一份 Markdown，fork 之后直接编辑 `skills/i-have-adhd/SKILL.md`。注意 fork 和上游同名，得先卸载再装自己的：

```bash
claude plugin uninstall i-have-adhd
claude plugin marketplace remove i-have-adhd
claude plugin marketplace add <your-username>/i-have-adhd
claude plugin install i-have-adhd@i-have-adhd
```

　　常见改法是放宽规则 9 的五项上限，或者把规则 6 的时间单位从分钟换成天。

　　**把规则抄进宿主级配置当兜底**。always-on 的开关只影响技能是否载入，有些平台还要单独关自己的开关。更彻底的做法是把十条规则写进 `~/.codex/AGENTS.md`、`~/.config/zed/AGENTS.md` 或者 Cursor 的 User Rules，这样即使插件没加载，规则依然在。

　　**和 harness 的任务工具配合**。规则 5 明确写了：宿主有 task/plan 工具时，用清单承载进度，不要再写一遍计划散文。在 Claude Code 里开着 todo 工具用这个技能，状态重述由工具完成，输出会更干净。

### 常见踩坑

　　**装了不等于开了**。这个技能带 `disable-model-invocation: true`，装完不喊 `/i-have-adhd` 它不会生效。Codex 那边同名机制写在 `agents/openai.yaml` 的 `policy.allow_implicit_invocation: false`。

　　**命令补全里没有 `/i-have-adhd`**。先重启 agent 进程，插件命令是启动时注册的。Grok 还多一步，安装时要 `--trust` 且要显式 `enable`，缺一个 hooks 和 skills 都不生效。

　　**设了 always-on 但新会话还是老样子**。先升级插件再重启，hook 只在启动时读那个标志文件。另外 Grok 不读 `~/.claude` 下的标志，得按它自己的路径放。

　　**装完回复里还有"好问题"**。大概率是旧会话的上下文太长，规则被淹了。开一个新会话，或者收紧 SKILL.md 里对应那条的措辞。

　　**`marketplace add` 失败**。仓库参数要用 `owner/repo` 形式，写本地路径时必须指向仓库根目录，不能指到 `.claude-plugin/`。

### 同类技能对比

| 技能 | 安装方式 | 核心特点 | 适用场景 | 热度 |
|------|---------|---------|---------|------|
| **i-have-adhd**（今日推荐）| `claude plugin install i-have-adhd@i-have-adhd` | 管 agent 输出的信息结构：先动作、编号、无客套 | 每天和 coding agent 对话，答案总被埋在铺垫里 | ⭐ 46.3k |
| humanizer | `npx skills add blader/humanizer --global` | 去掉文本里的 AI 写作痕迹，不虚构细节 | 润色对外文章、文档 | ⭐ 48.6k |
| ponytail | `codex plugin marketplace add DietrichGebert/ponytail` | 让 agent 少写代码、少动文件 | 控制改动面，压住过度实现 | ⭐ 139k |
| caveman | `gemini extensions install https://github.com/JuliusBrussee/caveman --consent` | 压缩输出 token，砍掉客套话 | 省 token、省阅读量 | — |

　　humanizer 处理的是"文本读起来像不像人写的"，i-have-adhd 处理的是"读的人能不能立刻动手"，一个面向成稿，一个面向对话。ponytail 管 agent 干什么（少写代码），这个技能管 agent 怎么说。要压 token 就配 caveman，它砍体量，i-have-adhd 砍顺序。

## 今日小结

　　适合每天在终端里和 coding agent 打交道的人，尤其是同时开好几个会话、经常需要回头翻上文的那种。配置成本是两条命令加一次 `/i-have-adhd`，花不到两分钟。换来的东西很实在：每条回复的第一行就是下一步动作，最后一行就是刚刚发生了什么，中间不再有需要你自己捞的答案。
