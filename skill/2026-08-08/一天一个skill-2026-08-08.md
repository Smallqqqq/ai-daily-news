# debug-skill — 让 AI 编程助手像人一样调试代码

  Claude Code 帮你修了一个 bug，第三次提交之后你终于受不了了——它的调试方式是在代码里塞 `print()`、看输出、猜原因、改一行、再塞 `print()`。你十分钟能搞定的事，它花了二十分钟还没找到根因。debug-skill 做的事情很直接：给 AI Agent 装上真正的调试器——断点、单步执行、变量检查、调用栈回溯，和你用 VS Code 调试一模一样。

  debug-skill 由以色列开发者 Almog Baku 创建，311 stars，MIT 协议。它的核心价值不在"又一个调试技能"，而在于它把 VS Code 级别的调试能力翻译成了 AI Agent 能消费的 CLI 命令——`dap`（Debug Adapter Protocol 的薄封装），让任何能从 Bash 调命令的 Agent 都能操作真正的调试器。

### 它解决什么问题

  AI 编程 Agent 调试代码时有一个根本性的能力缺陷：它们只能"看"代码，不能"跑"代码。当你告诉 Claude "这个 API 返回 500"，它会读源码、分析逻辑、推测可能的原因——然后直接改代码。它没有办法在运行时停在断点处检查变量、单步跟踪数据流、查看调用栈回溯。

  这个问题不只是效率低下，它会导致三种典型的调试失败模式：

  1. **症状修复而非根因修复**。Agent 看到 `NoneType has no attribute 'name'`，直接在调用处加了 `if x is not None`。但它不知道 `x` 为什么是 `None`，也不知道上游哪一步丢了数据。问题消失了一周，然后在另一个调用点以相同方式复现。

  2. **多轮猜测循环**。Agent 提出一个假设，改一行代码，让你跑一遍测试。测试没过，再提一个假设，再改一行。每次迭代都要重新加载上下文，token 消耗巨大，而且越往后 Agent 越容易"忘记"前面排除过什么。

  3. **复杂数据流完全不可见**。一个请求经过中间件 → service 层 → repository 层 → 数据库，中间某个环节悄悄改了字段名。Agent 读源码看不出问题，因为问题不在代码里，在运行时数据结构的变化。没有断点调试，这类问题几乎不可能定位。

  debug-skill 的解法是把调试器交给 Agent：让它在运行时设置断点、检查变量值、单步执行、回溯调用栈、评估表达式。Agent 不需要猜——它能看见。

### 核心原理

  debug-skill 分两层：**Skill 层**和 **CLI 层**。

  **Skill 层**（`debugging-code/SKILL.md`）是一套结构化的调试工作流知识，教 Agent 什么时候该设断点、怎么根据错误信息选择断点位置、如何用单步执行缩小范围、如何根据变量值判断假设是否成立。它不只是"你可以用 dap 命令"这样的提示，而是一套完整的调试 SOP——从复现问题到隔离根因到验证修复，每个阶段都有明确的出口条件。

  **CLI 层**（`dap`）是一个用 Go 写的无状态 CLI 工具，包装了微软的 Debug Adapter Protocol。它的架构很简洁：

  ```
  dap <cmd>  →  Unix socket  →  后台守护进程  →  DAP 协议  →  debugpy/dlv/js-debug/lldb-dap  →  你的程序
  ```

  关键设计决策是**无状态 CLI + 后台守护进程**。Agent 每次只发一条命令（如 `dap step`），守护进程维护调试会话的状态。CLI 本身不持有任何状态，所以 Agent 不需要管理调试器的生命周期——它只需要在怀疑有问题时设断点、需要检查变量时 eval、找到根因后 stop。守护进程空闲 10 分钟后自动退出，不会残留僵尸进程。

  每次执行命令后，CLI 自动返回完整上下文——当前位置、周围源码、局部变量、调用栈、程序输出。Agent 不需要额外发 `context` 或 `stack` 命令来获取上下文，一次调用拿到所有信息。这个设计对 token 效率很关键：如果每次 step 后还要再发两三个命令才能看清状况，token 消耗会成倍增长。

  语言支持覆盖了主流后端技术栈：Python（debugpy）、Go（Delve）、Node.js/TypeScript（js-debug）、Rust/C/C++（lldb-dap）。后端根据文件扩展名自动检测，也支持手动指定。还支持远程调试——可以 attach 到容器里的 debugpy、运行中的进程 PID、或自定义的 DAP 端点。

### 安装配置

  **第一步：安装 Skill**

  Claude Code 插件市场一键安装：

  ```
  /plugin marketplace add AlmogBaku/debug-skill
  /plugin install debugging-code@debug-skill-marketplace
  ```

  其他 Agent（Cursor、Windsurf、Copilot、Cline 等 20+）：

  ```bash
  npx skills add AlmogBaku/debug-skill
  ```

  **第二步：安装 dap CLI**

  macOS（Homebrew）：

  ```bash
  brew install AlmogBaku/tap/dap
  ```

  Linux / macOS（一键脚本）：

  ```bash
  bash <(curl -fsSL https://raw.githubusercontent.com/AlmogBaku/debug-skill/master/skills/debugging-code/scripts/install-dap.sh)
  ```

  源码安装（需 Go 1.21+）：

  ```bash
  go install github.com/AlmogBaku/debug-skill/cmd/dap@latest
  ```

  **第三步：安装对应语言的调试后端**

  dap CLI 依赖各语言的调试后端，按你的技术栈安装：

  ```bash
  pip install debugpy          # Python
  go install github.com/go-delve/delve/cmd/dlv@latest  # Go
  npm install -g @vscode/js-debug  # Node.js（通常已内置）
  ```

  装完后在 Claude Code 中描述你的 bug，Skill 会自动激活。也可以显式调用：`/debugging-code`。

### 使用指南

#### 场景一：API 返回了错误的数据，不知道在哪一步出的问题

  你告诉 Claude："`/api/orders/123` 返回的 `total_price` 是 0，但购物车里明明有三个商品。"

  Agent 不会直接去改计算逻辑。它会：

  1. 在 `calculate_total` 函数入口设断点：`dap debug orders/service.py --break orders/service.py:156`
  2. 触发请求后，停在断点处，`dap eval "items"` 检查传入的商品列表是否完整
  3. 如果 items 没问题，`dap step` 单步跟进计算循环，`dap eval "item.price"` 检查每个商品的价格
  4. 发现第三个商品的价格是 `None`——数据库里存了 NULL
  5. 根因定位到了，修数据库迁移脚本而不是改 Python 代码

  整个过程 Agent 像人一样操作：设断点 → 观察数据 → 缩小范围 → 找到根因。不需要代码里塞满 `print()` 再读终端输出。

#### 场景二：并发竞态条件，偶尔出现偶尔不出现

  你告诉 Claude："用户偶尔收到两封确认邮件，看起来是同一个订单被处理了两次。"

  这类并发 bug 是最难排查的——代码逻辑看起来完全正确，只有在特定时序下才暴露。Agent 的做法：

  1. 在订单处理入口设断点：`dap debug orders/worker.py --break orders/worker.py:42`
  2. 同时在幂等检查处设第二个断点：`dap break add orders/worker.py:58`
  3. 启用 `--json` 模式输出，方便脚本化分析
  4. 多次触发后，`dap eval "lock.acquired"` 发现在某些情况下分布式锁获取成功但 TTL 已过期
  5. 根因是锁的 TTL 短于订单处理时间，第二个 worker 在锁释放后成功获取了锁

  如果没有断点调试，Agent 只能靠读代码猜——它看到一个 `with lock:` 语句，默认认为锁是可靠的。有了断点，它能验证锁的实际行为和预期是否一致。

#### 场景三：重构后性能回归，但不知道慢在哪

  你告诉 Claude："重构了用户查询接口，P99 延迟从 200ms 涨到了 2s，帮我查原因。"

  Agent 的策略：

  1. 先在怀疑的 ORM 查询处设断点：`dap debug app.py --break queries.py:88`
  2. `dap continue` 执行到断点，`dap eval "str(query)"` 打印生成的 SQL
  3. 发现 SQL 语句里多了一个不必要的 JOIN，导致全表扫描
  4. 但 Agent 不急着修——它用 `dap step` 单步跟踪 ORM 的关系加载逻辑
  5. 确认是 `select_related` 参数被误删了，加回来即可
  6. 修完后重新设断点验证：P99 回到 200ms

  性能问题的根因分析，断点比 profiler 更适合 Agent——profiler 的输出是大量数字，Agent 解读起来很费力；断点的输出是具体的数据结构和执行路径，Agent 天然擅长理解。

### 进阶技巧

  **多 Agent 并行调试**。dap 支持命名会话（`--session`），每个调试任务有独立的守护进程和 socket。如果你同时让 Claude 调查两个不同服务的 bug，两个 Agent 各开一个 dap session，互不干扰：

  ```bash
  dap debug orders/service.py --session bug-142 --break orders/service.py:88
  dap debug payments/gateway.py --session bug-143 --break payments/gateway.py:35
  ```

  **远程调试容器里的代码**。如果你的服务跑在 Docker 里，不需要把代码拉到本地再调试。在容器里启动 debugpy（`python -m debugpy --listen 0.0.0.0:5678 app.py`），然后 Agent 直接 attach：

  ```bash
  dap debug --attach container-host:5678 --backend debugpy --break handler.py:20
  ```

  这对微服务架构尤其有用——Agent 可以调试线上 staging 环境的实际行为，而不是本地 mock 数据。

### 常见踩坑

  **Windows 兼容性**。dap CLI 用 Unix domain socket 做进程间通信。Windows 上 Go 的 `net.Dial` 不支持 Unix socket，所以 Windows 用户需要走 WSL 或在 Linux 虚机里跑。仓库里已经有 `platform_windows.go` 适配文件，但作者坦言 Windows 原生支持仍在完善中。如果你主力环境是 Windows，建议在 WSL2 里安装 dap 和调试后端。

  **调试后端的版本匹配**。delve（Go 调试器）的版本必须和 Go 编译器版本匹配。如果你用 Go 1.22，装了 dlv 1.22 以下的版本，断点可能不会触发，且不会报错——Agent 会以为程序没走到那个路径，实际上走到了但调试器没停下来。每次升级 Go 版本后记得同步更新 delve：`go install github.com/go-delve/delve/cmd/dlv@latest`。

  **Node.js 调试的性能开销**。js-debug 后端在大型 Node.js 项目中启动较慢（特别是 monorepo 里有几百个 tsconfig 的情况），首次 `dap debug` 可能需要 10-15 秒。这不是 bug，是 js-debug 在解析项目配置。Agent 第一次调用超时时，不要以为调试器挂了，等一等就好。

### 同类技能对比

| 技能 | 安装方式 | 核心特点 | 适用场景 | 热度 |
|------|---------|---------|---------|------|
| **debug-skill**（今日推荐）| `/plugin install` 或 `npx skills add` | 真实调试器（DAP 协议），断点/单步/变量检查，支持 Python/Go/JS/Rust | 需要运行时数据才能定位的复杂 bug | ⭐ 311 |
| Claude Code 内置 `/debug` | 已内置 | 代码分析 + 日志推理，无运行时断点能力 | 代码逻辑错误、静态可分析的 bug | 内置 |
| doraemonkeys/debug-mode | git clone + 手动移动目录 | 假设驱动的日志插桩调试，需要人工在循环中复现 bug | 可稳定复现的 bug | ⭐ ~150 |
| millionco/debug-agent | `npx skills add` | 运行时证据收集 + NDJSON 日志分析 | 需要证据链的调试场景 | ⭐ 288 |

  debug-skill 的独特价值在于它是唯一一个给 Agent 装上**真正的调试器**的方案。其他方案要么依赖代码分析，要么依赖日志插桩。只有 debug-skill 让 Agent 获得了和人类开发者一样的运行时可见性——停在任意一行、看任意变量的值、追踪完整调用栈。

## 今日小结

  如果你经常让 Claude Code 帮你修 bug，而这个 bug 不是"一眼就能看出 typo"那种，debug-skill 是你今天最值得装的技能。安装五分钟（插件市场两条命令 + dap CLI 一条命令），换来的是 Agent 从"print() 猜谜模式"升级为"断点调试模式"。两者之间的效率差距，和你在 VS Code 里用断点 vs 不用断点的差距一样大。适合所有后端开发者——Python、Go、Node.js、Rust 全栈覆盖。花五分钟装好，下次遇到复杂 bug 的时候，你只需要描述问题，Agent 自己会设断点、查变量、追踪调用栈，找到根因然后精准修复。
