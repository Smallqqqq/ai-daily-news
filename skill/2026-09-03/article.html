让 Claude Code 写一个 R 包，大概率拿到这样的东西：%>% 管道符、expect_true() 断言、fluidPage() 布局、roxygen 注释不换行、CRAN 检查的坑一个不落。语法都对，但 r-lib 生态的现代工程规范一个没踩。这不能怪模型笨。R 语言的训练语料远少于 Python，网上大量老教程教的还是 2018 年的写法。Posit（RStudio 母公司）开源的 posit-dev/skills 就是来补这个差的：把公司内部工程师的 R 生态开发规范打包成 20 多个 Agent Skill，装进任何支持 SKILL.md 的编程 agent。429 stars，MIT 协议，最近提交是 5 天前。

![posit-skills-demo.png](./posit-skills-demo.png)

它解决什么问题

数据分析团队用 AI 编程助手，和 Web 团队用 AI 编程助手，踩的坑完全不一样。R 用户最常翻车的是这些：

写 R 包，AI 生成 expect_true(sum(x) == 3) 而不是 expect_equal(sum(x), 3)。断言失败时前者只会说 "FALSE"，后者告诉你期望值和实际值各是多少。写 Shiny 应用，AI 还在用 fluidRow(column(6, ...)) 的 legacy 布局，而不是 bslib 的 layout_column_wrap()。写 Quarto 文档，AI 分不清 cell 选项语法是 #| 而不是 knitr 的 {r ...}。提交 CRAN，AI 不知道 DESCRIPTION 的 Authors@R 格式、URL 校验、拼写检查这些额外要求。

这些问题都有现成答案，分散在 tidyverse 风格指南、bslib 文档、CRAN 政策页里。posit-dev/skills 把这些答案按任务组织成 skill，agent 匹配到任务时自动加载，不用你每次复制粘贴文档。

核心原理

每个 skill 是一个目录：入口 SKILL.md 写触发条件和主流程，references/ 放按需加载的详细文档。这叫 progressive disclosure：skill 激活时只读主文件，需要细节再翻 reference，不会把整个知识库灌进上下文。

以 r-package-development 为例。SKILL.md 里硬编码了 r-lib 生态的命令规范：测试用 devtools::test()，代码生成后必须跑 air format .，管道符只用 base pipe |> 不用 magrittr %>%，单行匿名函数用 \() ...，报错断言用 expect_snapshot(error = TRUE) 而不是 expect_error()，因为快照能让用户审查完整输出文本。这些是 Posit 工程师（这个 skill 的作者是 Simon P. Couch，testthat 生态的核心维护者之一）日常写包的标准动作。

shiny-bslib 的做法类似，但更偏 API 知识：主文件给出 page_sidebar() + card() + value_box() 的现代布局速查，references 里分 page-layouts、grid-layouts、cards、value-boxes、navigation、theming 等 12 个专题，用到才读。

触发靠 description 字段。比如 r-package-development 的 description 写"用户在处理 R 包、跑测试、写文档、搭包结构时使用"。你在对话里说"给这个 R 包加个函数并补测试"，agent 就会自己加载它。

安装配置

全部 20+ 个技能一起装：

npx skills add posit-dev/skills

用 Claude Code 插件市场按类别装：

/plugin marketplace add posit-dev/skills
/plugin install r-lib@posit-dev-skills
/plugin install shiny@posit-dev-skills
/plugin install quarto@posit-dev-skills
/plugin install github@posit-dev-skills

手动词装一个目录也完全可以。skill 就是 Markdown 文件：

git clone https://github.com/posit-dev/skills.git
cp -r skills/r-lib/r-package-development ~/.claude/skills/

装完新开会话生效。仓库结构一目了然：posit-dev/（通用开发技能）、github/（PR 工作流）、open-source/（发布与 changelog）、r-lib/（R 包开发）、shiny/、quarto/、brand-yml/、ggsql/。

使用指南

场景一：让 AI 按 r-lib 规范开发 R 包

触发条件：你在 R 包项目里说"加一个函数并写测试"。操作：正常下指令，agent 会自动加载 r-package-development。预期结果：测试放进 tests/testthat/test-{name}.R，断言用具体 expectation，代码跑过 air format，NEWS.md 按字母序加了条目，就是 CRAN 审查员想看到的样子。

场景二：把 legacy Shiny 应用现代化

触发条件：你说"把这个 Shiny 应用改成 bslib 布局"。agent 加载 shiny-bslib，按迁移指南把 tabsetPanel 换成 navset_card_underline()、fluidRow/column 换成 layout_column_wrap()、wellPanel 换成 card()，顺手把主题换成 bs_theme(version = 5)。skill 里带了一份从 legacy 模式到新模式的对照表，不用你提示每一步。

场景三：R Markdown 项目迁移到 Quarto

触发条件：你说"把这些 .Rmd 转成 Quarto"。quarto-authoring 只在你明确提到迁移时才读 conversion 参考文件，写新文档时不碰它们，避免浪费上下文。转换时按源格式加载对应指南：R Markdown、bookdown、xaringan、distill、blogdown、Jupyter 各有各的 conversion reference，覆盖 YAML 头、cell 选项（#| hashpipe 语法）、交叉引用等差异点。

场景四：PR 全自动：创建、盯 CI、处理 review 线程

github/ 下的三个技能和 R 无关，谁都能用：pr-create 从当前改动创建 PR、盯 GitHub CI 到通过为止，失败自动调试；pr-threads-address 扫出所有未解决的 review 线程，逐条改代码提交；pr-threads-resolve 批量关掉已处理的线程。一套 Posit 内部用的 PR 工作流。

进阶技巧

brand-yml 技能值得单独拿出来说。_brand.yml 是 Posit 推的品牌配置文件：一处定义配色、字体、logo，Shiny 应用和 Quarto 文档共用。这个 skill 教 agent 自动发现项目的 _brand.yml、生成主题函数、把品牌色应用到图表的 scale。AI 生成图表时配色随机的问题，用它一次解决。

另一个冷知识：Posit Assistant（RStudio 内置的 AI 助手）的 managed skills 就是从同一个仓库来的：shiny-bslib、quarto-authoring、predictive-modeling 这些。你在 Claude Code 里装这套，和在 RStudio 里用官方 AI 助手拿到的是同一份知识。

常见踩坑

装完发现不触发。检查两点：skill 目录名必须和 SKILL.md 里的 name 字段一致；有些 agent（比如 Codex）安装新 skill 后要重启会话才生效。另外这个仓库的 skill 大多假设 R 环境已经配好（R、Rscript、devtools 等在 PATH 里），Windows 用户先确认 Rscript -e "1" 能跑通。

用 shiny-bslib 时注意它假设你熟悉基础 Shiny。它是 UI 现代化技能，不是 Shiny 入门教程。从零学 Shiny 的人先看官方教程，别指望 skill 教 reactive 概念。

今日小结

适合谁：用 R 做数据分析和包开发的人——生物统计、金融量化、药企报表团队。R 用户是 AI 编程助手里最被忽视的群体，训练语料少、老教程多，AI 生成的 R 代码质量明显差一档。配置成本十分钟：一条 npx skills add posit-dev/skills 搞定，agent 以后写 R 包自动走 r-lib 规范、写 Shiny 自动用 bslib、写文档自动转 Quarto。换来的是 CRAN 提交少被拒一轮、Shiny 应用不用手动重写布局、PR 流程省掉手工盯 CI。对 R 团队来说，这是近期最值的一笔十分钟投资。
