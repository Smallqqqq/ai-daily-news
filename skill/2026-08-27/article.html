你让 Claude Code 做个新功能。它没问两句就开始写代码，写到一半发现理解偏了，推倒重来；你让它修个 bug，它不先复现就动手改，改完你说不算，它再猜。缺的是流程纪律。Superpowers 把「问清楚 → 写计划 → 派子代理执行 → TDD → 互相审查」这套老工程师的干活方式，打包成一组会自动接连触发的 skills。277,856 stars，MIT 协议，Claude 官方插件市场上一步装完。

它是一套方法论：skill 之间互相衔接，你想在任何一环跳过，下一环都会把你拉回来。

![Superpowers 工作流演示](./superpowers-demo.png)

它解决什么问题

Coding agent 的常见翻车模式有三个。一是上手就写：需求没对齐，写到一半方向错了，白烧 token。二是没有计划：多步任务全靠上下文硬扛，/clear 一次全丢。三是没有审查：agent 写完就算完，没人验证它改对了没有。

Superpowers 的答案是把这些散落在「资深工程师直觉」里的步骤变成硬性环节。它从会话启动就开始干预：入口 skill（using-superpowers）要求 agent 在做任何创造性工作之前，先走 brainstorming 把需求问透，不直接写代码。

核心原理

它由十几个互相衔接的 skill 组成，每个 skill 的 description 都写好了触发边界，工作流靠接力完成：

  • brainstorming：创造性工作开始前强制探索需求和设计，把你没说出来的意图问出来，再把 spec 按小块展示给你签字
  • writing-plans：把确认过的需求翻译成带文件、接口、测试、验证命令的实现计划，「一个热情但没品位的初级工程师照着也能干」
  • subagent-driven-development：计划敲定后「go」，把每个任务派给子代理执行，主线程审查每个子代理的产出再继续，agent 能连续自主干两三个小时不跑偏
  • test-driven-development：强制真正的红-绿-重构循环，不写测试不让写实现
  • verification-before-completion / requesting-code-review：干活完成后先跑验证命令留证据，再走审查流程

触发是自动的：你不需要背什么命令，agent 在该用哪个 skill 的时候自己会加载。需要时也可以用 /skill-name 显式调用。这套机制决定了一件事：它既是工具，也是规矩。

安装配置

Claude Code 官方市场一步装：

/plugin install superpowers@claude-plugins-official

也可以走作者自己的市场（带几个周边插件）：

/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

同一套技能在 13 个平台上都有原生插件清单，各平台装法是：

平台 安装命令
Copilot CLI copilot plugin marketplace add obra/superpowers-marketplace 后 copilot plugin install superpowers@superpowers-marketplace
Codex CLI /plugins → 搜 superpowers 安装
Gemini CLI gemini extensions install https://github.com/obra/superpowers
Devin CLI devin plugins install obra/superpowers
OpenCode 按仓库里 .opencode/INSTALL.md 操作
Kimi / Antigravity / Grok Build 等 各自一条插件命令（见 repo README）

装完新开一个会话即生效。要求：Claude Code 或任一支持 Agent Skills 的宿主，无 API key、无账号配置。

使用指南

场景一：从零做功能，先问清再动手

你只说了一句「做个 GitHub star 排行页」。agent 不写代码，先回你几个问题：数据源要哪个仓库、多久刷新、要不要图表。你回答后，它把整理好的 spec 一条条贴出来签字。你点头，它产出一份带文件路径和测试清单的实现计划，你确认，才进入开发。全程你没写过一行 prompt 工程。

场景二：修 bug，先复现证据再改代码

报告说「大文件导索引偶发超时」。agent 加载 systematic-debugging：先造最小复现、抓日志拿到证据链，定位根因后才动手，改完跑单测和复现脚本，最后把证据摆出来说自己修对了什么。不再出现「改了一行你看行不行」。

场景三：大任务收尾，子代理干完审查门把关

计划里拆出六个任务，每个任务一个子代理在隔离上下文里干，主线程逐个审产出。全部干完触发 verification-before-completion 跑验证命令，再走 requesting-code-review。合不合并，由审查意见定，不由 agent 的「我觉得好了」定。

进阶技巧

这套 skills 支持组合。先把 brainstorming 当需求澄清器用顺手，再把 subagent-driven-development 和 TDD 绑定成「每个任务必须先写测试再写实现」的双保险。计划文件写到磁盘上之后，换个新会话执行 executing-plans 就能接着干——计划和上下文解耦，长任务不再绑定单一会话。

常见踩坑

  • OpenCode 是独立安装路径：即使你在 Claude Code 里已装过，OpenCode 要按仓库 .opencode/INSTALL.md 单独装一遍，两边的安装互不共享
  • 长会话注意 Hermes：Hermes Agent 没有 post-compaction 钩子，会话压缩发生在第一轮时可能丢掉 using-superpowers 引导，超长任务建议开局新会话
  • claude.ai 上传精简字段：通过 Skills API 或 package 分发时，只有 name、description、license 等标准 frontmatter 字段生效，Claude Code 专属字段（context: fork 等）会丢
