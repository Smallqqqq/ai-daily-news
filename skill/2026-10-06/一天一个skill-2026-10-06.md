# Second Brain OS — 你的知识库，AI 自己维护

　　你截图、收藏、存进"稍后读"，然后再也没有回去看过。Second Brain OS 把这个动作反过来：材料丢进去，整理和链接由 agent 完成，最后长成一套归你自己的 markdown 知识库。

---

![[second-brain-os-demo-1.png]]

### 它解决什么问题

　　官方文档里有一句话把痛点说得很准："Saving feels like an action, and it discharges the feeling that made you want to save." 保存这个动作本身，就释放了你想读的那股冲动。

　　于是队列越攒越长，阅读始终没有发生。更糟的是检索成本倒挂：想翻出当初存的东西，得先记得自己存过、存在哪、当时用什么措辞搜，比直接重新搜一次还贵。所以你重新搜索、重新保存，循环一遍。四百条未读不是资源，是一笔你绕着走的债。

　　大部分方案的做法是要求你更自律。而自律恰恰是已经失败过的那一环。这个技能做的是删掉你一直失败的那一步：归档和连接交给 agent，丢进 `raw/` 的东西会被处理、被链接，之后能用大白话问出来。

### 核心原理

　　它实现的是 Andrej Karpathy 在 2026 年 4 月 4 日发布的一个 gist 里提出的 llm-wiki 模式。反转很干脆：以前是你维护笔记、偶尔问 AI；现在是 AI 维护 wiki，你来读。

　　关键在于"编译"而不是"摘要"。一篇新资料会被整合进已有页面，讲某个概念的页面随资料变多而变好，不会退化成"每个来源分别说了什么"的清单。

　　三个动作撑起全部：ingest 摄入、lint 体检、query 查询，其余都是变体。

　　和 RAG 的分歧在"工作发生在什么时候"。RAG 在查询时干活，每次都从零开始，靠相似度捞几个 chunk 让模型作答；wiki 在摄入时干一次，结果被复用、被继续改进。这个差别会复利。第十篇关于某个主题的资料，在 RAG 里只是又一个 chunk；在 wiki 里，它改进的是前九篇共同建立的那个页面。矛盾也一样。两份打架的文档在 RAG 里是两个可能永远不会被同时检索到的 chunk，在页面上则是标了日期、你绕不开的记录。

　　官方把代价也写清楚了：摄入贵，写页面要花模型时间；质量依赖摄入质量；召回依赖链接，没人链的页面图谱到不了。它的结论是，这套权衡适合几千页规模、有人精心挑选的个人语料，不适合没人组织的一百万份文档。

　　库本身分成两层，这是它不容易烂掉的原因。知识层按"想法"组织，永远增长；项目层按管线组织（Inputs / Process / Outputs / Feedback），项目交付后就冷却。混在一起的后果官方也点了名：wiki 里长出死任务列表，每一次搜索都变差。

### 安装配置

　　官方 Quickstart 是九步，真正必要的是这六条。不需要注册账号，不需要 MCP，也不需要 Obsidian：

```bash
git clone https://github.com/undefined-ui/second-brain-os.git
cp -r second-brain-os/vault-template ~/brain
mkdir -p ~/brain/.claude
cp -r second-brain-os/skills   ~/brain/.claude/skills
cp -r second-brain-os/commands ~/brain/.claude/commands
cp -r second-brain-os/agents   ~/brain/.claude/agents
cp -r second-brain-os/scripts  ~/brain/scripts
cd ~/brain && claude
```

　　Windows 上照官方指南敲的时候，把 `python3` 换成 `python`：前者通常指向 Microsoft Store 的占位符，跑不起来。

　　装完得到什么：18 个 skill、72 个 slash command、6 个 subagent（其中 4 个被设计成只读）、一组零依赖的 Python 脚本负责链接检查、统计和图谱导出。用 Obsidian 打开 `~/brain` 就能看到图谱视图。顺带一提，这个仓库自己的在线指南就是同一个模式的产物：65 个页面、10 个章节、2.5 万字、86 条人工核过的互链。

### 使用指南

#### 场景一：把一篇文章变成库里的知识

　　剪藏进 `raw/`，然后 `/ingest`，或者直接说 "ingest this"。ingest 的核心规则是"没有链接就不算摄入完成"，每次运行以固定格式收尾：

```
Ingested: <source name>
New pages: <n> (list)
Updated pages: <n> (list)
Links added: <n>
Contradictions found: <none | description>
Gaps created: <list of linked pages that do not exist yet>
```

　　想灌历史存档用 `/backfill`，它按批次走、每批显示成本。视频和播客走 `/ingest-youtube`、`/ingest-voice`，PDF 走 `/ingest-pdf`，导出的聊天记录有 `/ingest-chats`，浏览器高亮有 `/ingest-highlights`。同一批命令里还藏着 `/contradictions`（列出记录在案的矛盾）和 `/trace`（追一个想法的来源链路）。

#### 场景二：问自己的库

　　`/ask` 或 "what do I know about X"。答案沿 wiki 页面导航出来，不走向量库那一套，每个结论背后有能点开的来源页。这一步真正兑现了"忘了自己存过什么都还能找回来"。

#### 场景三：开一个项目

　　`/project` 建四段式目录，然后让 agent 采访你，把目标写进项目自己的 `CLAUDE.md`。官方要求一个项目只写一个目标，理由很实在：写三个目标的产出，通常一个都不服务。项目跑完后把成品回灌进知识层，这是第二次做同类项目会明显变快的地方，也是几乎所有人都会跳过的一步。

#### 场景四：定期体检

　　`/lint` 查结构问题，`/health` 看库的状态，`/metrics` 记录带日期的健康快照，`/orphans` 捞出没人链接的孤儿页，`/graph` 看链接结构。图谱分析交给 `graph-analyst` 这个 subagent，它专门负责报告枢纽页、桥接和聚类。

### 进阶技巧

　　手写的页面在 frontmatter 里标 `maintained_by: human`，并在 `CLAUDE.md` 里写明"永不重写标记为 human 的页面，只追加链接、把问题记给作者"。这行元数据解决的是最让人恼火的一类事故：agent 把你亲手写的东西重写了一遍。

　　敏感材料可以分两条通道：私密内容用本地模型摄入，其余交给前沿模型。质量会降，官方承认本地模型在"什么值得单独成页""两份资料是否真的矛盾"这类判断上更弱，但这个切分是可行的。`/privacy` 会专门审计库里不该出现的材料。

　　想让维护自己跑起来，`/schedule` 配合 MCP 可以在你不开会话的时候定时整理。注意这是 MCP 唯一真正必要的场景；Agent 在库目录里启动时，读写文件不需要任何额外通道。

### 常见踩坑

　　**库跑了两周就停摆。** 几乎总是采集通道的问题：剪藏要点三次，或者手机没法把东西送进库，材料不来了，库自然就死了。修采集，别修库。另一个原因是回报预期太早，三十页的时候确实没有东西可以连接。

　　**页面变成"摘要的摘要"。** 来源页概括文章，概念页再概括来源页，每层都丢信息。根因是页面契约里出现了"摘要"字样。概念页要用你自己的话把一个想法讲清楚，独立成立。

　　**过三百页之后摄入质量下降。** 通常是上下文问题，agent 没有先查已有什么，就不断新建页面。确认每次摄入都先读 `index.md` 再动手，这一步是质量不随规模下滑的关键。

　　**别期待一夜见效。** 官方给的时间表：第一次真实回报在第 2 到 4 周，大家描述的那种"整个系统的意义所在"的状态要六个月。五页的图谱没什么看头，五十页的时候你会盯着它不想关。

## 今日小结

　　如果你有"收藏了但从不回看"的毛病，这是今天最值得花二十分钟配上的技能：六条命令装好，摄入第一篇文章就能看出差别，它不会变成一个孤立的摘要，而是拆成概念和实体接进已有页面。缺点也直说：它需要你持续往里喂东西，库的价值和你的采集习惯成正比，第一次回报在两到四周之后。好在没有任何锁定，库里全是你自己的文件，哪天不用了，删掉 `.claude` 目录，剩下的还是一套能读的 markdown 笔记。
