# ponytail — 最懒的资深开发者，写最少的代码

  你让 AI 加一个日期选择器。它装了 flatpickr、写了包装组件、加了样式表，然后聊起了时区问题。404 行。而资深开发者看到的只是：浏览器十年前就自带 `<input type="date">`，一行。ponytail 就是把这个"懒"硬塞给 AI agent 的 skill，不是偷懒，是知道什么才是必要的。129.5k stars，本周涨了 19,480，MIT，Claude Code 两条命令装好，Codex、Copilot CLI、Gemini、Cursor 等 20 多种 agent 宿主都有官方安装方案。

### 它解决什么问题

  AI 写代码的第一本能是"满足"。要日期选择器就装最流行的库，要过滤就写通用管道，需求还没说完就开始抽象。结果一行能写的写了五十行，为不存在的需求建了接口。代码量膨胀直接烧钱：token、耗时、上下文全涨。ponytail 专治这个：方向是"写得更少"，把 agent 拉到"最懒的资深开发者"的尺度——The best code is the code you never wrote。

  作者把话也说在前面：懒的是解决方案，读问题从不懒。理解任务、追踪真实流程是爬阶梯的前提；信任边界的校验、数据丢失处理、安全、可访问性永远不在砍掉范围里。

### 核心原理

  ponytail 是一套规则集（SKILL.md + 钩子），核心是写代码前必须过的 **7 级决策阶梯**——agent 停在第一个成立的台阶上：

| 级别 | 问自己 | 结果 |
|------|--------|------|
| 1 | 这东西需要存在吗？ | 不需要 → 跳过（YAGNI），一句话说明 |
| 2 | 代码库里已经有了吗？ | 复用，不重写 |
| 3 | 标准库能做吗？ | 用标准库 |
| 4 | 平台原生特性覆盖吗？ | 用 `<input type="date">`，别装库 |
| 5 | 已安装的依赖解决吗？ | 用它，不新增依赖 |
| 6 | 能一行搞定吗？ | 一行 |
| 7 | 只有走到这一步 | 写最小可用的那一段 |

  配合几条硬规则：不建只有一个实现的接口、不为一种产品建工厂；修 bug 改根因（先 grep 所有调用者，在共享函数里加守卫比每个调用者打补丁更小）；刻意的简化（全局锁、O(n²) 扫描）必须用 `ponytail:` 注释标出已知上限和升级路径；任何时候不得砍校验、错误处理、安全和无障碍。

  效果数据来自作者的真实测试：12 个功能任务、无头 Claude Code 会话、编辑真实开源仓库（tiangolo/full-stack-fastapi-template），按 git diff 评分——代码行数 -54%（单任务上限 -94%）、token -22%、成本 -20%、时间 -27%，对抗性测试安全率 100%。

### 安装配置

Claude Code 插件市场（两条命令，分开发）：

```bash
/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail
```

其他宿主：Codex 是 `codex plugin marketplace add DietrichGebert/ponytail` + `codex plugin add ponytail@ponytail`（要在 /hooks 里信任钩子）；Copilot CLI 是 `copilot plugin install ponytail@ponytail`；Gemini CLI 是 `gemini extensions install https://github.com/DietrichGebert/ponytail`；OpenCode 在 opencode.json 加 `{"plugin": ["@dietrichgebert/ponytail"]}`。纯指令类宿主（Cursor、Windsurf、Cline、Aider 等）直接复制对应的规则文件。注意：Claude Code 插件模式要求 Node 在 PATH 里，钩子脚本靠它跑。

强度默认 full，随时切换：`/ponytail lite`（按要求的建，但点出更懒的替代方案）、`/ponytail ultra`（YAGNI 极端派，先删后加）、`/ponytail off` 报告当前级别。

### 使用指南

#### 场景一：日期选择器——从 404 行到 1 行

  触发：让 agent 加一个日期选择字段。普通 agent 会装 flatpickr、写 wrapper 组件、加样式表。ponytail 模式下它停在阶梯第 4 级——平台原生特性——输出：

```html
<!-- ponytail: browser has one -->
<input type="date">
```

  预期结果：3 行，原生控件，零依赖。颜色选择器同理，287 行降到 23 行（`<input type="color">`）；倒计时器从 190 行动画仪表盘降到 13 行。

#### 场景二：/ponytail-review——审你的 diff，给删除清单

  触发：代码写完，想看看哪些是过度设计。`/ponytail-review` 审查当前 diff 的过度工程部分，返回可以直接删掉的清单；`/ponytail-audit` 审查整个仓库。预期结果：拿到一份"这些可以删"的清单（每条都有阶梯依据），比人工 review 快得多。

#### 场景三：复杂需求先交懒版本，再当场确认边界

  触发：需求本身复杂（"做一个完整的 X"）。ponytail 先交付懒版本，同时追问"做了 Y；X 的部分是否覆盖？需要完整 X 就说"。预期结果：你明确说"要完整版"它才铺开，否则就用最小实现。这个对话习惯能挡住大多数 agent 自我加戏。

### 进阶技巧

  **和 caveman 并用**：caveman（8 月 12 日推过）压缩 agent 的措辞，ponytail 压缩代码，规则互不重叠，装一起各管各的。**子代理注入控制**：`PONYTAIL_SUBAGENT_MATCHER` 环境变量用正则控制哪些子代理带 ponytail 规则——主代理保证风格，探索型子代理可以不带。**默认强度统一**：`PONYTAIL_DEFAULT_MODE` 环境变量或 `~/.config/ponytail/config.json` 的 `defaultMode` 字段，团队统一配置不需要改每个人的提示词。

### 常见踩坑

  **推理模型上成本可能反升**：OpenAI 推理模型内部多步反思跟"先复用"指令冲突，作者明确标注成本反而可能变贵；指令遵循弱的小模型（llama3.2 3B 这类）结果不稳定，装了效果打折。**两条安装命令必须分开发**：marketplace add 和 install 是两条独立命令，粘成一条不生效。**教程新旧问题**：早期版本以"80-94% 代码缩减"为宣传口径（虚高），新版已改口为修正后的 -54%；看到旧数字的教程基本是旧版内容。
