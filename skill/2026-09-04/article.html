让 AI agent 直接 release 一个功能，你通常要补最后一艘船：规格没写全、测试没到位、安全没过问，agent 还会用"会再补测试的"这种话搪塞过去。问题不在 agent 的智商，而在它没被生产纪律约束过。Addy Osmani——Google Chrome 团队工程副总裁、前端性能优化领域写了 20 年书的那个——把 Chrome 团队内部的工作流打包成了 25 个 Agent Skill：9 个斜杠命令，从需求访谈一路管到灰度发布，每个技能末尾强制提交验证证据，「应该没问题」（"Seems right"）永远不够。92k stars，MIT，支持 70+ 种 agent。

![addys-agent-skills-demo.jpg](./addys-agent-skills-demo.jpg)

它解决什么问题

AI 编程 agent 的核心能力不缺，缺的是质量门禁。它写的代码会编译会跑，但不一定过得了你同事的 code review、过不了性能基准、更过不了安全审计。而靠人肉盯着它补齐这些，等于每次都要把工程规范口头再传一遍。

addyosmani/agent-skills 把这件事变成了结构化的 24 个生命周期技能加 1 个元技能，按 Define → Plan → Build → Verify → Review → Ship 六个阶段排列，Agent 在做对应的事时自动加载对应技能：设计 API 自动触发 api-and-interface-design，构建界面自动触发 frontend-ui-engineering。你不需要记住任何规范，规范就在技能里。

核心原理

这套技能的设计有三个特征，都很硬核：

  1. 反合理化表格（Rationalizations）：每个技能里都有一张 Agent 常用借口清单，附已写好的驳斥论点。比如 Agent 想跳过测试时借口是 "I'll add tests later"，表格里直接给出记录在案的反对理由。设计意图就是让 Agent 没有理由跳过步骤：它想糊弄你，先过自己那关。
  2. 验证证据强制（Verification is non-negotiable）：每个技能以"证据要求"收尾——测试通过、构建输出、运行时数据，三选一必须有。README 的原话是"There is no substitute for evidence"。这正好补上 AI 编程最常死的点：看起来对。
  3. 渐进式披露：SKILL.md 是唯一入口，详细规范放在 references/ 按需加载——Agent 真正要用的时候才读，不把整个知识库灌进上下文。配套 7 份共享参考清单：definition-of-done（项目级常设过关标准，区别于单任务验收标准）、security-checklist、performance-checklist、accessibility-checklist、observability-checklist、testing-patterns、orchestration-patterns。

此外还有 4 个专家人设（personas）：code-reviewer、test-engineer、security-auditor、web-performance-auditor，可以像召唤独立专家一样让 Agent 切换视角做专项审查。编排规范里还写了条重要规则："personas don't invoke personas"——专家人设不会私自再召唤别的专家，避免 Agent 自我声学的失控膨胀。

安装配置

一条命令全局装（skills CLI 支持 70+ 种 agent）：

# 安装全部 25 个技能（推荐，装完 references/ 清单也齐全）
npx skills add addyosmani/agent-skills

# 不装先浏览，选要哪几个
npx skills add addyosmani/agent-skills --list
npx skills add addyosmani/agent-skills --skill interview-me

只用 Claude Code，走插件市场（更干净，支持升级）：

/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills

如果插件市场 SSH 拉取报错，换 HTTPS 源重试：

/plugin marketplace add https://github.com/addyosmani/agent-skills.git

使用指南

场景一：新功能从白纸到验收，/spec 一把锁住返工

触发条件：开始写任何新功能或重大变更之前。

操作：/spec → Agent 先产出 PRD（目标、命令、结构、代码风格、测试、边界条件），你确认后 /plan 把它拆成带验收标准的小型可验证任务，再动手。

预期结果：开发前双方确认一致；中途改的需求不会变成返工，因为边界在 spec 里已经讨论过。假如需求本身很模糊，先用 /interview-me 让它一次只问一个问题，问到 95% 置信度再动工——这是专门治"Agent 拿模糊需求就开干"的。

场景二：一句 /webperf，把前端性能审计交给专家人设

触发条件：页面性能疑似退化、或上线前必须过性能基线。

操作：直接输入 /webperf，会挂载 web-performance-auditor 人设，按测量优先流程跑 Core Web Vitals 审计、性能剖析、包体分析。

预期结果：得到一份可执行的性能报告，LCP/INP/CLS 的当前值、瓶颈定位、反模式提示都写在里面（不是一句"看起来还行"）。这正是它的性能优化技能"先测量再优化"原则的落地。

场景三：/build auto——半自动驾驶，人只在验收点出现

触发条件：spec 已确定，希望 Agent 自主执行整个实现链。

操作：/build auto → Agent 生成计划并一次批准后，自主逐个实现任务；每个任务仍然单独走 TDD、单独提交，失败或高风险步骤会直接暂停等你确认。

预期结果：命令的定位是"把人从任务与任务之间移开，而不是从验证里移开"——没人盯着每个小步骤，但每一步的验证证据还在，风险步骤照样停下。适合"验证前置已经定义得很清晰"的稳定迭代。

进阶技巧

  1. 让 Agent 自动路由技能：元技能 using-agent-skills 会在会话开始时把收到的活映射到正确的技能流程。它单独不执行任何事，但配合其他 24 个技能后，Agent 会根据"当前在做什么"自动加载对应规范，不必每次都手动敲斜杠命令。
  2. 质疑链用在高风险改动上：doubt-driven-development 针对在途非平凡决策，流程是 CLAIM → EXTRACT → DOUBT → RECONCILE → STOP 五步：声明、抽取、质疑、调和、停下。对生产、安全、不可逆的改动，它能掐掉"差不多就提交了"的冲动；允许的话还能跨模型升级对抗性审查。
  3. 代码健康放在 merge 前：/review 按五轴审查、变更规模约 100 行的节奏控制评审面，严重级别标签用 Nit/Optional/FYI；/code-simplify 则遵循 Chesterton's Fence（不理解为什么存在就不要动）和 Rule of 500，在行为不变的前提下压复杂度。

常见踩坑

单技能安装会缺 references/ 清单：npx skills add ... --skill xxx 只复制 skills/<name>/ 目录本身，仓库级的 references/（definition-of-done、security-checklist 这些共享清单）不会跟过来，指向它们的路径会失效。仓库已开 issue #361。所以装单技能前先想清楚——要么全装，要么直接 git clone 后手工拷技能目录。

装完要重启会话：skill 在会话启动时加载，装完不重启就指望斜杠命令出现，等于白装。Claude Code 里 /plugin 安装完成后确认市场已加载，或干脆开个新会话再测。

今日小结

适合所有让 AI agent 写生产代码的开发者——不管你是用 Claude Code、Codex 还是 Cursor，一条 npx skills add 命令就能装全。配置 1 分钟，换来的是"Agent 再也找不到借口跳过测试、跳过安全、跳过验证"。从 /spec 到 /ship，花这 5 分钟，之后每次 agent 交付都过一遍 Chrome 工程副总裁的验收清单。
