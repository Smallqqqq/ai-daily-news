你花钱买的技术书，读完三个月就忘光了。想把书里的东西喂给 Claude Code，要么把 PDF 整个塞进上下文，200 页吃掉 7.5 万 token，聊两句窗口就满了；要么直接问模型，它对没读过的书只会编。book-to-skill 给了第三条路：把书拆成一套结构化的技能文件，agent 用到哪一章就读哪一章。29.4k stars，MIT，一条命令装好。

它解决什么问题

技术书的宿命是读完即忘。真到要用的时候，你打开 PDF 搜索一个关键词，返回的是二十个页码，你还得自己翻；你把 PDF 丢给 AI 助手，它要么编造，要么回你一句"我没有这本书的内容"；你当年划的重点笔记，躺在某个笔记软件里再也没打开过。

换个思路：把书当知识库看，而不是当文件看。book-to-skill 做的事就是把一本书拆解成 agent 能按需读取的结构：核心框架、决策规则、反模式、术语表、速查表，各归各位。以后写代码时遇到相关问题，agent 自己去翻对应章节，你不用再回去翻书。

核心原理

这个 skill 的设计原则是一句话：提取结构，不做摘要（Extract structure, not summaries）。摘要读完就没了，结构才能被反复调用。所以它提取的是五类东西：具名框架（named frameworks）、可执行原则（actionable principles）、具体技术（techniques）、反模式（anti-patterns）、以及作者的表述精度（voice calibration）。最后这条指的是保留作者原话里的判断句，比如"当 X 超过 Y 时用 Z"，而不是改写成"Z 通常是个不错的选择"。

流程分两半。前半段是确定性的 Python 提取器 scripts/extract.py：文档进来，干净文本和元数据出去，产出一个 workdir，里面有 full_text.txt（各来源用分隔符隔开）和 metadata.json（合并后的页数、字数、估算 token 数、每个来源的明细）。后半段是 agent 按 SKILL.md 的规范做结构化：先读前 8000 字符拿到标题、作者、章节结构，读目录，然后逐章生成文件。

产出物的结构是这样：

文件 内容 体积预算
SKILL.md 核心框架 + 章节索引 + 主题索引，agent 主入口 < 4,000 tokens
chapters/ch01-*.md 逐章文件，含核心思想、框架、心智模型、反模式、要点 800–3,000 tokens/章
glossary.md 术语表，按字母序 ≤ 1,500 tokens
patterns.md 模式库，按 When / How / Trade-offs 三段式 ≤ 2,000 tokens
cheatsheet.md 速查表，优先放决策规则和阈值 ≤ 1,200 tokens

SKILL.md 前重后轻是这里最关键的设计——上下文压缩是从末尾开始截断的，所以最核心的约 2,000 token 框架内容必须放在最前面，章节索引和辅助说明往后放。chapter 文件平时不加载，agent 只在需要时读特定的那一章。

有 50k token 以上的书还有个细节处理：不把全文一次性交给 agent 读，而是教它用 REPL 式访问。wc -w 量体量，grep -n 定位章节偏移，sed -n 'start,endp' 抽片段，带 offset/limit 的 Read 做有界读取。理由很直白：一本 200 页的书约 7.5 万 token，如果每生成一章就重读一遍全文，25 章下来就是 200 万输入 token。

安装配置

跨 agent 的 skills CLI 一条命令：

npx skills add virgiliojr94/book-to-skill

或者手动 clone（会自动注册 /book-to-skill 命令）：

git clone https://github.com/virgiliojr94/book-to-skill.git ~/.claude/skills/book-to-skill

不同宿主的技能目录不一样：Copilot CLI 用 ~/.copilot/skills/，Amp / Codex 用 ~/.agents/skills/，Claude Code 用 ~/.claude/skills/，Hermes Agent 用 ${HERMES_HOME:-$HOME/.hermes}/skills/<category>/。

装完先跑一次体检，看看各格式的提取器齐不齐（这一步只打印报告，不处理文件）：

python3 scripts/extract.py --check

PDF 提取的依赖按书的类型选：纯文字书用 pdftotext（poppler 包，快）或 pypdf / pdfminer.six；带代码、表格、公式的技术书用 docling（结构感知，约 1.5 秒/页）；扫描版 PDF 需要先 OCR 再处理：

ocrmypdf input.pdf output.pdf

使用指南

场景一：把一本技术书变成随叫随到的参考

最基础的用法，给一个路径就行：

/book-to-skill ./designing-data-intensive-applications.pdf ddia

它会先问你一个问题：这本书是技术型（含代码、表格、公式、图表）还是文字型（以叙述为主）？不确定就选"not sure"，会按文字型处理。然后是一轮成本估算确认，列出页数、字数、估算的输入/输出 token、预计耗时和将要生成的文件数。

确认后进入生成流程。以一本 25 章的技术书为例，产出大致是：一个 4,000 token 的 SKILL.md、25 个章节文件（每章 2,000–3,000 token）、加上术语表、模式库、速查表。整个过程在本机跑，不联网。

装好之后，你写代码时随口问：

用 ddia 书里讲的一致性模型，看看我这个分布式锁的设计有什么问题

agent 会自动加载 ddia 技能，去读对应章节，然后基于书里的实际内容回答，依据全是原文。

场景二：先分析再决定要不要花钱生成

一本书值不值得做成技能，你未必一上来就清楚。这时候用分析模式，只跑到结构分析那一步就停：

/book-to-skill ./some-book.epub --analyze-only

或者直接说"just extract"、"先分析一下"。它会输出一份提取报告，最后附一张章节表：

| # | Title | Main Frameworks |
|---|-------|-----------------|
| 1 | Why Data Systems Matter | 可靠性/可扩展性/可维护性三支柱 |
| 2 | Data Models | 关系模型 vs 文档模型决策树 |
...

看完这张表你就能判断：这本书的框架密度够不够高、值不值得花 token 做完整转换。如果报告显示某几章只是车轱辘话，也可以只用后面的增量模式补进来。

场景三：把第二本书折进已有技能

手上有本讲同一主题的旧书，想补充进来，不想另起一个技能：

/book-to-skill ./new-book-on-caching.pdf ddia

slug 匹配到已存在的技能目录时，它会进入 Update / Fold-in 模式，走六步合并流程。先读现有的 SKILL.md 索引和所有章节文件，把新文本分类成"对已有章节的修订"还是"新增内容"。新增章节从现有最大编号往后接着编。术语表重新按字母序合并，每个词条追加章节引用（形如 (Ch 4, Ch 13)）。模式库合并后保持在 2,500 token 以内。最后重新生成 SKILL.md，更新章节数、页数、日期，把新框架折进 4,000 token 的上限里。

结果是一本融合书：同一个主题下两本书的知识互相补位，索引统一。

场景四：把内部文档变成团队技能

这套流程不只吃书。SKILL.md 明确列了其他适用对象：内部文档、品牌 / 设计系统、研究资料集、规范与标准。团队的设计规范散在十几个 Confluence 页面里，或者一套内部 API 标准散在一堆 README 里，都可以打包成一个目录丢进去：

/book-to-skill ./our-api-standards/ our-api-standard

生成出来的技能，团队每个人装同一个版本，agent 给出的建议就遵循同一份规范。

进阶技巧

章节 token 预算分两档。 DEPTH=reference 和 DEPTH=study 生成的内容厚度不同。第 4 步会问你用途：是要"应用框架"、"用书里的心智模型思考"、"当参考资料查"，还是全都要。只有选了纯参考资料才走 reference 档，其余都按 study 档生成。两档差别在预算表里写得很清楚：文字型书的 study 档每章 1,000–1,800 token，比 reference 多出工作示例的篇幅。注意这是目标值，不是上限，写得薄的章节宁可低于下限也不注水。

注入前先过一遍安全扫描。 第 9.5 步会跑 tools/scan_generated_skill.py 扫描生成的技能。这个设计是因为书里的文本会被原样带进技能文件，如果来源文档里混了 prompt 注入内容，扫描会拦下来。非零退出码意味着停下来人工审查，不要直接加载或发布。

发布默认私有。 第 11 步可以一键推到 GitHub，但版权闸门在：书衍生出来的技能默认建私有仓库，除非来源是你自己的作品、开放许可、或者明确获得再分发授权。可见性判断也极其严格，只有回答里出现光秃秃的 "public" 这个词才建公开仓库，任何转述、整句话、沉默或者推测，一律落到 --private。

常见踩坑

我通读了一遍它的 SKILL.md，这份文档对边界情况的交代比预想的细，下面几条是最容易踩的。

扫描版 PDF 直接进去是空的。 提取器拿到的是图片层，OCR 之前没有文本可提。先跑 ocrmypdf input.pdf output.pdf 补一层文字，再交给 book-to-skill。

含大量代码和表格的技术书，别用默认提取器。 默认的文本提取会把表格结构压平、代码缩进吃掉。第 1.5 步那个问题老老实实选"Technical"，它会切到 docling 做结构感知提取，代价是约 1.5 秒/页。一本 400 页的书大概多花十分钟，但代码和公式能保住。

docling 没装时不会报错，会静默降级。 --install-missing ask 会在缺少更好的提取器时询问你，但非交互式会话（比如你在脚本里跑）默认走 fallback，不装也不提示。跑之前先 --check 看一眼，比事后发现表格全坏了要省事。

workdir 别手动删错。 每次运行会产生一个 <tempdir>/book_skill_work-<pid>/ 工作目录，清理逻辑只删本次运行创建的那个（从输出的 Workdir -> 行或 metadata.json 里的 workdir 字段取）。早期版本的固定路径 book_skill_work 已经废弃，现在是空操作，别去找它、也别删它以外的东西。想固定工作目录位置就设环境变量 BOOK_SKILL_WORKDIR。

今日小结

book-to-skill 适合这样的人：书架上有几本翻过但记不住的技术书、团队规范散在一堆文档里没个准话、或者你已经在用 Claude Code 但发现它对你所在领域的专业内容只能泛泛而谈。配置时间取决于书的类型：纯文字书装完就能跑，技术书多花几分钟装 docling。换来的是一个随叫随到的专业参考库，问什么，agent 去翻对应的章节，用书里的原话回答你，而不是编一段听起来差不多的东西。
