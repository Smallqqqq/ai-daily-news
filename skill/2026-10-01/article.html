给 coding agent 写代码的人多半熟悉这个循环：改完，push，等几分钟 CI 跑完，红了，翻日志，改一行，再 push，再等几分钟。每次重试都从零开始，重新 checkout、重新装依赖、重新 build，哪怕你只改了一个测试断言。

local-ci 是 RedwoodJS 团队做的本地 CI 运行器：把你的 GitHub Actions workflow 原样搬进本机 Docker，失败就原地暂停，修完只重试失败的那一步。799 stars，README 第一句就写着 "Pause on failure. Fix and retry — before you commit, before you push."

![local-ci 命令行演示](./local-ci-demo.gif)

它解决什么问题

CI 是最后一道门，职责是拦下不该上线的提交。但当 agent 也在提交代码时，这道门被当成调试器用了。

作者在 Show HN 里算过一笔账：GitHub Actions 通常能进研发团队支出前五，agent 的提交量再叠上去，账单翻倍几乎是必然。更隐蔽的成本是日志——云端 CI 的失败日志又长又碎，agent 读一次要烧掉大量 token，读完还不一定能定位到那一行真实报错。

本地跑 CI 的老前辈是 act（72k stars），它用兼容层重新实现每个 action，行为偏差说不清。失败后想重试，还得从头跑。

local-ci 换了条路。

核心原理

市面上「本地跑 Actions」的工具，大多在 actions/runner 外面包一层兼容层。local-ci 走的是另一条路：替换 runner 交谈的云端 API。GitHub 官方 runner 启动后本来要连 github.com 拉作业、报进度、传制品、读写缓存，local-ci 在本机把这套服务全实现了一遍——Twirp 端点、Azure Block Blob 制品协议、缓存 REST API。作业指令和云端一模一样，执行的是官方 runner 二进制，行为逐位一致（README 原话 bit-for-bit），actions/checkout、actions/setup-node、actions/cache 即插即用。

缓存零往返。 依赖装在本机文件系统上，没有上传下载。第二次跑时，pnpm/Yarn/Bun 的 node_modules 从锁文件对应的不可变快照按 copy-on-write 克隆，GitHub 上要跑几分钟的依赖安装在本地几秒完成。

失败暂停，容器不销毁。 第 6 步挂了，容器带着全部状态停在那里：环境变量、装好的工具、中间产物原封不动。你在宿主机改文件，改动同步进容器，重试只跑那一步。

跑的是工作区，不是提交。 不需要 commit 或 stash，未提交的改动直接进 CI。对 agent 这点很关键：改完文件就能验证，验证通过再提交。

给 agent 的接口是 NDJSON 事件流。加 --json（或 LOCAL_CI_JSON=1），stdout 每行一个 JSON 对象，run.start/job.start/step.start/step.finish/run.paused/run.finish 事件带 schemaVersion，不用正则去刮人类可读的输出。暂停时如果 stdout 不是 TTY，前台进程以退出码 77 退出，调用方据此接续。

安装配置

前置条件两个：Docker（macOS 用 OrbStack 或 Docker Desktop，Linux 用原生 Docker 或 Docker Desktop）和 Node 环境。

# 跑当前分支全部相关 workflow
npx run-local-ci run --all

# 或指定单个 workflow
npx run-local-ci run -w .github/workflows/ci.yml

装成 Agent Skill，让 Claude Code / Codex / Cursor 认识这个命令（支持 40+ agent 宿主）：

npx skills add redwoodjs/local-ci --skill local-ci

然后在 CLAUDE.md / AGENTS.md 里加一段约定，agent 会在报告「干完了」之前先自己跑一遍：

## CI

Before completing any work, run the `local-ci` skill to validate your changes locally. If it fails, fix the issue and re-run. Do not report work as done until it passes.

secrets 按顺序从 .env.local-ci、shell 环境变量、--github-token 里取，workflow 文件不用改。

使用指南

场景一：agent 提交前自检

这是它设计时的第一目标。workflow 文件一行不改，agent 在 --json 模式下吃事件流：

npx run-local-ci run --all --json

失败信息定位到 step.finish 里 status: "failed" 的那条，带 job、step 名和 index。agent 知道哪一步挂了，去读那一步的日志输出，然后改代码。

场景二：失败暂停，原地重试

人肉调试工作流时用这个：

npx run-local-ci run -w .github/workflows/ci.yml --pause-on-failure

挂了之后容器活着，改文件，然后只重试失败的那一步：

npx run-local-ci retry --name <runner-name>              # 默认只重跑失败的那一步
npx run-local-ci retry --name <runner-name> --from-step 4  # 从第 4 步往后重跑
npx run-local-ci abort --name <runner-name>              # 不修了，拆掉容器

官方推荐配一个习惯：先 commit 当前状态再跑。commit 变成存档点，如果 agent 越改越糟，可以退回去换一种修法。

场景三：工作区直接跑，不提交

npx run-local-ci run --workflow .github/workflows/ci.yml

未提交的改动、没 stash 的文件直接进 CI。适合改到一半想验证 lint 或单测。

场景四：预热依赖，并行 job 不重复装

workflow 里有多个 job 都要 pnpm install 时，先跑一个一次性预热 job：

- id: install
  run: pnpm install --frozen-lockfile
local-ci run --all --prewarm-through .github/workflows/ci.yml:test:install

预热 job 跑完把快照原子发布，后面每个并行 job 从快照克隆，各自拿到私有的可写 node_modules。写进 .env.local-ci 就每次自动生效。

进阶技巧

变量直接从 GitHub 拉。 本地跑时 workflow 里的 ${{ vars.FOO }} 会缺值报错，把 GitHub 上已有的变量导下来：

gh variable list --json name,value --limit 1000 | local-ci run --all --var-file -

--var-file - 读 stdin，一条 pipe 解决，不用手工维护第二份变量清单。

缺工具就加镜像。 默认 runner 镜像没有构建工具链，报 missing tool 时建一个 .github/local-ci.Dockerfile，local-ci 自动检测、按内容哈希缓存：

FROM ghcr.io/actions/actions-runner:latest
RUN sudo apt-get update \
 && sudo apt-get install -y --no-install-recommends <your-packages> \
 && sudo rm -rf /var/lib/apt/lists/*

接远程 Docker。 本机不想装 Docker 时把 daemon 指向别的机器：LOCAL_CI_DOCKER_HOST=ssh://user@remote-server。它不认标准的 DOCKER_HOST——你 shell 里设了的话 local-ci 会直接报错让你改名，这是故意的，避免和 docker CLI 互相打架。

常见踩坑

Windows 有两个限制。 runs-on: windows-* 的 job 不支持，直接跳过并给出原因；官方前置条件列的是 macOS 和 Linux 主机，Windows 主机要跑得靠 Docker Desktop 提供 Linux 容器，文档没有背书。macOS job 则要求 Apple Silicon 主机加 tart，其他机器跳过。

还在 0.x 阶段。 npm 包 0.18.0，API 表面还在动。项目从 Agent CI 更名而来，@redwoodjs/agent-ci、AGENT_CI_* 环境变量、.env.agent-ci 在这轮 0.x 内仍然兼容，新配置统一用 LOCAL_CI_*。

许可不是标准开源。 FSL-1.1-MIT（Functional Source License），内部使用和商用开发都没问题，但不能拿它做与 local-ci 竞争的商业产品；发布满两年自动转 MIT。

官方镜像很裸。 ghcr.io/actions/actions-runner:latest 只有 runner agent、Node、git、curl、jq、unzip。GitHub 托管 runner 里的 python3 和构建工具链一律没有，第一次跑大概率要配自定义镜像。

同类技能对比

local-ci（今日推荐）

安装方式：npx run-local-ci run --all

核心特点：官方 runner 原样执行，失败暂停原地重试，NDJSON 事件流

适用场景：agent 提交前自检、本地调试 workflow

热度：⭐ 799

act

安装方式：brew install act / winget install nektos.act

核心特点：兼容层重实现各 action 步骤

适用场景：偶尔本地跑跑 workflow

热度：⭐ 72,178

GitHub Actions 云端

安装方式：—

核心特点：权威门禁，环境最真实

适用场景：最终验收

热度：—

act 解决「我想在本地跑一遍」，local-ci 解决「这一遍跑挂了之后，我要在几秒内重试到绿」。前者是替代品，后者是反馈环；它把官方 runner 原封不动搬进来，就为了让你不用怀疑行为差异，只专注修 bug。

⭐ 799 · v0.18.0 · FSL-1.1-MIT · https://github.com/redwoodjs/local-ci

今日小结

如果你的 workflow 主要跑在 ubuntu-latest 上，手里有 Docker，local-ci 值得花十分钟装上。我的建议是先 npx run-local-ci run --all 本地跑通一次，再把 skill 和 CLAUDE.md 约定加上；之后 agent 每次说「改完了」，先本地绿一遍再 push，远程 CI 回归门禁的本职。

省时间只是一半。以前 agent 每轮修复都要推一次脏提交才能拿到 CI 反馈，历史里全是 "fix ci"、"fix ci again"；现在这些循环都发生在本地，推到远端的每个提交都已经是绿的。
