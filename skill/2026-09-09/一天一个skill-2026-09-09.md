# ruflo — 给 Claude Code 装上智能体调度层

  模型负责"写代码"，但这些代码往往要改很多文件、跨多个仓库、还要跑测试、审安全——一个 agent 干不完，一堆 agent 又没人管。ruflo 就是那个"管理层"：100+ 专职 agents、可编排的 swarm、跨会话持久记忆，全部通过一套命令装进 Claude Code。71.7k stars、8.5k forks，本周 GitHub 上前排的多 agent 编排项目，今天值得花 5 分钟装上。

### 它解决什么问题

  单个 Claude Code 会话有两个硬边界：上下文窗口装不下整个仓库，会话结束记忆清零。工程上为了绕过边界，要么写长 prompt 教会模型重复劳动，要么人肉切任务、人肉记进度。

  ruflo 的思路是把"调度"从人身上搬走：任务来了先分解，分给多个专职 agent（写码、评审、测试、安全各司其职），有 swarms 协调它们并行，干完的结果沉淀进 HNSW 向量记忆，下次问起"上次那口矿到哪了"直接就检索出来。

### 核心原理

  一句话定义：Agent = Model + Harness。模型负责生成，harness 负责工具、记忆、循环、沙箱与控制。ruflo 是挂在 Claude Code 上的 meta-harness。

  安装后在项目里生成 `.claude/`、MCP 配置和 hooks 三样东西。MCP server 是一个长驻 Node 进程（`npx ruflo@latest mcp start`），暴露 314+ 个工具，按命名空间组织：`mcp__claude-flow__memory_*`（检索/写入记忆）、`swarm_*`（蜂群拓扑）、`agent_spawn`（拉起专职 agent）、`task_*`（任务生命周期）、`intelligence_*`（RETRIEVE → JUDGE → DISTILL → CONSOLIDATE 四步管道）。hooks 负责在会话前后自动触发后台 worker（默认 12 个：审计、优化、测试缺口扫描等）。记忆不是 JSON 文件，是 HNSW 索引的向量库，召回不做暴力遍历。

### 安装配置

  两条路，按需选一条：

  **只装核心 skill（1 个文件，最小起步）：**
  ```bash
  npx skills add ruvnet/ruflo --skill ruflo --yes
  ```

  **完整平台（MCP + hooks + 后台 worker）：**
  ```bash
  # 1. 初始化：项目里生成 .claude/、MCP 配置和 hooks
  npx ruflo@latest init

  # 2. 健康检查：Node 20+ / npm 9+ / MCP server / 记忆库 / API key 一次自检
  npx ruflo doctor --fix

  # 3. 看当前项目适合哪些插件
  npx ruflo discover-plugins
  ```

  如果用 Claude Code 插件市场路径（只装 slash commands + agent 定义，最轻）：

  ```text
  /plugin marketplace add ruvnet/ruflo
  /plugin install ruflo-core@ruflo
  /plugin install ruflo-swarm@ruflo
  ```

  Windows 用户注意：`curl | bash` 脚本只在 Git Bash/WSL 下走，日常用 `npx` 三连即可。

### 使用指南

#### 场景一：跨仓库功能点改动，一个 swarm 并行推进

  触发条件：改的是横跨两三个仓库的联动改动（比如公共 SDK + 两个下游服务）。

  ```bash
  npx ruflo init
  # 在对话里描述任务，让它自己拉起 swarm：
  # "用 swarm 协调，把 read-timeout 从 5s 改成 10s 涉及的所有仓库都改掉，先出计划再动手"
  ```

  预期结果：ruflo 把任务拆成子任务，多个 agent 按拓扑（层级/网格/自适应）并行执行，改动通过 federation 跨仓库下发，你最后只需在汇总节点审查 commit。

#### 场景二：深任务分解（SPARC 方法论）+ 分阶段执行

  触发条件：需求是"给这套服务加鉴权"，单轮对话说不清、一次改不完。

  ```bash
  # 用内置的 goal-planner 做 GOAP A* 规划，输出可验证的目标序列
  npx ruflo discover-plugins   # 先确认 sparc 插件已启用
  ```

  预期结果：任务被拆成"识别所有路由 → 加中间件 → 补单测 → 扫安全盲点"的 DAG，每步有验收标准，agent 完成一步才推进下一步，中途不会自己"创造需求"。

#### 场景三：跨会话记忆——昨天分析过的代码，今天直接问

  触发条件：两个会话之间隔了十几个小时甚至两天，中间没有任何笔记。

  ```text
  对话开头直接问："回一下 ruflo 记忆里关于 payment-service 超时重试的分析"
  ```

  预期结果：`mcp__claude-flow__memory_*` 从 HNSW 向量库里语义检索到上次的结论，带来源（哪个会话、哪个文件）返回，不用把线索写在 README 或者聊天框里。

#### 场景四：安全审计 + 测试缺口自动扫描

  触发条件：合并前想把"潜在漏洞"和"没测到的分支"捞出来。

  ```bash
  # security-audit 插件：提示注入、PII 门控、CVE 修复建议
  npx ruflo plugins list
  # testgaps 后台 worker 会在会话间自动标记未覆盖的测试路径
  ```

  预期结果：审计结果落进对话，指向具体文件和行；测试缺口作为后台任务生成清单，merge 前逐条关掉。

### 进阶技巧

  **`--pin` 锁定 + verify 校验供应链。** 团队多个项目共用一个 ruflo 时，用 `ruflo verify` 对照签名 witness 验证安装字节；升级前先对比，避免供应商悄悄塞东西。

  **只装需要的插件，别一次 --all。** `npx ruflo plugins list` 逐个看，需要才 `plugins install @claude-flow/plugin-xxx`。全量装把 MCP 工具从几十个拉到 314 个，提示词空间被占满，选工具的准确率反而会掉。

### 常见踩坑

  **小改动别上 swarm。** 官方 skill 明确写了 do-not：单文件改动、一次对话能改完的 bug，swarm 的调度开销远大于收益——多 agent 的串行 handoff 比单 agent 直线干还慢。让 ruflo 自己判断：它会在任务复杂度不够时拒绝起 swarm。

  **Windows 上 curl | bash 会失败。** 那个脚本是 POSIX 的，PowerShell 里跑 → 语法错误或权限拒绝。用 `npx ruflo@latest init` 一条命令，效果一致。

  **命令名两代混用。** ruflo 前身是 claude-flow（npm 包 claude-flow、@claude-flow/cli 仍兼容），网上教程一半在教 `npx claude-flow ...`，都是同一套东西，看到别慌，功能没区别。

  **插件功能需要 API key。** 记忆检索、向量库、部分多 provider 路由要配 key，否则 doctor 会标红。`npx ruflo doctor --fix` 能指出来缺哪个。
