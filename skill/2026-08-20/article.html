它解决什么问题

上下文窗口是 AI 编程助手的硬通货，而工具输出是最大的挥霍者。读一个文件、跑一条命令、抓一个页面，原始数据整块进窗口，模型只需要其中几行。用过的 25K tokens（Claude Code 的截断上限）就永远占着窗口，直到 compaction 一刀切掉。切完之后模型忘了自己在改哪个文件、任务做到哪一步。

作者 mksglu 给自己的 Claude Code 会话装完这套东西后，工作 6 倍时长才开始退化，于是开源。2 月上线，两个 Show HN 帖子，其中一个拿到 570+ 分冲到 HN 榜首。现在 19.7K star、1.4K fork，支持 17 种 agent 平台。

核心原理

context-mode 是一个 MCP 服务器加一组 hooks，全部机制不调一次 LLM，纯算法。

第一层，沙盒执行。ctx_execute 在独立子进程里跑代码（12 种语言运行时），只把 stdout 送回上下文。原始数据（日志、API 响应、快照）留在沙盒里。ctx_execute_file 处理文件同理，45KB 的文件只回 155 字节摘要。

第二层，全文索引。ctx_index 按标题切块（代码块保持完整）存入 SQLite FTS5 虚表，搜索走 BM25 相关度排序，索引时做 Porter 词干化，running 和 ran 命中同一个词干。需要细节时 ctx_search 按需取回，原始页面永不进窗口。ctx_fetch_and_index 把 URL 抓取、转 markdown、切块、索引连成一条流水线，24 小时 TTL 缓存。

第三层，会话续命。每次文件编辑、git 操作、任务、错误、用户决策都记进项目级 SQLite。compaction 发生时不是把旧数据倒回窗口，而是 FTS5 索引加 BM25 检索只取相关部分。配合 --continue 参数跨会话续接；不加 --continue，上一个会话的数据立即删除。

第四层，PreToolUse hook 自动路由。钩子匹配 Bash、Read、Grep、Glob、WebFetch 等内置工具，把"读文件数行数"这类操作自动改道 ctx_execute。README 里的对比：47 次 Read 700KB，1 次 ctx_execute 3.6KB。

安装配置

Claude Code 全自动方式（插件市场，带 hooks 和 slash 命令）：

/plugin marketplace add mksglu/claude-context-mode
/plugin install context-mode@claude-context-mode

只想先试试工具、不要自动路由：

claude mcp add context-mode -- npx -y context-mode

Codex CLI 同样一条命令：

codex mcp add context-mode -- npx -y context-mode

插件版额外注册 7 个 slash 命令：/context-mode:ctx-stats 看省了多少 token，ctx-doctor 诊断环境，ctx-index/ctx-search 管理索引，ctx-upgrade 升级，ctx-purge 清空，ctx-insight 打开团队分析面板。

使用指南

场景一：长会话里分析日志和构建输出

触发条件：agent 要读 error.log、构建输出、测试报告这类大文件。操作：不直接 Read，改用 ctx_execute_file 处理，让它 grep 关键错误、统计出现次数，只回结果。预期：45KB 日志只占 155 字节窗口，剩下的地方留给真正的工作。

场景二：大代码库的统计型审计

触发条件："统计每个文件的函数数""找出所有 TODO""分析依赖树"。操作：让模型写一段脚本交给 ctx_execute 跑。模型在这里是代码生成器，不是数据处理器，50 次 Read 换成 1 次执行。官方示例：

ctx_execute("javascript", `
  const files = fs.readdirSync('src').filter(f => f.endsWith('.ts'));
  files.forEach(f => console.log(f + ': ' + fs.readFileSync('src/'+f,'utf8').split('\n').length + ' lines'));
`);

预期：700KB 的读取压成 3.6KB 的结果输出。

场景三：调研外部资料

触发条件：要读官方文档、HN 帖子、GitHub Issue 列表做技术调研。操作：ctx_fetch_and_index 抓取并索引（可并发 1-8 个 URL），然后 ctx_search 多查询一次取回。预期：原始页面零入窗，索引只占 40 字节，需要哪段搜哪段。

进阶技巧

批量执行并发：ctx_batch_execute 一次跑多条命令加多组搜索，可选 concurrency 1-8 并发 I/O 密集任务，实测 986KB 压到 62KB。

Playwright 组合技：浏览器快照先落盘（browser_snapshot 带 filename 参数），再交给 ctx_execute_file 或 ctx_index 处理。快照这种 56KB 的大户最值得改道。

statusline 集成：装完在 Claude Code 状态栏显示"本次会话已省 $X · 累计 $Y · 效率 Z%"，省钱看得见。

常见踩坑

第三方 MCP 工具的输出拦不住。PreToolUse 钩子只匹配 Bash、Read、Grep、Glob、WebFetch、WebSearch 这类内置工具；MCP 响应走 JSON-RPC 直达模型，没有 hook 能在入窗前压缩它。98% 的节省只对内置工具和 CLI 包装生效。自建 MCP 时把思路搬到服务端：返回紧凑摘要，加可查询的全量存储。

短任务反而更贵。有用户拿自己的 SaaS 项目做了三组对照实测（naramalkoht.com 有完整数据）：上下文窗口确实省了 37K tokens，但 plan 用量反而上涨。MCP 工具定义全程常驻窗口，每次调用还有往返开销，一次大审计光工具调用就吃掉 86K tokens。结论：单文件小改别开，多文件、长会话、大代码库才是主场。

路径必须绝对。早期版本索引按相对路径解析，踩过"索引 8.1KB 只留住 0.5KB"的坑。传绝对路径；升级插件后该问题已修复，习惯保留。
