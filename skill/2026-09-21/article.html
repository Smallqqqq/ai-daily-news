2026-09-21

AI 修 bug 的方式一直是：加几行 print，跑一遍，猜一下，再改。它能读代码、能推理，但看不到运行时的变量到底长什么样。debug-skill 把 Debug Adapter Protocol 包成一个 CLI，让 agent 真的能下断点、单步执行、检查调用栈。

![debug-skill 演示](./debug-skill-demo.gif)

它解决什么问题

一句话能说清：agent 平时是在读代码，不是在跑代码。

遇到崩溃、异常、输出不对的时候，它手里只有两条路。要么加 print 语句反复跑，要么纯靠静态推理猜一个原因。前者慢且脏，改一次跑一次；后者经常猜错，尤其在涉及多个模块、状态在几层调用之间被改坏的时候。人类开发者早就不用这种办法了，我们用断点。

这个技能就是把断点还给 agent。它接入的是真正的调试器进程，agent 拿到的是那一刻内存里真实的值。

适合的场景很具体：偶发 bug 需要特定状态才复现、某个值在哪一层调用被改坏、抛异常时想看看当时完整的局部变量。这些用 print 做起来都很别扭。

核心原理

仓库里有两个东西，别搞混。

一个是 Claude Code 技能本身（debugging-code），教 agent 调试的工作流：断点该下在哪、怎么沿调用栈向上追、什么时候该停下来重新想。另一个是配套的 dap 命令行工具，这是实际干活的部分。

链路是这样的：

dap <cmd>  →  Unix socket  →  Daemon  →  DAP 协议  →  debugpy / dlv / js-debug / lldb-dap  →  你的程序

中间架一层守护进程，是因为调试会话本身有状态，程序得停在断点上等你。如果每条命令都重新起一个调试器，程序就重启一次，状态全没了。守护进程负责把这个会话挂着，CLI 每次只发一条命令、拿回一份完整快照。

这个设计的一个直接后果是无状态 CLI。任何 agent 只要能跑 bash 就能操作调试器，不需要维持长连接，不需要理解 DAP 协议。dap 在 dap debug 时自动拉起守护进程，dap stop 或者空闲 10 分钟后自动结束。

执行类命令（debug、continue、step）返回的是完整上下文：当前位置、源码、局部变量、调用栈、程序输出。agent 不需要额外再问一轮。

还有个细节值得单独说：命名会话。--session agent1 可以让多个 agent 各自挂一个调试会话，互不干扰。这是为并行 agent 编排准备的。

语言支持靠自动识别，按文件扩展名挑后端：

语言 调试后端 自动识别
Python debugpy 是
Go dlv（Delve） 是
Node.js / TypeScript js-debug 是
Rust / C / C++ lldb-dap 是

安装配置

Claude Code 走插件市场，两条命令：

/plugin marketplace add AlmogBaku/debug-skill
/plugin install debugging-code@debug-skill-marketplace

然后装 dap CLI。三选一，按你的系统挑：

# macOS / Linux 一行脚本
bash <(curl -fsSL https://raw.githubusercontent.com/AlmogBaku/debug-skill/master/skills/debugging-code/scripts/install-dap.sh)

# macOS 用 Homebrew
brew install AlmogBaku/tap/dap

# 有 Go 环境
go install github.com/AlmogBaku/debug-skill/cmd/dap@latest

Windows 用户走 releases 页面下预编译二进制，或者用 Go 那条。

如果你用的是 Codex、Cursor、OpenCode 这些，用 skills.sh 装：

npx skills add AlmogBaku/debug-skill

或者直接把 skills/debugging-code/ 目录拷进对应 agent 的 skills 目录。

使用指南

场景一：用一个条件断点抓住偶发 bug

经典的场景：某个函数在绝大多数输入下正常，只有特定数据才出问题，你没法手动构造那个状态。

别设普通断点，设条件的。语法是 "文件:行号:条件"，引号必须带：

dap debug app.py --break "app.py:42:i == 100"
dap debug bank.py --break "bank.py:68:balance < 0"

让 agent 直接问："用条件断点抓住 balance 变成负数的第一时刻，然后把当时的完整局部变量给我看。"

agent 会拿到断住那一瞬间的所有状态，而不用先跑一百次。

场景二：追一个值是"在哪一层被改坏的"

假设 compute() 返回了 None，但你翻代码看不出哪一步出的问题。这类 bug 用 print 追起来最痛苦，因为你不知道该在哪几个地方加。

做法是沿调用栈向上走，找到值第一次出错的那一帧：

dap eval "result" --frame 0     # 当前帧：已经是 None
dap eval "result" --frame 1     # 上一帧：还是正常值
dap eval "input" --frame 1      # 再查上一帧的入参

技能文档里给的原则是：一直向上追，直到你找到这个值第一次变错的那一层。那一层就是问题所在，不是它显形的那一层。

这一步的关键在于 --frame N。没有这个参数，你只能在最内层干瞪眼。

场景三：多个 agent 同时调试不同服务

微服务或者多进程场景，几个 agent 各自负责一块。默认情况下它们的调试会话会打架。

用命名会话隔离：

dap debug app.py  --session agent1 --break app.py:10
dap debug main.go --session agent2 --break main.go:8
dap stop --session agent1

每个会话有自己的守护进程和 socket，互不干扰。编排型 skill（比如 ruflo、oh-my-claudecode 那类）配上这个能力，可以让每个子 agent 独立调试自己负责的那部分。

场景四：接一个已经在跑的进程

程序已经起来了，或者跑在容器里，你不想重启它。

dap debug --attach container:5678 --backend debugpy --break handler.py:20
dap debug --pid 12345 --backend debugpy

这一条对排查生产环境行为差异特别有用。你连上去看的是真实进程的真实状态，不是一个复现出来的近似环境。

进阶技巧

用 restart 而不是重新 debug。改完代码想再跑一遍的时候，dap restart 会保留你这次会话里对断点的所有增删改。用 dap debug 重来一遍，这些断点配置就没了。调试过程中往往断点位置要挪好几次，这个差别很实在。

在重启之前，先用 eval 验证修复假设。程序还停在断点上的时候，你可以直接对着当前状态试算：

dap eval "len(items) == 0"
dap eval "[x for x in items if x is None]"

如果假设成立，再改代码、再 restart。这样一轮里能验证掉好几个猜想，比"改一次跑一次"快得多。

注意别在 eval 里放有副作用的表达式。技能文档明确不建议。你的表达式会在真实进程里真的执行，改数据、发请求、写文件都会生效。

两条来自技能文档的原则，价值超过任何命令。一条是 "Two strikes, rethink"：同一个 bug 试了两次修不好，立刻停下重新想，别接着试第三次。另一条是 "如果你已经连续单步超过 3 次，你需要的是一个断点，不是更多单步"。这两条其实是在防 agent 最容易犯的毛病：在一个错误的方向上越走越深。

常见踩坑

调试后端要单独装。dap 自己不包含 debugpy、dlv 这些东西，它是去调用系统里已有的。跑起来报找不到后端的话，看仓库里的 references/installing-debuggers.md，每个语言的装法都写了。

macOS 上用 dlv --pid 附加 Go 进程会失败。这是 System Integrity Protection 的限制，不是 bug。README 里明确标了这个坑，需要关掉 SIP 才能用 PID 附加的方式调试 Go 进程。

调试会话会留守护进程。正常结束会自动清理，异常中断的话进程可能还挂着。手动清 dap stop，或者等 10 分钟空闲超时自动退出。

同类技能对比

debug-skill（今日推荐）

安装方式：/plugin install debugging-code + 装 dap

核心特点：真接入调试器进程，断点/单步/调用栈全套

适用场景：偶发 bug、值在哪层被改坏、附加运行中进程

热度：⭐ 323

Superpowers 的 systematic-debugging

安装方式：/plugin install superpowers

核心特点：方法论纪律：四阶段流程 + 三次失败强制停手

适用场景：防止 agent 乱改代码，靠推理定位

热度：⭐ 高（整套框架）

IntelliJ IDEA ij-debugger

安装方式：需 IDE 2026.2+ 并开放 MCP

核心特点：IDE 内置调试器暴露给外部 agent

适用场景：已经在用 JetBrains 全家桶的团队

热度：官方内置

传统 print / 日志诊断

安装方式：无需安装

核心特点：改代码加输出，重跑

适用场景：简单问题、一次性脚本

热度：—

选 debug-skill 的理由在于它补的是能力缺口而不是加约束。systematic-debugging 那类技能是在教 agent「别乱猜」，这个技能是让 agent 不用猜。两者其实不冲突，一个管纪律，一个给工具，配着用效果更好。IDE 方案的问题在于绑死在 IDE 上，命令行和 CI 环境里用不了。

还有一个现实的考虑：agent 调 bug 时的往返次数直接决定你的 token 花费。让它在真实状态上做一次 eval，比让它改代码重跑三轮便宜得多。

今日小结

如果你经常让 AI 修 bug，尤其是那种"偶尔才复现"、"不知道哪一层出的问题"的类型，这个技能装上去的收益是立刻的。配置大概十分钟：插件两条命令，dap 一条命令，再加一个对应语言的调试后端。

换来的是 agent 的工作方式从"加 print 猜"变成"下断点看"。它省掉的不只是时间，还有来回改代码引入的新问题。
