2026-08-26

你手头有一个自己搭的 AI agent：写 SQL 的、查文档的、回复工单的。它不算差，但 benchmark 分数卡在 70% 上不去，prompt 改了七八版，效果忽上忽下，每次调完你都不知道是改对了还是碰巧。微软开源的 agent-lightning 上周发布了一个新东西：一个 SKILL.md，装进你的 Claude Code 或 Codex，让 coding agent 替你干这件事——它不靠感觉调参，靠 benchmark 分数说话，一轮轮测、一轮轮改，直到准确率、成本、延迟、可靠性之间达到你设定的平衡。17.8k stars，MIT 协议，微软官方维护。

它解决什么问题

Agent 调优一直处在手工时代。改 prompt 全凭经验，加工具靠猜，换模型拍脑袋，每调一版都要自己跑一遍评测看分数，过程琐碎而且没有系统记录：上一版为什么比这一版好？哪个改动起了作用？说不清。agent-lightning 的 skill 把这件事变成了一套带测量、带迭代、带记录的标准流程。

它和这个仓库的母体要分开看。microsoft/agent-lightning 本身是一个 3,500 行的轻量 Agentic RL 训练框架，用强化学习训练 agent，那个需要 GPU 集群。而 v1.0.1 发布的 Agent Lightning Skill 是仓库里新增的一个技能文件，装进 coding agent 之后，教它按照同一套优化方法论去调优其他 agent：框架负责大规模训练，skill 负责把优化流程变成 coding agent 能执行的 SOP。没有 GPU 也能用 skill，它输出的是可验证的改进，不是训练好的权重。

核心原理

skill 把 agent 优化建模成一个测量驱动的循环，每一步都有客观分数兜底：

  1. 定义可测量的 benchmark。没有指标就不动手。评测集可以是现有的（SWE-bench、GSM8K），也可以是任务专属的一组用例。分数是唯一的裁判。
  2. 盘点优化面。skill 引导 coding agent 逐一检查五个可调维度：prompts（指令措辞与结构）、tools（工具选择与调用方式）、workflows（多步流程编排）、models（模型档位与路由）、reasoning settings（推理深度、采样参数）。
  3. 单变量改动。一次只改一个维度，跑 benchmark，记录分数变化。这解决了"改了七八处，不知道哪处起作用"的老问题。
  4. 四维权衡。每个改动同时看准确率、成本、延迟、可靠性四个数。准确率涨了 2% 但成本翻倍，这个改动留不留，由你定的阈值决定，skill 只负责把数据摆出来。
  5. 迭代到收敛。改到连续两轮没有显著提升为止。整个过程有记录，可回溯。

方法论来自框架那侧被验证过的东西：官方报告里，一个 Qwen3.5-9B 的 coding agent 只用 6K 训练样本，SWE-bench Verified 就从 41.8% 提到 56.4%。skill 把这套"测量、迭代、权衡"的纪律搬到了 prompt 层优化上，区别是它不训练权重，它调的是 agent 的配置。

安装配置

一条命令。需要 gh CLI v2.90.0 或更高版本（gh skill 是 2026 年 4 月加入 GitHub CLI 的新命令，公开预览阶段）：

# 检查 gh 版本，低于 2.90.0 先升级
gh --version

# 安装到 Claude Code（用户级，所有项目可用）
gh skill install microsoft/agent-lightning agent-lightning --agent claude-code --scope user

# 或者装给 Codex / GitHub Copilot
gh skill install microsoft/agent-lightning agent-lightning --agent codex
gh skill install microsoft/agent-lightning agent-lightning --agent copilot

安装后重启 agent 会话。skill 会把来源仓库、ref、commit SHA 写进 SKILL.md 的 frontmatter，谁装的、装的哪个版本，一路可查。

使用指南

场景一：给卡分的自建 agent 做一轮系统调优

你有个 LangChain 搭的客服工单分类 agent，测试集准确率 72%。把 agent 代码和测试集路径给 Claude Code，说一句"用 agent-lightning 的流程优化这个 agent，目标准确率 80%，成本不能超过现在的 1.2 倍"。skill 会让 coding agent 先确认 benchmark 能跑通，然后逐维度试：改分类指令的措辞、精简工具描述、试更小一档的模型加更长的推理参数。每轮改动都有分数和成本记录，最后给出一份改动清单和最终分数。

场景二：成本超支，在不掉分的前提下省钱

Agent 跑得好但账单难看。常见的隐性成本点：prompt 里塞了太多 few-shot 示例、每个子任务都调了旗舰模型、工具输出整个灌进上下文。skill 的流程在这里的价值是量化：把"感觉贵"变成"这条 prompt 平均 3,200 token、这个子任务占了总成本 41%"，然后有针对性地砍。砍完跑 benchmark 确认分数没掉。

场景三：多 agent 系统里只优化拖后腿的那一个

planner + executor + verifier 三个 agent 的组合，verifier 的误放率太高。skill 支持选择性优化：把 verifier 单独拎出来，定义它专属的评测集，只调它的 prompt 和 reasoning settings，另外两个 agent 完全不动。这是手工调优最难做到的：牵一发不带动全身。

进阶技巧

调优记录本身就是资产。让 coding agent 把每轮改动、分数、成本存成结构化记录，攒上几轮后，你就能看出自己 agent 的敏感点：哪些维度改动收益大、哪些纯属折腾。这套记录以后喂给别的优化任务，就是现成的先验。

skill 和框架可以接力。先用 skill 做 prompt 层调优，把 benchmark 和数据整理好；如果还想再上台阶，同一套环境直接交给 agent-lightning 框架做 RL 训练，skill 阶段攒下的评测和记录全部复用。

常见踩坑

  • gh 版本旧：gh skill 是 v2.90.0 才有的命令，老版本直接报 unknown command，升级 gh 即可。
  • benchmark 不客观：如果评测集本身有偏差（比如全是简单样本），分数涨了也不代表真变好。skill 的第一步就是审视 benchmark 质量，这步别跳。
  • 和框架混淆：skill 是纯指令文件，不需要 GPU、不需要 verl。但如果你想走 RL 训练路线，框架侧需要 CUDA 环境和 verl GPU 栈，安装步骤在官方文档的 Installation 一节。
  • 一次改太多：单变量迭代是这套方法的核心纪律。coding agent 贪快一次改三处，分数涨了也不知道为什么涨，skill 会把它拉回单变量。

同类技能对比

agent-lightning（今日推荐）

安装方式：gh skill install

核心特点：测量驱动地调优已有 agent 的 prompt/工具/模型配置

适用场景：手上已有 agent，想系统提分或降本

热度：⭐ 17.8k

SkillAnything（08-13 推荐）

安装方式：npx skills add

核心特点：从目标出发生成可测试的新 skill

适用场景：还没有 skill，要从零造一个

热度：⭐ 463

SkillAlchemy（07-23 推荐）

安装方式：npx skills add

核心特点：从人物/方法论蒸馏出新 skill

适用场景：想把经验整理成 skill

热度：⭐ 287

addyosmani/agent-skills

安装方式：npx skills add

核心特点：24 条通用工程规范

适用场景：给 agent 补工程纪律

热度：⭐ 80k

SkillAnything 和 SkillAlchemy 解决"怎么造 skill"，agent-lightning 解决"怎么优化已经存在的 agent"。前者产出的是新文件，后者产出的是被数据验证过的改进。三个技能恰好拼起来：造 skill → 装进 agent → 测量调优。

今日小结

适合手里已经有自建 agent、且苦于"调优靠感觉"的人。安装一分钟，价值在于把 agent 调优从玄学变成带记录、带分数、可回溯的工程流程。今天看完，花十分钟拿一个真实 benchmark 跑一轮单变量调优，你就能体会到分数说话和感觉说话的区别。
