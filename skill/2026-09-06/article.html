多数仓库的 README 停留在创建那天。文档烂尾比代码烂尾更普遍：迁移表结构的人不会同步更新数据流说明，加接口的人不会回去改 API 文档，AI 助手规则文件（CLAUDE.md、AGENTS.md）更是从来没人写过。divar-ir 把这个活交给了多 Agent 系统：5 个分析 Agent 并发扫描仓库的五个维度，生成阶段再派 2 个 Agent 把分析结果写成 README 和 AI 助手规则。753 stars，MIT，Claude Code 插件两条命令装好，也能按 CronJob 挂在 GitLab 上自动干活。

![aidocgen-demo](./aidocgen-demo.png)

（GitHub 仓库页面：divar-ir/ai-doc-gen，753 stars，MIT，最近提交是 Claude Code skills 插件打包）

它解决什么问题

代码文档有一个反人性的事实：写一次的成本高，持续维护的成本更高。新功能上线两周后，代码变了 40%，文档还停在原地。团队接手一个新仓库，读代码靠人肉翻，上 GitHub 找 README，发现 README 讲的还是三年前的架构。

AI 助手让这个问题的后果扩大了。Claude Code 改一个项目，靠的是它自己读仓库 + CLAUDE.md 里的约定。CLAUDE.md 没写，它就靠猜；猜错了，改完的代码和项目实际风格脱节。文档不只是给人看的，也变成了 AI 的上下文。

ai-doc-gen 的定位是把"分析"和"写文档"拆开。分析是确定性的活（这个模块被谁引用、数据从哪流到哪、API 契约是什么），适合并发跑；写文档是根据分析结果组织语言，一个生成 Agent 就够了。拆开后，两个阶段各自能独立跑、独立重试，也方便你把分析结果留在 .ai/docs/ 里当团队共享事实源。

核心原理

整套系统是"分析—生成"两段流水线，用 pydantic-ai 写成的多 Agent：

  1. 分析阶段：AnalyzerAgent 调度 5 个分析 Agent 并发执行（asyncio.gather，单个 Agent 失败不影响其他，只要有一个成功就算通过），各自负责一个维度，产出写到 .ai/docs/：
    • code-structure.md — 文件树与模块关系
    • data-flow.md — 状态与数据穿越路径
    • dependencies.md — 包/模块导入拓扑
    • request-flow.md — API 调用链路
    • api-endpoints.md — 接口定义与输入输出契约
  2. 生成阶段：两个 Agent 并行。DocumenterAgent 消费分析结果生成 README.md（章节可配置，支持 Mermaid/C4 图和 --use-existing-readme 把旧 README 当上下文）；AIRulesGeneratorAgent 生成 CLAUDE.md、AGENTS.md 和 .cursor/rules/*.mdc，明细级别有 minimal / standard / comprehensive 三档，文件已存在时默认跳过不覆盖。
  3. 自动化模式：cronjob analyze 接 GitLab，扫描活跃项目、跑分析、开 Merge Request（分支 ai-analysis-YYYY-MM-DD，提交带 [AI] 前缀），文档由维护者 review 后点合并——不强制生效，只提建议。

配置分三层，优先级 Pydantic 默认值 < .ai/config.yaml < CLI 参数。每个 Agent 可以单独配模型和 endpoint，都走 OpenAI 兼容 API（OpenAI、Anthropic 网关、OpenRouter、本地模型都行）。

安装配置

方式一：Claude Code 插件（推荐，无需 API key，无需 Python 环境）

/plugin marketplace add divar-ir/ai-doc-gen
/plugin install ai-doc-gen@divar

装完获得三个 skill：analyze-codebase、generate-readme、generate-ai-rules，命令式调用即可。

方式二：源码安装（可以 CLI 跑、接 CronJob）

git clone https://github.com/divar-ir/ai-doc-gen.git
cd ai-doc-gen
curl -LsSf https://astral.sh/uv/install.sh | sh
uv sync                                  # Python 3.13 + uv 是前置条件
cp .env.sample .env                      # 填 LLM 的 base_url 和 key
mkdir -p .ai && cp config_example.yaml .ai/config.yaml
uv run src/main.py analyze --repo-path .
uv run src/main.py generate readme --repo-path .
uv run src/main.py generate ai-rules --repo-path .

并发度用 ANALYZER_MAX_WORKERS 控制，0 表示按 CPU 数自动检测。团队部署有 Dockerfile 和 Helm Chart（K8s CronJob）。

使用指南

场景一：接手陌生仓库，先让 5 个 Agent 探路

git clone 到一个新项目后，直接：

uv run src/main.py analyze --repo-path . --repo-name new-repo

.ai/docs/ 下出现五份分析文档。先读 code-structure.md 搞清楚模块边界，再翻 request-flow.md 看请求从入口到 DB 的链路。五个维度的分析并行跑，比单 Agent 通读全仓库快得多，每个维度还不互相污染上下文。读完分析再让 agent 改代码，它一上来就带着结构认知。

场景二：给老项目补 README，保留旧文语境

仓库有十几年前的 README，直接覆盖生成风险太大：

uv run src/main.py generate readme --repo-path . --use-existing-readme

旧 README 作为上下文传给 DocumenterAgent，新生成的文档会延续原来的叙述风格和术语，只补上缺口（架构总览、启动方式、API 清单）。生成前可以先把 README 里确定过时的大段描述删掉，避免它被当成"事实"吸收进新文档。

场景三：GitLab 上挂 CronJob，文档自动提 MR

想根治"README 永远滞后"，在 GitLab 上配一个定时任务：

uv run src/main.py cronjob analyze --max-days-since-last-commit 14

每 14 天扫描一次活跃仓库，自动分析并开 MR。MR 由工程师 review，合并即生效。它不做强推，文档变化被当成代码评审的一部分，不占用谁的额外时间。

进阶技巧

每个 Agent 用不同模型。.ai/config.yaml 里给 API 契约分析配贵一点的模型（输出质量要紧），给文件树分析配本地小模型省成本。所有模型走 OpenAI 兼容接口，per-agent 独立配置，一套配置混着用。

CLAUDE.md 会越写越长，控制长度。生成 ai-rules 时用 --detail-level standard --max-claude-lines 600 限制行数，CLAUDE.md 太长会让每次会话都背上冗余上下文，600 行以内够用。

观测成本。项目内置 OpenTelemetry 和 Langfuse 集成，团队跑 cronjob 时可以看每次分析花多少钱、哪个 Agent 慢，决定要不要给某个维度换小模型。

常见踩坑

Python 版本要求 3.13。pip install 的方式能装上，但跑起来报语法错误——仓库用 Python 3.13 的语法特性。低版本机器建议直接用插件方式安装，或者用 uv 安装的隔离 Python。

生成前先备份人工维护的内容。generate ai-rules 对已存在的文件默认跳过，但 generate readme 会覆盖 README.md。给重要仓库先跑 git commit 或者把旧 README 留在 git 历史里，翻车了 git checkout 回来。

CronJob 模式权限不足。gitlab token 只有读权限的话，MR 创建会失败。需要 api scope 的 token，且账号要有目标仓库的开发权限。
