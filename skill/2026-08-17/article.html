让 Claude Code 单打独斗修一个大任务，它会一步步串行干：改完前端改后端，上下文越堆越厚，没有第二双眼睛审它写的代码，跑一半卡住也没人接管。oh-my-claudecode（OMC）把"一支开发团队"装进一个 Claude Code 插件：规划、执行、验证、修复各司其职，还能在 tmux 里拉起真实的 Codex、Gemini CLI 分屏当外部顾问。38,597 stars，MIT 协议，2026 年 1 月发布以来迭代极其活跃。

多 agent 编排领域 7 月 18 日推荐过 workflow-orchestrator（75 stars）。OMC 的热度是它的 500 倍，且解决方式完全不同：workflow-orchestrator 靠 hook 和隔离 agent 编排，OMC 直接把跨模型 CLI 进程拉进 tmux 分屏，还带模型路由和 HUD 状态栏。同领域重磅新秀，值得单独说透。

![omc-character](./omc-character.jpg)

它解决什么问题

单 agent 处理复杂任务有四个绕不过去的坎。第一是串行：一个任务干完才能干下一个，没有依赖图，没有并行波次。第二是上下文膨胀：所有子任务的探索、报错、修复痕迹全堆在一个会话里，做到一半 token 见底。第三是没有对抗性检查：agent 自报"已完成"，没人验证它是不是真的完成了。第四是模型错配：改个注释也用顶级模型，账单白白烧掉。

OMC 的思路是把人管团队的方式搬进来。你是发起人，它是项目经理：把任务拆成带依赖的阶段，派不同 agent 并行执行，每个阶段收尾时验证，没通过就进入修复循环。README 里那句话很准确："Don't learn Claude Code. Just use OMC."

核心原理

先分清两个表面。OMC 有终端 CLI（omc ...）和会话内 slash 命令（/team、/autopilot）两套入口，底层走同一套编排逻辑。装好之后不改变 Claude Code 的用法，你在会话里正常说需求，也可以显式调用某个模式。

Team 模式是当前的主编排面（v4.1.7 起取代了旧的 swarm）。它把一次任务跑成五阶段流水线：team-plan 拆解任务、team-prd 生成需求、team-exec 并行执行、team-verify 验证结果、team-fix 修复问题。每个阶段有明确的进出条件，执行阶段自动按依赖关系调度并行 agent。

最有意思的是 v4.4.0 的改动：移除了 Codex/Gemini 的 MCP 服务器，改为 CLI-first。omc team 2:codex "review auth flow" 会在 tmux 里拉起两个真实的 Codex CLI 进程分屏干活，任务完成进程即死，不留常驻开销。这意味着 Claude 之外，Codex、Gemini、Antigravity、Grok、Cursor 的 CLI 都能作为 worker 加入你的团队，各模型干各模型擅长的事。

模型路由是省钱的另一层。OMC 内置 19 个专职 agent（架构、研究、设计、测试、数据科学等），每个 agent 有推荐的模型档位：简单任务自动派 Haiku 级模型，复杂推理派 Opus 级。官方称智能路由省 30-50% token。会话里还有个 HUD 状态栏，实时显示当前哪个 agent 在干什么。

安装配置

推荐走 Claude Code 插件市场，两条命令在会话里输入。注意必须一条一条输入，一次粘贴两行会失败：

/plugin marketplace add https://github.com/Yeachan-Heo/oh-my-claudecode
/plugin install oh-my-claudecode

装完在会话里跑 /setup（或终端跑 omc setup）完成初始化。走 npm 路径也行：

npm i -g oh-my-claude-sisyphus@latest
omc setup

包名叫 sisyphus（西西弗斯），取的正是那个推石上山的神话：任务循环往复，直到验收完成。装完直接在会话里说一句 autopilot: build a REST API for managing tasks 就能开工，也可以显式用 /autopilot 调用。

使用指南

场景一：/team 并行清一批编译错误

仓库升级依赖后冒出几十个 TypeScript 报错，分布在三个包。在会话里输入：

/team 3:executor "fix all TypeScript errors"

Team 模式会先规划修复顺序，然后拉起 3 个 executor 并行处理，各自负责一片文件。全部完成后自动进入 verify 阶段跑类型检查，没过就转 fix 阶段再来一轮。你得到的是收尾报告，不是几十条中间过程。

场景二：omc team 拉起 Codex 当外部评审

你想让另一个模型审一遍自己的代码，又不想手动切工具。终端里跑：

omc team 2:codex "review auth flow"

tmux 里会出现两个真实的 Codex CLI 分屏，各自独立评审认证流程。评审结论回传给主会话。Codex、Gemini、Antigravity、Grok 的 CLI 都能这样拉进来，前提是对应 CLI 已安装并登录。

场景三：/autopilot 全自动交付一个功能

需求明确、不想逐步盯着时，用 autopilot：

/autopilot "build a todo app with Next.js and Tailwind"

单个 lead agent 从头干到尾，遇到需要确认的点才停下来问你。要更严的质量门，可以配 stage profile：

{
  "autopilot": {
    "workflows": {
      "plan-build-qa": {
        "version": 1,
        "stages": ["ralplan", "execution", "qa"]
      }
    }
  }
}

这样每次 autopilot 都先规划、再执行、最后过 QA 门。UltraQA 模式更狠，它会循环跑测试、构建、lint，失败就诊断修复再跑，直到全部通过才收工。

进阶技巧

三模型顾问合成：/ccg 一条命令把同一个问题同时抛给 Codex 和 Antigravity，Claude 综合三方意见给出结论。适合架构选型这类没有标准答案的问题。

持续验证循环：/ralph "refactor auth" 进入持久模式，带 verify/fix 循环，任务必须完全做完才停，不给"部分完成"留口子。适合那种"失败就是事故"的改动。

常见踩坑

npm 安装时可能看到 deprecated prebuild-install@7.1.3 警告。它来自上游 better-sqlite3 的原生依赖，不是 OMC 自己能修的，官方在 issue #2913 里跟踪，不影响安装结果，忽略即可。

插件市场两条命令一次粘贴会失败，逐条回车。这是 Claude Code 插件安装的机制限制，README 里专门提醒过。

omc team 的 CLI worker 需要本机装了 tmux，且 codex/gemini/agy 等对应 CLI 已安装并完成认证。Windows 上没有原生 tmux，这条路径主要在 Linux/macOS 上可用；Windows 用户用会话内的 /team 一样能并行编排。

今日小结

适合两类人：被单 agent 串行效率折磨的日常开发者，装完五分钟就能用 /team 和 /autopilot 起步；想低成本引入多模型交叉评审的人，omc team 一条命令把 Codex、Gemini 拉进 tmux 当顾问。配置成本两条命令，换回来的是并行执行、独立验证和 30-50% 的 token 节省。Windows 用户用会话内命令即可，跨模型 CLI 编队留给 Linux/macOS。
