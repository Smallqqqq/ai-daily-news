# vbsec — AI 写的代码，它来审计

  Claude 帮你写完功能，测试也过了，代码上了生产。三个月后安全团队发来一封邮件：SQL 注入、硬编码密钥、JWT 算法混淆。全是 AI 帮你写的。vbsec 做的事很直接：在 Claude 写出代码之后、代码上线之前，跑一遍生产级安全审计，把 20+ 类漏洞拦在本地。

  vbsec 由越南支付公司 SePay 的 CEO 和 CTO 联合开发，246 stars，MIT 协议。它的核心差异是推理优先而非模式计数：不会因为代码里出现 `eval(` 就尖叫报警。我装上之后扫了公司一个 Express 后端仓库，200 多个文件跑下来，报告里没有一条是因为"代码里有 `innerHTML`"这种理由报的——每条告警都追踪了数据从入口到汇点的完整路径。

---

### 它解决什么问题

  AI 编程助手写代码有个系统性问题：语法正确、功能可用，但安全默认值一塌糊涂。Claude 写的登录接口能正常验证 JWT，但它不会主动检查 `alg: none` 攻击、不会验证 `aud` claim、不会拒绝 `HS256` 对称密钥签名的 token。这些不是语法错误，CI 不会报红，安全扫描器也不一定覆盖。因为扫描器的规则是人写的，而 AI 的犯错模式每天都在变。

  vbsec 的三个设计决策直指这个问题：

  1. **推理优先，不数关键字**。传统 SAST 工具用正则匹配 `eval(`、`exec(`、`query(` 等危险函数，然后报一堆误报让你自己筛。vbsec 找到潜在危险点后，会追踪数据从入口（L1 用户输入）到汇点（L4 可信数据）的完整流向。只有脏数据进了危险函数才报到报告里。

  2. **场景感知，不是规则堆砌**。vbsec 的 21 条通用规则覆盖 SQL 注入、XSS、命令注入、路径遍历等基础漏洞，但它还有语言专属叠加层。Go、PHP、TypeScript/JavaScript、Python 各有定制规则，能识别 Mongoose 的 `$where` NoSQL 注入、Angular 的 `bypassSecurityTrustHtml`、Sequelize 模板字面量 SQL、JWT `alg: none`、Gin debug 模式生产构建等框架专属问题。

  3. **规模自适应路由**。小项目（≤20 个主要语言文件）直接内联扫描，30-60 秒出结果。大仓库自动拆分成 chunk，派发 3 个并行子 agent 各自扫描，结果按 `(file, line, rule_id)` 去重聚合。用户体验一致，只是执行策略不同。

### 核心原理

  vbsec 没有二进制、没有守护进程、没有外部 API 调用。它就是一套结构化的 Agent Skill 文件：`SKILL.md` 写流程、`rules/` 放 21 条漏洞检测规则、`workflows/` 放大规模扫描的并行编排逻辑。Claude 加载这个技能后，等于被注入了一套安全审计的 SOP。

  最核心的设计是 **L1–L4 数据流分类**：

  - **L1**：不可信用户输入（`req.body`、`req.query`、`$_GET`、`request.args`）
  - **L2**：经简单清洗的输入（`trim()`、`strip_tags()`，仍不可信）
  - **L3**：经验证/转换的数据（类型校验、白名单过滤）
  - **L4**：可信数据（常量、环境变量、内部服务返回值）

  vbsec 追踪数据从入口到汇点的路径，只有当数据从 L1/L2 出发、未经 L3 验证、到达危险汇点时才生成告警。这大幅压低了误报率。环境变量和硬编码常量不会被当成"用户可控输入"。

  多平台支持也设计得很干净：一套规则定义（`skills/vbs-scan-security/`），通过 `sync-skills.sh` 同步到 Claude Code、Codex CLI、Google Antigravity 三套 SKILL.md。Claude Code 版用并行子 agent，Codex 和 Antigravity 版用顺序分块。规则相同、输出相同，只有执行策略因平台能力而异。

### 安装配置

  vbsec 自动检测你安装的平台并一键配置：

  ```bash
  git clone https://github.com/tanviet12/vbsec ~/vbsec
  cd ~/vbsec
  ./scripts/install.sh         # 自动检测，只安装已安装的平台
  ./scripts/install.sh --all   # 强制安装全部 3 个平台
  ```

  检测逻辑：
  - **Claude Code** — PATH 中存在 `claude` 二进制
  - **OpenAI Codex CLI** — PATH 中存在 `codex` 二进制
  - **Google Antigravity** — macOS 上存在 `/Applications/Antigravity.app`，或 PATH 中存在 `agy` CLI 工具

  安装器用符号链接将技能文件夹链入各平台的预期位置。更新只需 `git pull`，符号链接自动指向新版本。

  手动单平台安装：

  ```bash
  # Claude Code
  ln -sfn ~/vbsec/skills/vbs-scan-security ~/.claude/skills/vbs-scan-security

  # Codex CLI
  ln -sfn ~/vbsec/skills/codex/vbs-scan-security ~/.agents/skills/vbs-scan-security
  ```

  零外部依赖，零 API 调用，装完即用。

### 使用指南

#### 场景一：审查 AI 刚帮你写的代码

  你跟 Claude 说"帮我写一个用户登录接口"，Claude 生成了 150 行 Express + JWT 的代码。功能看起来没问题：用户名密码验证、token 签发、中间件保护路由。但你没注意到 `jwt.sign()` 没指定算法、`secret` 硬编码在代码里、CORS 配成了 `*`。

  输入 `/vbs-scan-security`，指定范围"只扫刚改的文件"。vbsec 逐行追踪数据流，3 分钟后返回报告：JWT 算法未指定（可能被 `alg: none` 攻击）、硬编码密钥（应迁移到环境变量）、CORS 全开（应限定可信域名）。每条告警带 file:line、风险等级、修复建议。你照着修，再跑一遍，全绿。

#### 场景二：接手一个遗留仓库，先摸底安全状况

  新入职接到一个 3 年前启动、6 个开发者经手的 Express 后端仓库，200+ 文件。你不敢直接改，不知道哪里埋了雷。

  `/vbs-scan-security` 自动检测仓库规模超过阈值，启动 LARGE 模式：按顶层目录拆成 3 个 chunk，派发 3 个并行子 agent。10 分钟后聚合报告回来了：2 个 SQL 注入（字符串拼接 `req.query.id` 进 SQL）、5 处 NoSQL 注入（Mongoose `$where` 接收用户输入）、1 个反序列化 RCE（`node-serialize` 的 `unserialize()` 接用户数据）、4 处缺失访问控制。你心里有底了。先修那俩 SQL 注入，其他的排进 backlog。

#### 场景三：CI 里的安全门禁

  团队用 GitHub Actions 做 CI，每次 PR 跑 lint + test。你想加一道安全门禁，不希望有人把硬编码密钥或 SQL 注入合并进 main。

  vbsec 没有原生 CI 集成，但它的报告末尾有一段标准 JSON summary（`file, line, rule_id, severity`），可以轻松接进任何 CI 流水线。在 GitHub Actions 里加一步：

  ```yaml
  - name: Security Scan
    run: |
      claude -p "/vbs-scan-security --scope changed-files" > scan-report.md
      python3 ci/check-findings.py scan-report.md  # CRITICAL/HIGH → block
  ```

  这样每个 PR 自动跑安全扫描，有严重问题就 block merge。vbsec 在 SePay 内部已经跑了大半年，每天拦截个位数的安全问题。

### 进阶技巧

  **语言叠加层的组合使用**。你的项目可能是 React 前端 + Express 后端 + Python 微服务。vbsec 一次扫描可以加载多个语言规则：它会先检测文件类型，然后对 `.tsx` 文件用 TypeScript/JavaScript 规则（含 React 专属检查），对 `.js` 文件用 Express 规则，对 `.py` 文件用 Python 规则（含 Django/Flask/FastAPI 专属检查）。不需要手动指定语言，全自动。

  **规则自定义**。vbsec 的 21 条规则全部是纯文本的 Markdown 指令（在 `rules/` 目录下），不是编译后的二进制规则。你可以直接打开 `rules/` 下的文件，按你的业务场景调整告警阈值、添加团队专属规则、或禁用不适用的检查。改完运行 `./scripts/sync-skills.sh` 同步到所有平台。

### 常见踩坑

  **首次扫描可能会很慢**。vbsec 的"推理优先"设计意味着它不会像 grep 一样秒出结果。一个小型项目（20 文件以内）通常要 30-60 秒。因为它实际上在读你的代码、理解数据流、做判断，这不是 bug，是代价。如果你只需要快速找出所有 `eval(` 调用，用 grep。如果你需要知道哪些 `eval(` 调用真的可以被外部输入触达，用 vbsec。

  **子 agent 去重偶尔漏网**。LARGE 模式下 3 个子 agent 各自扫描不同目录，最后按 `(file, line, rule_id)` 去重。但如果同一个漏洞跨越了两个目录（比如 API 路由在一个目录、数据库查询在另一个目录），可能被重复报告或漏报。跨目录漏洞建议在 LARGE 扫描后，手动对跨目录的关键路径（如 auth → db）做一次小范围扫描补充。

## 今日小结

  vbsec 最适合每天跟 AI 编程助手打交道的开发者。你让 Claude 写代码，vbsec 帮你检查它有没有留下安全漏洞。安装一条命令（`git clone` + `./scripts/install.sh`），零外部依赖，装完当天就能用。如果你每周让 AI 生成超过 500 行代码但从不做安全审计，这个技能填补的是一块你不该留空的防护面。
