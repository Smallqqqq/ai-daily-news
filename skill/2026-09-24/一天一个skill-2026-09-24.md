# security-audit — 让 Claude Code 变成一支安全审计队，每条结论都能追到源码

　　AI 写的代码正以远超人工审计的速度堆进仓库。对着项目敲一句 `security audit this codebase`，agent 立刻能吐出十几条看着像漏洞的东西，但没人说得清里面有几条是真的。单 agent 做安全审计有两个绕不过去的毛病：它给自己打分，以及你根本不知道它看过哪些地方。Cloudflare 把这套流程开源成了一个 Skill。

![[security-audit-hero.png]]

### 它解决什么问题

　　单 agent 审计的第一个毛病是**自己出题自己判卷**。同一个模型提出候选漏洞，再由同一个模型判断这个候选成不成立，结论必然向"我说得对"倾斜。安全审计里最难的不是找到可疑代码，而是承认自己找到的东西站不住脚。

　　第二个毛病是**覆盖不可见**。一轮扫完，你不知道它读过哪些文件、哪些信任边界压根没碰过。于是"没发现问题"和"没看过"在报告里长得一模一样。Cloudflare 在官方博客里给了个数据：同一个仓库跑多轮，单轮平均只能找到重复跑最终能找到的漏洞总数的一半左右。

　　security-audit 就是针对这两点设计的。它的做法是拉起一支分工明确、互相不认识的审计队，每个人都必须留下可核查的证据。

### 核心原理

　　这个 Skill 把一个仓库的审计拆成六个阶段，每个阶段的产物都落成磁盘上的文件，而不是留在某个 agent 的上下文里。

　　**第一阶段，侦察。** 主 agent（skill 里叫 parent）派三个并行的子 agent 去摸清架构、信任边界、输入面、历史证据和确定性覆盖情况，汇总成 `architecture.md` 和 `coverage-ledger.json`。覆盖账本（coverage ledger）是这个 Skill 的地基：它把待审的目标切成稳定的覆盖单元，之后每一次派活、每一次判断"还缺什么"，都对着这个账本来。

　　**第二阶段，按账本狩猎。** 每个覆盖单元分配给一个隔离的 hunter agent，各自记录检查了什么；再派 coverage critic 专门找账本里没被覆盖到的缝。这一步的产出不是结论，是待验证的候选。

　　**第三阶段，候选验证，这是整套设计里最关键的一环。** 每一个候选漏洞都交给一个全新的 verifier，而这个 verifier 的任务是**证伪**它。Skill 的设计原则写得很直白：「检查一条结论的 agent，永远不能是发现它的那个 agent。」

　　**第四阶段，结构化输出。** 所有结果写进 `findings.json`，并且必须通过 `report-schema.json` 的校验。判决分三种，语义严格区分：

| 判决 | 含义 |
|------|------|
| `confirmed` | 有完整可追溯的源码依据 + 有边界、被实际观测到的结果 |
| `needs_validation` | 有一个确切未解决的事实，**不给严重等级** |
| `rejected` | 候选被证伪，记录在案 |

　　`needs_validation` 这个中间态是这个 Skill 最见功力的地方。它拒绝在事实不清楚的时候硬给一个 severity，逼着审计者把"我确定知道什么、我还不确定什么"分开写。

　　**第五阶段，独立复核。** 再由一批全新的 agent 去核对最终报告里的源码声明。如果某条结论在复核中被实质替换，替换后的版本要再过一遍另一个独立 verifier。主 agent 会在第四、第五阶段调用 `validate-findings.cjs` 做校验；覆盖账本则由 `validate-coverage-ledger.cjs` 在创建后及之后每次更新后校验。两个脚本都是零依赖的 `.cjs`。

　　**第六阶段，中性报告。** 从已验证的记录和覆盖账本推导出 `REPORT.md`、`FINDINGS-DETAIL.md`、`NEEDS-VALIDATION.md` 三份文档。报告不区分目标是自研还是第三方，只陈述证据。

　　多条设计原则直接写在 README 里，值得原样抄下来：

- **只确认已确立的边界失效**。有源码依据但被阻断的线索，保留为 `needs_validation`，附上它确切未解决的那个事实。
- **严重等级必须有影响面**。likelihood × impact，而不是"跟检查表不一致"。
- **纵深防御的缺口不是漏洞**。如果 A 层已经拦住了攻击，B 层缺失只是一条加固建议。
- **多轮跑能提升覆盖**。这个结论有实测支撑。

![[security-audit-funnel.png]]

　　上面这张是 Cloudflare 官方给出的漏洞漏斗。左边是发现环节（VDH）：20,799 条原始候选，经过验证活下来 12,057 条，其中 5,044 条判为重复、2,302 条在验证阶段被拒、1,227 条需要复现。右边是验证环节（VVS）：系统内共 13,841 个 bug，去重折叠掉 5,442 条、1,154 条判为提错仓库或不算风险，最终 7,245 个送到业务团队手里——其中判定为可被互联网利用的有 396 个，剩 6,849 个不做此判定。按等级分，Critical 41 个、High 777 个、Medium/Low 6,427 个。

　　这些数字背后的系统被 Cloudflare 称为 vulnerability harness，覆盖 145 个仓库，由这个 Skill 演化而来。官方披露的几个数据点：验证拒绝率从 40% 降到 11%，高可信结论占比从 35% 升到 58%；一个三万行左右的标准测试仓库跑出 100 条发现、确认 80 个真实 bug，端到端约 14 小时；单条修复平均 5 分钟。运行状态存在 SQLite 里，以 `(run_id, repo, stage)` 为键，模型被当成无状态的计算单元，任何阶段都能断点续跑，每个 agent 的上下文控制在窗口的 25% 以内。

### 安装配置

　　用 Skills CLI 安装，两条命令的区别只在于装到哪一层：

```bash
# 装到当前项目（只对这个仓库生效）
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
```

```bash
# 装成用户级，所有仓库都能用
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit \
  --global
```

　　`npx skills --help` 里有 agent 选择和非交互模式的参数。

　　三个前置条件，缺一个都会影响它能做到哪一步：

1. **一个支持工具调用和并行子 agent 的 coding agent**。这套流程的骨架就是并发调度 hunter 和 verifier，单线程 agent 跑不出效果。
2. **Node.js**，给两个零依赖的校验脚本用。
3. **操作系统级的沙箱**——这条是硬要求，下面单独说。

### 使用指南

#### 场景一：给一个仓库做完整安全审计

　　触发条件：你要对一个代码库做全面安全审查，或者要一份能交给别人的报告。

　　操作：在目标仓库里启动 agent，说一句就行。

```
security audit this codebase
```

　　也可以明确指定范围和输出位置：

```
do a security review, output to ~/audits/my-project
```

　　预期结果：Skill 会走满全部六个阶段。默认输出到 `~/security-audit-skill/<repo-name>/run-<N>/`，`<N>` 是下一个没用过的整数，所以多跑几次不会互相覆盖。目录里会有 `run-metadata.json`、`architecture.md`、`coverage-ledger.json`、`findings.json` 和三份 Markdown 报告。

　　注意它只在两种情况下写进目标仓库内部：你显式指定了仓库内的目录，**并且**主 agent 确认版本控制忽略整个目录。否则它会停下来问你要一个外部路径。

#### 场景二：只审一段改动，或者一个子系统

　　触发条件：上线前只想确认这次改动有没有引入安全问题，不想为全仓库付一遍成本。

　　操作：把范围说清楚。

```
find security vulnerabilities in ./src/payment
```

```
security audit the diff between main and this branch
```

　　预期结果：这会被识别成一次 scoped run。账本只给范围内的攻击面建单元，范围外全部记为 `out_of_scope`，注意是 `out_of_scope` 而不是 `covered`。报告会明确标注自己只覆盖了一部分。

　　如果目标很大，还可以先选 profile。三个档位：`quick` 只跑一轮 hunter 加一轮 coverage critic，适合小目标或快速初筛；`standard` 是默认档；`deep` 面向高风险或大目标，按子系统和生命周期模式拆单元，critic 要跑到干净为止，候选验证和最终记录复核保持为两批独立的新 agent。

#### 场景三：把审计结果接进工单系统

　　触发条件：你想批量消费审计结果，而不是读一份 Markdown 报告。

　　操作：直接读 `findings.json`。它是机器可读的，每条记录都能追溯到具体源码，并且已经通过了 schema 校验。

```bash
# 只看确认成立的
cat findings.json | jq '.findings[] | select(.verdict == "confirmed")'

# 单独捞出来未解决的问题，这些不该当漏洞处理，而是该有人去查清楚
cat findings.json | jq '.findings[] | select(.verdict == "needs_validation")'
```

　　预期结果：`findings.json` 的三种判决天然对应三种处理方式：`confirmed` 进修复队列，`needs_validation` 进调查队列且不带严重等级，`rejected` 留档避免下一轮重复提出。因为每条都标了源码位置，工单里可以直接附上。

### 进阶技巧

**多轮跑是设计的一部分，不是补救措施。** 脚本会读取同仓库之前所有兼容的 `coverage-ledger.json` 和 `findings.json`，对比当前源码和每条历史记录，来决定这一轮该往哪打。逻辑相当细致：历史 `confirmed` 记录只有在相关源码和条件都没变、且证据仍满足当前契约时，才会被带入当前候选集；源码变过的，生成一个新的复核单元重新走独立验证；历史 `rejected` 只压制那条失败的断言本身，不压制它所在单元的覆盖。也就是说，跑第二遍是官方认可的唯一提高召回率的手段。

**用预算门禁防止 agent 烧钱。** 你可以给 `run-metadata.json` 里的 `budget` 设一个最大 agent 调用次数。主 agent 在启动侦察之前会先做一次严格的门禁计算：预留四次基线侦察调用、critic 调用、以及至少一个 verifier 调用，剩下的才分配给 hunter。如果预算连这个最低配置都覆盖不了，它**一个 agent 都不会启动**，直接把 `run_status` 标成 `incomplete` 并说明原因。没把握就不跑。

**攻击面清单可以按需加载。** 仓库里除了 `SKILL.md`，还有十一个攻击类目文件，覆盖内存安全与二进制、AI/LLM（prompt 注入、工具调用、输出处理）、Web 协议与认证、客户端、供应链与发布、云与部署、RPC 与消息队列、资源耗尽、数据隔离与生命周期、桌面移动与本地 IPC。审 LLM 应用就带 `AI-AND-LLM.md`，审 IoT 固件就带 `MEMORY-SAFETY-AND-BINARY.md`，不用把所有类目一次性塞进上下文。

### 常见踩坑

**沙箱不满足时它会拒绝执行，这是有意设计，不是缺陷。** 这是最需要提前知道的一条。Skill 要求跑目标代码时必须在一个操作系统级沙箱里，且必须同时满足四项：禁绝外部网络（需要本地通信时只给隔离的 loopback 命名空间）、环境变量从显式白名单构建且 `HOME`／临时目录／缓存都指向 scratch、目标只能往自己分配到的 `scratch/` 目录写、以及显式的 CPU／内存／进程数／文件大小／磁盘／墙钟时间限制。

　　四项里只要有一项无法强制，它就不执行目标代码，而是把"缺少沙箱能力"本身记成一条 `needs_validation` 阻塞项，并给出一份安全的验证方案。所以如果你在裸机或者权限很松的容器里跑，看到大量 `needs_validation`，先回头检查沙箱，它在按设计工作。另外这四项之外还有行为约束：用假的凭证和 fixture，不碰任何已部署的端点、共享基础设施、生产身份或别人的数据，不测试线上进程的可用性。

**子 agent 的写入是被隔离的，主 agent 是唯一写入者。** 每个 hunter 或 verifier 拿到的是 `<output-dir>/agents/<agent-id>/` 下独立的 `scratch/` 和 `artifacts/`。scratch 归 agent 和目标代码写，artifacts 归主 agent 独占，永远不暴露给沙箱。从 scratch 提升文件到 artifacts 走一套防竞态的流程：校验相对路径（拒绝绝对路径、空段、`.`、`..`、符号链接）、从持有的描述符逐级 no-follow 遍历、`fstat` 确认是普通文件且硬链接数恰好为 1、读写两侧都强制字节上限、复制后再 `fstat` 一次确认身份没变。任何一步不可用或失败，就直接丢弃该文件；如果它恰好是决定性证据，记为 `needs_validation` 并写明阻塞原因。

　　顺带一个容易忽略的细节：agent ID 必须匹配 `^[a-z0-9][a-z0-9_-]{0,63}$`，且不能等于 Windows 设备名（`con`、`prn`、`aux`、`nul`、`com1` 到 `com9`、`lpt1` 到 `lpt9`）。在 Windows 上跑的时候这个校验会救你一次。

**别指望一轮扫完。** Cloudflare 明确说他们没有召回率指标，任何声称有的数字都是"纯属臆测"。单轮找到的比例大约是一半，所以计划里就该排不止一轮。

**它默认不会乱动手。** Skill 默认处于 guidance（指导）模式：加载它并不授权它执行完整的六阶段流程或创建文件。只有当你明确要求审计、渗透测试、全量/端到端审查，或者索取报告产物时，才会进入 full audit 模式。如果请求两种模式都说得通，它会先问你一个聚焦的问题，而不是直接开干。

　　前面推过的 SkillSpector 和今天这个都在"安全"这个大类下，但解决的问题在两头：SkillSpector 审的是**你要装进来的东西**，那个 SKILL.md 里有没有藏 prompt 注入、脚本会不会读 `~/.ssh`；security-audit 审的是**你自己写的代码**——你的服务有没有真实的信任边界失效。一个管供应链入口，一个管自研资产，两个都装上并不重复。

## 今日小结

　　如果你维护着任何跑在生产上的代码，security-audit 值得今天花五分钟装上。安装就是一条 `npx skills add`，成本几乎为零；真正需要投入的是理解它的三个约定——覆盖账本决定它看哪里、对抗验证决定它信什么、`needs_validation` 决定它不装懂。

　　它真正的价值是把安全审计里最难自证的两件事——覆盖面和结论可信度——变成磁盘上可核查的文件。验证拒绝率从 40% 降到 11%、可信结论占比翻倍，是 Cloudflare 在 145 个仓库上跑出来的结果，这套方法在你自己的仓库里有没有同等效果，取决于覆盖账本划得好不好、沙箱给得够不够。挑一个你熟悉的、有明确信任边界的服务先跑一轮 `quick`，看看它给 `needs_validation` 的那些条目：如果里面有几条是你确实回答不上来的，那这个 Skill 已经帮你找到东西了。
